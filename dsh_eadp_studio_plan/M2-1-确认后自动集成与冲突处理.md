### 3.3 确认后自动合并、可选评审与成果追溯（节选）

同一项目每个需求使用独立 worktree/分支和后端占用，满足前置完成及场景门禁后才开始原型生产。A、B 无依赖时可以并行，各自在本人 worktree 验证当前需求；A 确认完成后自动合入，B 本地不自动更新，B 随后确认完成时基于新的认可集成头生成和检查集成候选。B 若依赖 A，则在设计时登记 A 及所需范围，必须等 A 自动合并并被后端确认完成后才能认领，以包含 A 的认可集成状态作为 B 的工作基础。

作者看到业务差异、输入/前置依据和检查摘要，不需要阅读源码。两条路径为“直接确认”和“AI辅助评审后作者确认”：直接路径点击“确认完成”即记录作者确认并自动继续提交合并；选择“提交评审”时，AI基于固定候选和需求/验收依据给出问题与建议，作者处理意见并自行确认，之后进入同一提交合并流程。两条路径均无需他人或管理员审批，不建立独立业务评审者角色。AI输出只提供辅助判断，不能触发作者确认、合并或完成；已有结构、工程、Mock、安全、占用、前置及精确候选检查仍须成立。

AI辅助评审绑定实际读取的固定候选、需求版本及输入依据，修订后重新检查、更新评审依据并由作者重新确认，旧报告不能证明新版本已评审。AI报告、对话及工具过程留本地，最终确认记录区分直接确认或AI辅助评审后确认，关联固定版本及必要的作者处置依据；后端不接收评审全文或过程日志，不显示“交叉评审通过”。实际分支权限不允许操作时返回真实拒绝，不擅改保护或偷偷换提交路径；GitLab MR 合流本身不等于业务完成。

原型菜单的最终确认须明确或选择一个需求，确认按钮与明确的用户自然语言确认进入同一 Host 操作。提交包含本任务完整相关代码及场景/需求/关系等文档，并基于认可集成头形成项目快照；“完整”不等于把工作空间全部未提交文件一起提交，其他需求未完成草稿必须排除。场景/需求阶段已确认 MD 已在 Git 中留存，最终完成引用其精确版本；新改内容仍需确认，旧哈希不能替代。Git 条件更新与后端完成均成功后自动固定基线，再由 Host 后台生成清单，不要求进入基线菜单二次审批。

集成遵守 2.7.4：受理和最终完成两次核验当前占用人及占用 ID，基于认可集成头只合入本任务，检查精确候选后条件更新稳定分支，后端接受后才释放。公共路由、组件及清单可能冲突；集成窗口短暂串行，不阻断其他需求本地生产。冲突展示受影响需求及业务差异，由作者决定取舍，无法可靠处理的源码冲突交维护者处理；修订后重新检查，不要求非研发人员编辑冲突标记，不自动宣布合并完成。管理员释放与在途合并竞态按操作记录核对，未获认可的合入阻断后续集成和发布，不能被其他任务顺带带入。

撤销未共享修改只处理已核验属于本任务的补丁；人工改动或基线不匹配时阻断。不得清空目录、强制 reset 或覆盖 worktree。已共享但未认可的错误集成通过可追溯反向提交纠正，并核对 Git/后端集成状态；已认可成果的业务修改另建需求版本、检查和完成。该纠正是保障当前集成有效的工程处理，不提供旧站点恢复功能。验收要求无静默覆盖、无提交丢失、冲突可解释且可处理，不承诺协作无冲突。
