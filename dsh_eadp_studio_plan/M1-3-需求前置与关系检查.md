## 实现规格（原文节选，小节编号保留）

### 3.1 项目资产到原型任务的契约（节选）

用户在场景菜单新建场景即在 `场景/` 创建一个 MD，通过对话完善。明确用户自然语言确认或按钮共用 Host 入口，冻结字节并计算 SHA-256 内容哈希，提交推送 Git 成功后上报固定引用/哈希及必要控制元数据。后端接受后默认调用 Agent 拆分本地需求候选并展示标题；候选草稿不是已确认需求，不为全部候选预占需求。

用户选中候选后预留正式需求 ID、取得设计占用，在 `需求/` 完善对应 MD，整理业务目标、使用者、流程、规则、字段、异常、验收条件和排除项，并明确前置需求 ID 及要求完成的需求版本或范围；没有前置时显式记录无前置。前置可以尚未完成，不能因此阻止本需求录入；场景关系、复用来源和软件包依赖不替代生产前置条件。技术标识和页面/Mock 约定由工具填充，不要求作者手工操作。需求确认也先推送 MD，再向后端登记哈希及固定引用，随后自动申请编码。

每次确认绑定精确字节与文件/资产身份；文件变化后旧哈希仍是历史依据，当前文件恢复待确认。两个确认入口、响应丢失重试和场景拆分恢复共用操作标识，不能产生重复需求集合。原型反馈与已确认需求冲突时，由 AI 提出需求修订，用户确认新 MD 并推送、登记新哈希；按既有变更/占用/前置门禁重新绑定任务再继续编码，保留代码现场。相关验收包括未推送不确认、正文可由授权客户端从固定 Git 引用读取、业务 API 拒绝上传正文且后端不持久保存正文、旧哈希拒绝、拆分幂等和反向修订闭环。

后端按真实操作者有效 Git 读取授权，从登记仓库的固定 commit SHA 与核验过的相对路径临时读取 MD，在内存中复算实际 SHA-256，并核验实体、分类、来源、场景及前置关系与上报元数据一致；不能接受“正文有前置、元数据却报无前置”。读取失败、权限不足、哈希或字段不一致及结果未知均阻断，不回退信任客户端声明。正文不进入数据库、日志、落盘缓存或错误响应；Git 读取与解析在短数据库事务外完成，事务内重核验占用、revision 及业务条件，见 [临时读取校验决策](../docs/adr/0002-backend-transient-git-validation.md)。真实授权读取与伪造关系等正负用例仍须 G0 验证。
