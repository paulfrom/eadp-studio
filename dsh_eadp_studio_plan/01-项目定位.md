# 1. 产品定位与使用闭环

> 拆分自《eadp项目工作台：产品定位、过程资产与实施方案》；目录导航与原章节编号索引见 [README.md](README.md)。

### 1.1 目标、用户与范围

**eadp项目工作台以项目资产沉淀和复用为主线，帮助非研发人员把业务想法整理为可操作、可确认、可追溯的项目成果。**工作台帮助使用者把业务目标、场景、规则、字段、异常和范围讲清楚，借助 AI 整理材料及生成演示，保留可复用的固定成果，再把确认的版本交给研发理解、评估和实施。

**Agent 交互是本项目成立的基础：五阶段中的过程、资产与文档均通过人与 AI Agent 协作完成。** 使用者在本地与 AI Agent 交互整理业务材料、生成与修订演示，确认结果后才进入协同上报。

**产品最终交付物是一个可安装的 eadp 项目工作台桌面客户端，基于官方 DSH 桌面工程构建，内置并默认启用工作台 Studio：打开即进入五阶段主界面（项目场景 → 需求协同 → 原型展示 → 基线确认 → 交接清单）。用户只安装工作台，不需要先下载 DSH 再安装插件。** 模型经宿主会话配置；协同后端是企业集中部署的固定服务，客户端连接固定服务地址，多作者共享占用与协同状态。主界面结构与新增产品能力基线见 [05-产品形态与主界面.md](05-产品形态与主界面.md)。

项目目标包括：使场景、需求及原型成果按各自确认条件持续沉淀并能够检索、引用和复用；让反馈、修改和确认依据随成果版本保留；使用 AI Agent 降低表达和原型制作门槛，减少非研发与研发之间重复口头转述、信息遗漏和版本误解。原型是资产生产模块，不是场景和需求材料沉淀的前提。

直接使用人基本不是开发人员。以下角色是建议的责任划分，并非已经确定的岗位名单，一人可承担多个职责：

| 角色 | 在工作台中的工作 | 边界 |
| --- | --- | --- |
| 业务、产品或实施人员（成果作者） | 描述场景和规则、回答待确认问题、操作原型、反馈修订、直接确认或选择 AI 辅助评审后自行确认、发起分享与交接 | 不要求掌握源码、Git、包管理器或服务器操作；两条路径均由作者最终确认，不要求另一成员审批 |
| 项目负责人或资产维护者 | 组织成果、责任人、确认状态和交接资料，查看待澄清项及变更影响 | 不作为直接提交或确认版本的强制二次审批人 |
| 研发人员（下游资产消费者） | 读取交接成果、定位版本与依据、提出澄清或可行性反馈；未来设计资产中确认技术约束 | 不是日常原型生产主用户；实际开发、调试、测试、上线及研发仓库和任务管理在工作台外 |
| 工具与部署维护者 | 提供并验证插件、模板、工具链、协同后端/身份接入、GitLab 接入、发布凭证、服务器和访问设置 | 一次提供基础配置并持续维护；不把配置和命令操作转交非研发作者 |

### 1.2 五阶段工作流程与确认上报

工作台主流程切分为**项目场景 → 需求协同 → 原型展示 → 基线确认 → 交接清单**。用户先在工作空间中新建项目，或输入获授权的 Git 地址获取远程项目，再开展五阶段工作。“基线确认”展示原型确认完成后形成的基线，不增加一次人工确认。

每个项目默认设置三个业务文件夹：`场景/<scenario-id>.md`、`需求/<requirement-id>.md`、`原型代码/`。新建场景即创建一份 MD；场景拆分先得到本地候选标题和内容，用户选中某项后才预留正式需求 ID、取得需求设计占用并形成 MD 草稿，不占用全部候选。根目录可以保存项目资产、基线及交接清单文件，系统记录位置按 2.3 规定，不增加第四个业务文件夹。新项目由工具初始化既定结构；通过 Git 地址获取项目时先克隆并校验文件契约、权限及模板，不把任意工程直接视为可运行原型。

每次录入和修改均在本地与 AI 交互，用户可随时向 AI 明确表达“确认”，或点击当前成果的确认按钮；两者调用同一个 Host 确认动作，绑定当前成果及其固定内容，Agent 不能自行确认。内容有歧义、尚未落盘或检查未通过时，先明确对象或修正后再确认。

**阶段确认也同步正文到 Git：Host 固定并推送当前 MD 后，将文件内容的 SHA-256 哈希、固定 Git 引用和必要控制元数据上报业务 API；API 不接受正文上传。后端按操作者既有 Git 读取授权临时读取固定 MD，独立校验哈希与元数据，不保存正文。** 有权限的其他客户端通过固定 Git 引用读取材料，并校验内容哈希。Git 推送成功但后端尚未接受时显示“待同步”，不能视为阶段已确认，也不触发下一阶段。认领、主动取消和管理员释放只传必要协同控制，不上传对话或逐步上报生成过程；占用无自动到期。

| 阶段 | 谁操作、确认 | 本地 AI 交互及成果 | 向协同后端上报的节点 |
| --- | --- | --- | --- |
| 项目场景 | 有项目编辑权限的作者新建场景 MD，与 AI 交互并确认 | 整理业务目标、使用者、触发条件、流程、规则和问题；后端接受场景确认后，默认调用 AI Agent 拆分需求，展示生成的需求标题 | 先推送场景 MD，再上报内容哈希和固定引用；修改已有场景仍须冻结关联需求，场景与需求联动确认一次原子上报，不能只更新场景 |
| 需求协同 | 作者从生成标题中选择一个需求，与 AI 交互并确认 | 整理需求、范围、验收条件及前置需求 ID/所需版本或范围，形成需求 MD；未选择或未确认的拆分结果仍是草稿 | 先推送需求 MD，再上报内容哈希、固定引用、关联场景和前置条件；后端接受后，在占用及前置条件满足时默认调用编码 Agent，未满足则显示等待原因 |
| 原型展示 | 作者围绕当前需求查看源文件、运行预览、与 AI 修订，满意后点击“确认”并明确完成的一个需求 | 后端授予有效占用后才开工；每需求独立 worktree，以认可集成状态和前置完成依据生成前端页面/Mock；交互参考 bolt.new；与需求冲突时先反向完善需求并重新确认 | 本地迭代不逐步上报；原型确认触发保存、检查、推送并自动集成该需求相关代码和文档，形成完整项目快照；不顺带确认其他需求 |
| 基线确认 | 作者查看原型确认形成的基线结果，无需再次确认 | 作者直接确认，或选择 AI 辅助评审后自行确认，两条路径无冲突时均自动合并；成功形成单需求完成依据及固定基线，Host 后台任务按基线自动生成交付清单 | 后端在提交受理和最终完成均校验当前占用人、占用 ID 及输入依据；合并成功且后端接受完成后才形成有效基线、原子更新确认状态并释放占用 |
| 交接清单 | 作者查看自动生成的清单、补充待澄清项并确认交接 | 以固定基线整理需求、流程、规则、异常、验收条件、限制及固定资料；研发在工作台外实施 | 清单正文进入 Git；确认后仅上报交接 ID、内容哈希、固定引用和确认状态；研发收悉仅为接收状态 |

默认调用 Agent 是确认成功后的流程衔接，不替代宿主的模型配置、执行审批或人工业务确认。需求前置未完成时仍可完成需求设计与确认，但编码必须等待前置及有效占用满足。原型中发现与已确认需求冲突时，保留当前代码、预览与对话现场，生成需求修订候选；用户确认新 MD、推送 Git 且后端接受新哈希后，重新绑定输入及前置依据再继续编码和完成确认。不得静默覆盖已确认需求或继续用旧输入完成新范围；涉及场景变更时按场景联动规则处理。

原型菜单提供“部署到远端”：只部署后端认可的项目当前已确认基线对应的固定原型代码版本，到项目配置的唯一远程目标。场景和需求阶段的 MD 提交不形成原型基线。未确认代码只在本地运行预览，不进入远程站点；发布状态与基线确认状态分开显示。

这里“需求开发完成”指工作台内的**原型任务已自动合并且后端接受完成确认**，不代表生产研发代码开发完成。同一需求的修改、认领、原型设计和修订使用同一个独占范围。初次录入场景时尚无关联需求，以独立场景 ID 占用；修改已有场景时，后端在取得场景修改态的同一短事务中检查全部关联需求：任何需求仍被占用或业务任务未结束，均拒绝场景修改，不暂停他人任务，也不先冻结再等待。取得修改态后，全部关联需求禁止另行修改、认领及 AI 开工；其他场景及无关联需求继续并行，不持项目级长锁。

场景修改与需求修改是一次联动过程：已完成需求的 ID、版本、基线及旧场景版本关系保留，差异中的变化或新增范围另生成新需求；未开始需求保留 ID，同步修改内容并产生新版本。作者在本地与 AI 确认联动清单，直接提交无需交叉评审，后端一次接受完整批次后解除冻结。

每个需求可以独立完成并确认基线、进入交接；项目批次基线只是选定已确认需求版本的集合，不要求所有需求到齐，不持有长时间项目级任务锁。需求内容或前置条件修改产生新候选版本，既有确认基线及交接依据保留，旧版本完成不代表新增范围已完成。场景联动中的已完成需求仍适用其旧场景版本，不改历史完成状态；新增或变化范围由新需求跟踪。无依赖需求可并行生产，有依赖需求须等待设计时指定的前置范围完成，不能以任意旧完成记录放行。

用户界面围绕“项目、场景、需求、原型、确认版本、交接、待确认问题和反馈”组织。后端展示各阶段最后确认进度，以及“由谁处理中、当前不能认领”的必要占用状态；本地“正在整理/生成”不作为已完成成果上报。Git worktree、MR、SHA、npm、shell、模板目录及 SSH 是内部实现，由 Host 自动处理；非研发人员无需手工执行 Git 命令、编辑发布配置或排查依赖安装。新成员如何发现项目、获取已确认需求并认领开工，按 2.7.7 的项目目录与认领走查执行。

“确认完成”在已有权限内自动保存、推送并继续合并成果；两条路径为作者直接确认、AI 辅助评审后作者确认，均无需另一项目成员审批或二次合并点击。AI 针对固定候选、需求版本与输入依据给出结果，由作者查看并自行确认及记录必要处置依据；修改后重新检查、更新评审依据并重新确认，不能沿用旧报告。AI 结论不能自行授予确认或业务完成。后端校验身份、当前占用人、占用 ID、输入/前置条件及完成状态，仓库权限或后端占用拒绝均如实展示，不能绕过。AI 报告、完整对话、提示词、中间草稿和工具日志保留在本地；Git/后端仅按既有边界记录最终作者确认方式、固定引用及必要处置依据，不上传评审全文。调用所配置模型供应方仍按既有模型策略执行，“不上传协同后端”不等于模型离线运行。

### 1.3 成果交接、检索复用与成功标准

#### 1.3.1 可追溯研发交接

每次交接选择后端已接受完成的需求及固定资料；待同步或孤立 Git tag/提交不得作为完成依据。原型确认形成有效基线后，Host 后台任务自动生成可交付清单；这里的“后台”不是新增服务端 Agent 或正文存储。清单按 2.3 的系统记录位置进入 Git，包含需求与业务目标、流程、规则、字段、异常、范围/验收条件、所涉需求和原型成果的固定 Git 引用、项目当前演示链接、已知限制、待澄清问题、来源及变更说明。清单明确演示链接会随项目当前成果更新，不对应历史页面快照；后续资料修订另形成新版本，不覆盖旧交接依据。

实现复用既有 Git 源文件和项目资产清单：Host 读取获授权仓库内指定提交的清单与材料，插件 client 提供可阅读的交接视图和材料定位入口。接收方使用该视图需安装完整 eadp 工作台客户端并具有 GitLab 材料权限；不安装时通过既有 GitLab 查看获授权固定版本的可读源材料与清单，当前不提供独立网页交接视图。此处是下游查阅，不把研发开发纳入工作台；不另建交接网站或发布平台；新增协同后端只保存交接确认状态和版本引用，不托管交接内容。接收方使用工作台时按协同会话及绑定 GitLab 成员权限读取材料；直接访问 GitLab 时仍使用其 GitLab 身份与仓库权限，原型演示访问按项目已配置的公开或受限访问策略执行，二者分别核验；无仓库权限时提示所需授权与维护者处理入口，不把共享演示链接当作资料读取授权，不建立独立交接身份平台。直接提交的成果可以交接，无需研发再审批后才定版。

原型使用单一稳定演示 URL，始终展示项目当前已完成、合并确认并成功发布的集成成果。交接清单保留固定 Git 资料和所涉需求完成依据，链接明确标为“项目当前演示”，不充作历史交接快照。交接视图展示当前演示标识及其与交接资料的关系；失效、更新中或状态未知时如实提示。Git 历史仅用于资料追溯，不提供历史站点恢复或本地历史预览切换。本地仅预览本人当前需求 worktree 的工作成果，不随他人远程更新自动改变。原始需求、规则和交接材料不随原型构建上传到演示站点或未经授权公开。

研发反馈按交接版本关联为澄清或可行性意见，由作者更新材料并形成新版本。记录“已收到”或“已确认收悉”仅表示接收状态，不等于研发接受排期、开发完成、技术验收或生产交付；不得把接收动作增加为直接提交的二次审批。

#### 1.3.2 检索与复用

场景和需求材料在必需检查通过、固定正文推送 Git 且后端接受阶段确认后即可独立沉淀，同时自动取得复用资格，不必等待原型完成，不新增资格按钮或二次审批；原型代码仍须集成成功、后端接受完成并形成固定原型基线。确认与当前可复用资格分别记录，但确认受理同时授予资格；资格由后端状态与 Git 固定材料共同核验，不因本地显示或存在 Git 提交就判定可复用。重复确认事件重放不得恢复后续已停用的资格。

材料确认前，核心业务规则与验收条件必须明确；缺失时保留草稿，不确认也不授予复用资格。其他待澄清事项可以随材料保留，但必须展示其限制与不适用范围，不能由 AI 编造补齐。此检查属于原有确认检查，不增加二次审批。正式确认材料、Git 可达固定引用、固定版本与来源记录，以及后端关联元数据、受理事件和来源证据长期保留，停用不删除。临时构建、缓存与任务现场单独清理，清理前保护未提交、未推送成果及在途任务唯一现场，不建设额外备份平台。

首期在项目资产清单按场景、业务分类、类型、标题、关键词、明确状态和版本检索；在可阅读成果视图查看来源、反馈、限制、版本及可复用资格和原因。首期复用单元为完整场景包或完整需求包，由作者显式选择固定版本，工具取出该包及必要来源关系，按新任务调整并记录来源、采用范围和修改，不要求用户手工复制源码；不做规则、字段或代码片段级提取复用。浏览或选中不算采用，以后端是否接受采用记录为界：停用生效时尚未接受的采用阻止，已接受的采用保留固定来源继续；采用受理不能绕过来源 Git 材料读取授权。采用受理不算复用成功，目标须经过自身检查、确认并由后端接受后，记录目标最终固定版本及来源，失败或取消不计成功，不能继承来源的确认或完成状态。当前不建设语义搜索、全企业资产库或跨项目自动同步。

新增场景和需求时从已有项目业务分类中选择并明确记录状态；业务分类按业务领域组织，不等同于资产类型，材料确认、原型完成与可复用资格也不合并为一个状态。所有具有项目编辑权限的成员均可维护项目分类词表；编辑既有分类保留固定材料的历史分类及 ID，不自动改写历史正文，实际词表值与实现编码在 G0 提供并验证，不扩为企业分类库。新草稿不可复用，编辑新草稿不暂停旧固定版本已有的复用资格。显式停用须由后端接受后才生效，生效后阻止新的采用；受理前不能显示已生效，历史固定版本及已复制且独立维护的目标保留来源，不自动撤销。所有具有该资产编辑权限的成员均可停用或恢复，后端以既有可信身份及该资产编辑权限受理并记录操作者、原因和时间，不把 Git 凭据等同于授权；恢复不重做确认或基线。

#### 1.3.3 阶段范围与验收

| 层次 | 产品范围 | 本期落实程度 |
| --- | --- | --- |

| 原型模块 | 指定模板自动初始化、页面/Mock 生成、操作反馈、预览、检查、分享 | 首期唯一生产模块；模板工程仅用于演示，不是研发业务开发工程 |
| 主界面（2026-10-13 产品决策） | 打开即五阶段 Studio（全局 `main` 面板满窗），标题栏提供本地/远程原型入口（见 [05-产品形态与主界面.md](05-产品形态与主界面.md)） | 形态可行性由 G0 验证；场景矩阵相关概念尚未设计，不列入本期范围 |
| 概要设计候选模块 | AI 辅助整理系统边界、模块职责、方案和接口概览及业务依据 | 当前只预留类型和版本关系；技术约束与方案可靠性需研发确认 |
| 详细设计候选模块 | AI 辅助整理接口、结构、处理流程和规则及设计依据 | 后续单独确认范围和验证，不承诺非研发人员独立完成可靠技术设计 |

当前推荐一个项目对应一个过程资产仓库，保存过程材料、清单和原型源码；它不是生产代码仓库，研发在工作台外维护自己的开发成果。采用成熟 docs-as-code 的内部版本管理模式，面向用户展示业务成果，源文件进入 Git、确认版本固定到不可变提交、复用固定来源。候选设计模块不经过原型模板复制与 Mock 生成，也不预先建设通用资产平台。本方案中所有 Mock 一律指生成原型页面内的合成数据与交互模拟；工作台项目本身（专用插件、协同后端、原型模块工具链与发布流程）按生产可用标准设计与执行，不是 Mock 工程。

试点选择 1–2 个真实原型需求及非研发作者，验证五阶段确认上报、两种提交路径、一次反馈修订、一次固定版本交接及一次完整场景包或需求包的检索复用；另验证已确认场景/需求在原型未完成时独立沉淀、分类与状态一致、资格原因可读及客户端不能绕过后端资格。以至少两位作者/两台客户端验证同需求互斥和不同需求并行。G0 必须观察非研发人员完成完整路径，确认无需开发知识和命令操作，并记录遇到的理解和操作难点。必需业务交互包括查询/筛选、表单校验、模拟提交、状态切换、空态及错误态；页面持续显示“交互原型 · 合成数据”。

成功要求：业务目标到成果与反馈可追溯；作者能够提交和确认版本；研发能快速定位版本、规则、异常、验收条件及待澄清项；复用具有来源和调整记录。统计非研发独立完成率、维护者介入次数、理解和操作难点、澄清轮次、交接信息缺口与定位耗时，先测量现有沟通方式和试点基线，再确认目标。无基线不宣称沟通减少了某个百分比，不用编译成功替代需求完成或成果沉淀。工作台不能承诺零沟通，也不以原型取代研发的技术判断。

截图/PRD 文件输入、元素点选定位均保留为候选能力，需分别验证上传/模型能力及业务组件映射。实时共同编辑、跨设备完整会话同步、任意框架导入、任意依赖安装、GitLab 开户或账号同步、企业统一身份平台，以及研发开发/调试/测试/上线和研发任务管理均不纳入范围。

### 1.4 内部工程路线与成立条件

产品采用官方 DSH Electron 桌面工程 + 内置单一专用插件，作为 eadp 项目工作台的完整定制发行，不自行开发桌面壳。用户通过单一安装包获得宿主、已启用的 Studio、指定模板和必要工具链，安装后直接使用，插件包仅为内部构建件；宿主、插件与运行时作为同一产品版本升级。满窗形态和完整安装包可行性由 G0-1 验证，承载确认无法满足时按本章末尾止损条款处理。指定模板及其 `AGENT.md` 规范原型生成与修改，不规范实际研发业务项目开发。当前工作台只登录协同后端，由后端独立协同用户绑定既有 GitLab 数字用户 ID；GitLab 管理 API 与成员权限门禁由后端提供，桌面 clone/push 使用本机用户 Git 凭据。维护者提供基础配置，不创建 GitLab 账号或账号同步平台，具体决策见 [协同登录与建仓 ADR](../docs/adr/0003-studio-auth-and-project-provisioning.md)。GitHub 仍属后续候选接入，不提前实现兼容层或自动切换。

**方向有条件可行，尚未验证实现可行性。** 以下事项必须通过 G0：
