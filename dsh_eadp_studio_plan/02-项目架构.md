> 拆分自《eadp项目工作台：产品定位、过程资产与实施方案》；目录导航与原章节编号索引见 [README.md](README.md)。

### 2.1 总体架构与代码边界

架构按“工作台核心 + 资产生产模块”分责。本地核心管理业务材料、需求和待确认问题、资产源文件、关系、提交确认、交接与基线；协同后端管理项目进度、实体标识、确认状态和跨机器独占处理权；原型模块消费这些上下文，负责原型工程生产与静态演示。当前资产生产模块仅建设原型，同时建设最小协同后端；未来设计模块复用公共资产契约，并自行验证其内容、检查与展示方式，不经过原型模板复制与 Mock 生成。协同后端由企业集中部署为固定服务，客户端连接固定服务地址，不在用户侧部署。

```text
eadp 工作台桌面安装包（内含固定官方 DSH Electron 桌面端）
├─ 官方会话、模型调用、事件、审批与取消
├─ 专用插件 client（满窗 Studio 主界面）：项目新建/Git 地址打开 / 五阶段导航 / 官方 Agent 交互 / MD 与源码 / 运行预览 / 确认与部署
├─ 专用插件 Host 核心：资产清单与检查 / 业务材料视图 / 任务绑定 / Git与提交确认 / 交接基线与复用记录
├─ 协同客户端 Host ── 既有可信认证 ── 工作台协同后端 API
│                                      └─ 持久化：确认进度 / 前置条件 / 占用及代次 / 场景冻结 / 认可集成头与提交操作
├─ 原型模块 Host：随包模板 / 受控生成 / 模板检查预览 / 专用静态发布
└─ 官方受限 webview ── loopback ── 插件拥有的模板预览进程
                                      │
本地 workspace：过程资产仓库（业务材料与清单 / 需求反馈 / 原型源文件 / 确认版本与交接复用记录）
                + 每需求独立 worktree（前置基础 + 本人当前改动）/ 未提交成果 / 本地任务关联记录
├─ Git CLI / 代码托管集成 ── 当前 GitLab：资产源文件 / 清单 / 版本 / 需求分支 / 自动集成 / 可选 MR
│                             └─ 后续 GitHub 接入（计划，未实现）
└─ Host 发布操作：核验项目当前已确认基线及固定 SHA ── 干净快照 ── 模板检查 / 构建 / 静态冒烟
                                                    │ SHA / 构建 / 产物校验值
                                                    │ SSH/SFTP（发布凭证仅供专用操作取用）
已配置远程服务器：互斥锁 / 当前部署记录 ── 临时上传校验 ── 单一当前站点原子替换
                                                    │ 既有静态 Web 服务（如 Nginx）
项目演示链接（HTTP 或 HTTPS；内网或公网，由服务器或既有入口落实项目访问策略）
```

这是**插件、协同后端与原型资产三个职责边界**，均不承担下游业务生产开发：协同后端独立提供进度与占用 API；专用插件按 DSH 的 Host/client 扩展约定开发；原型生成工程是项目仓库中受管理的资产源文件，按指定模板规定的运行时、检查与构建命令执行。项目清单、需求和确认记录不作为原型构建代码执行。
插件项目内包含指定模板工程目录及其 `AGENT.md`；生成工程从随包模板复制，后续 Agent 任务按已验证入口加载项目规则。
插件 client 不保存凭证，不直接执行 Git/shell，也不把生成工程作为高权限客户端模块装入宿主。
主界面形态（2026-10-13 产品决策）：**打开即进入工作台 Studio——插件全局 `main` 面板满窗承载五阶段导航，是产品的主界面而非附属面板**；标题栏为原型入口，按本地服务启动状态与远程服务部署状态判定：本地服务运行中显示「本地原型」，本地未运行但远程服务已部署显示「远程原型」，均无则显示「未运行」，点击直接跳转浏览器查看；不展示技术地址，本地预览仍仅监听 loopback。满窗形态可行性由 G0-1 验证，承载确认无法满足时按 1.4 止损条款重新作架构决策；会话右侧 tab 是否使用及承载内容，开发中按实际需要确认，不预先规定。主界面结构见 [05-产品形态与主界面.md](05-产品形态与主界面.md)。
复用官方交互会话与执行管线，不另写 Agent loop、会话 RPC、桌面启动器或通用进程守护器。
官方 [headless](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/headless/README.md) 与 [SDK 协议](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/protocol/README.md) 当前所述能力不足以直接承载独立远端 AI 交互服务；本路线所需的追加需求、审批与取消直接在官方宿主验证。新增协同后端仅承担进度和处理权 API，不依赖 headless/SDK 承载对话。

#### 2.1.1 工作空间、项目入口与三目录契约

用户先在工作空间中选择“新建项目”或输入获授权的 Git 地址打开远程项目。Host 负责新项目的仓库初始化，或将远程项目 clone 到受管理工作空间，核验项目身份、仓库权限和清单。工作台只登录协同后端；Git 地址只用于打开后端已登记、已 ready 且本人有权限的 GitLab 项目，不替代协同身份或成员授权。新建项目由后端先建空仓库、Host 本机初始化并推送、后端复核后置 ready；未 ready 不开放业务操作。既有仓库须符合本契约，不自动转换任意工程，不建立旧目录兼容层。

每个项目固定三个业务目录，目录对应业务内容，菜单对应操作阶段：

```text
项目根目录/
├─ 场景/
│  └─ <scenario-id>.md          # 新建一个场景即新建一个 MD
├─ 需求/
│  └─ <requirement-id>.md       # 选中需求后整理，确认时固定内容
├─ 原型代码/                    # 随包指定前端模板的完整工程
└─ 项目清单、基线与交接清单文件  # 根目录文件，不是第四个业务目录
```

业务标题保存在 MD 与清单内，不以标题充当稳定 ID。模板完整复制到 `原型代码/`，以该目录为安装、检查、运行与构建根；`AGENT.md` 保留在其根目录。确认、来源与反馈随相关 MD 或根目录清单保存，清单字段在 G0 固定。本地会话、占用绑定、候选草稿和执行日志属于插件任务现场，不混入交付源码或静态产物。每需求 worktree 保持同样目录结构。

### 2.2 模块职责与最小接口

| 模块 | 负责的输入/输出 | 不承担的职责 |
| --- | --- | --- |
| 项目资产核心（Host） | 项目、场景、业务材料与问题、资产清单与版本关系、检查和确认引用 → 可阅读成果与交接视图、资产索引、基线、检索与显式复用记录 | 不执行所有类型的构建、不从会话自动判定沉淀、不复制后端状态权威，不创建通用扩展框架 |
| 模板与生成工具 | 随包指定模板目录、`AGENT.md`、需求清单 → 自动初始化原型工程、页面、模板约定的路由、合成 Mock、补丁 | 不另选技术栈或调用通用脚手架，不修改规则/依赖/构建/安全配置，不实现任意框架适配器或通用 AST 改写平台 |
| 任务协调器（Host） | 原子取得后端占用、绑定项目/需求/任务/固定输入与官方会话；阶段确认成功后默认拆需求或启动编码，处理反向需求修订 → 本地状态、候选标题、检查结果和失败现场；按已验证入口加载工程 `AGENT.md` | 不把模型输出当用户确认，不假设所有资产均为模板工程，不复制官方会话历史或独立调度模型对话循环 |
| 工作台协同后端 | 可信身份、项目授权、固定版本及前置条件 → 进度、幂等事件、持久化占用、管理员释放、提交受理及完成、认可集成头与最小操作状态 | 不接收完整 AI 对话、提示词、中间草稿或工具日志，不运行远端 Agent 或建设通用工作流/集成平台 |
| Git/workspace 与代码托管集成 | 仓库、认可集成头、需求及任务 ID → 每需求独立 worktree/分支、任务提交、精确集成候选、条件合并和作者直接确认/AI 辅助评审后作者确认证据 | 不覆盖人工修改，不继承未经后端认可的集成结果，不承担发布授权、构建或部署 |
| 预览操作 | 任务 worktree 与模板启动/ready 契约 → 进程、端口、ready 状态 | 不在窗口最小化时终止任务，不管理与本插件无关的进程 |
| 专用发布操作（Host） | 项目当前已确认 baseline ID、固定代码 SHA、模板、目标设置 → 干净构建、单站点原子替换、当前产物/访问验证及链接状态 | 不使用未完成任务产物或仅阶段确认的文档提交，不提供历史站点切换/恢复，不把敏感发布交普通 Agent，不建设部署平台 |
| 插件 client | Host 状态与用户操作 → 满窗 Studio 主界面（五阶段导航）、业务材料、版本差异、待确认问题、进度和错误、标题栏原型入口；维护者可查看技术诊断 | 不直接访问代码/服务器凭证，不决定发布是否成功 |

用户逻辑操作至少覆盖：创建/打开项目、描述确认场景、设计确认需求及前置条件、认领原型任务、查看进度/占用/前置阻断、待确认问题、固定资料和关系、开始生成、反馈修订、查看检查摘要、直接确认完成或主动选择 AI 辅助评审后自行确认、查看交接及显式复用、通过标题栏原型入口查看本地/远程原型；Git 保存推送、自动合并及基线标记由后台完成。后端管理员有明确的手动释放占用入口，普通作者不获得该权限。原型模块提供本人当前预览、更新项目当前演示、查询部署状态和撤回访问；原型展示的体验基准为 bolt.new 式「AI 创建项目 → 浏览器即时演示」（1.5）。
工具注册名称、参数结构、事件订阅和状态持久化位置以目标 DSH 版本的真实接口为准，在 G0 输出契约，不先虚构 API。
最小本地任务记录包含：project ID、scenario/requirement ID、asset ID/type、task kind、输入版本与后端 base revision、前置需求 ID/所需版本及已完成依据、task ID、client instance ID、occupation ID/代次及 owner、官方 session ID、仓库/worktree/branch、认可的 base SHA、当前提交、检查点/结果、提交路径、确认身份与时间。集成操作只记录 operation ID、占用 ID、任务源 SHA、预期认可集成头、候选 SHA、检查及 Git/后端受理结果，用于条件更新和断网核对。原型任务另记录模板/`AGENT.md` 版本校验值及加载、当前预览结果；发布记录关联目标、当前已确认 baseline ID、固定代码 SHA、构建/产物标识及授权验证结果。session、task、集成和发布 ID 均不能代替资产身份或内容版本。
每次变更前保存受影响文件的基线与已有未提交补丁，变更后记录本任务差异；检查点使用宿主已验证能力或插件最小持久化记录，不另建会话系统。
同一 worktree 同时只有一个本地写入任务；跨作者/机器同需求排他必须依靠后端处理权，本地锁与 Git 分支均不能替代。任务取消、窗口关闭、宿主重启时须能区分已完成、执行中、未知与失败，不能假报成功。

#### 2.2.1 最小代码托管边界

核心以 Git 仓库标识关联工程，包含 provider、无凭证 remote URL 与提供方仓库标识等最小必要数据；clone、worktree、分支、提交、fetch/push 与 SHA 校验复用本地 Git CLI。
当前 GitLab 的 group/project ID、建仓、成员分配及实际成员权限检查由后端管理 API 边界封装，不渗入生成、预览或发布。后端只在绑定 GitLab 用户实际有权的群组/仓库范围操作，不能采用管理 token 的权限作为用户权限。桌面 clone/push 仍由本机 Git CLI 和用户凭据执行，协同会话不作为 Git 密码，管理 token 不发送桌面。GitLab 服务端最终核验 Git/分支操作，后端独立核验协同任务与管理员权限，发布权限仍单独授权。
后续 GitHub 的组织/仓库/PR 接入仅在该边界增加并独立验收，目前不实现其适配器、不提供跨平台自动切换，也不扩展为通用代码托管平台。

#### 2.2.2 五阶段 Agent 交互与确认驱动

Studio 在场景、需求与原型菜单提供当前实体绑定的官方 Agent 交互入口。场景/需求显示 MD 内容和待确认问题；原型展示参考 bolt.new 的“对话修改、源文件查看、运行与预览”模式，用户无需切回技术会话自行拼装上下文。编码 Agent 是使用原型规则和受控工具的官方会话任务角色，不增加第二套模型接入或独立运行循环。宿主组件如何承载由 G0-1 验证。

| 阶段/动作 | 固定上下文与 Agent 产出 | 确认及后续动作 |
| --- | --- | --- |
| 新建场景、场景交互 | 当前场景 MD、项目业务背景、既有问题；Agent 整理目标、流程、规则、异常和待确认项 | 用户明确说“确认”或点击确认，Host 固定并推送当前 MD，后端接受哈希确认后才显示场景已确认 |
| 场景确认后拆分 | 读取被接受的场景 MD 固定版本；Agent 输出候选需求标题、范围、场景来源和前置建议 | 默认启动一次拆分，展示生成的标题供选择；拆分不等于需求确认，不自动把全部候选送去编码 |
| 选中需求、需求交互 | 选中候选或已有需求、固定场景依据；Agent 整理需求 MD、验收条件、字段和前置条件 | 选中候选后幂等建立正式需求 ID 并领取设计占用；用户确认 MD，推送 Git 并上报哈希；后端接受后默认尝试领取生产占用并调用编码 Agent |
| 原型生成与反馈修改 | 已确认需求 MD/hash、场景引用、前置完成依据、当前 worktree 和模板规则；Agent 修改前端源码及 Mock | 运行并预览、查看源文件、继续对话修改；输入冲突走反向修订，预览成功不算需求完成 |
| 原型确认、基线结果 | 用户明确的目标需求、新鲜检查结果、最终代码与已确认 MD；整理完成依据 | 确认后自动提交相关代码文档、集成并上报完成，成功才形成基线；基线确认页展示结果与异常，无第二次确认按钮要求 |
| 交接清单 | 已被后端接受的固定基线、需求/场景 MD、检查及限制；后台任务生成交付清单 | Host 后台任务自动整理清单，可复用官方 Agent；用户查看和补充后按既有交接确认规则上报，清单失败可重试，不重复完成需求 |

“默认启动”由 Host 消费已接受的确认事件驱动；按确认事件 ID、阶段和输入 hash 绑定唯一后续任务，响应丢失先查询结果，失败显式重试，不重复创建候选或会话任务。拆分列表先保存在本地任务现场，使用稳定候选标识；未选项不领取全部需求占用，也不显示为已确认需求。选中后的正式 ID 与来源绑定持久保存，重试不得重复建需求。已有场景修改按 2.7.5 的联动清单处理，不无条件再次创建同名需求。

需求确认与原型生产认领是不同的原子操作。自动编码仍需满足项目权限、当前占用、场景冻结和全部指定前置完成条件；失败显示“需求已确认，等待开工条件”，不撤销需求确认，也不绕过门禁。场景拆分开始前同样核验其固定输入仍适用及场景未被新修改冻结；结果过期时保留草稿并要求重新核对。交接“后台生成”指桌面 Host 的后台任务，协同后端不运行 Agent、不保存正文；客户端关闭后恢复任务需先核对事件，不承诺离线服务端自动生成。

#### 2.2.3 MD 哈希确认与反向修订

按钮确认和用户对 AI 明确表达的确认意图调用同一 Host 确认入口。Host 从可信用户操作确定 project/entity、当前 MD 版本和操作范围；自然语言目标不明时澄清，Agent 生成的“已确认”、文档引用或工具输出不得代替用户确认。MD 内容由 Host 保存为 UTF-8，对实际文件字节计算 SHA-256，记录算法及文件相对路径；不能由模型编造 hash，也不能用 Git commit SHA 代替文件内容 hash。

确认时暂停该文件的并发写入并固定快照，校验所需字段、分类、来源、前置关系及权限；核心业务规则和验收条件必须明确，缺失或尚未明确时保持草稿并阻断确认及自动复用资格授予，不能用 AI 推断代填。其余待澄清项可以保留，但须展示限制及不适用范围。满足条件后将该快照按受控入口提交到 Git；从最终固定提交的对应文件重新计算 hash，与用户确认快照一致才上报。合并导致 MD 字节变化时须重新展示并确认，不能把旧确认套在新内容上。业务 API 接收实体 ID、内容 hash、固定 Git SHA/路径、expected revision、当前占用、必要分类控制元数据及幂等键，不接受 MD 正文上传或 AI 过程；后端按操作者 Git 授权临时读取固定 MD，在内存中独立核验哈希与元数据，不保存正文。内容确认及复用资格按 2.3.3 受理并关联该固定版本。Git 或后端拒绝、响应未知均不能显示确认成功、复用资格已生效或触发后续 Agent。确认后编辑产生新的候选内容，旧 hash 的确认只适用于旧版本。

原型反馈若仅调整实现且不改变已确认需求，编码 Agent 可在当前任务继续修改；若与业务规则、字段、范围或验收条件冲突，须展示代码反馈与需求差异并提出需求修订，不静默让需求迁就生成代码。用户接受修订方向后，按 2.7.2 保存工作现场、结束旧生产占用、取得设计占用，更新 `需求/<requirement-id>.md`；用户确认新 MD、Git 推送及后端接受新 hash 后，重新核验并领取生产占用，绑定新输入并复核保留的代码补丁，再继续编码与预览。发生占用竞争时保留现场并等待，不复用旧占用 ID。涉及场景变化时先走场景联动；已完成基线的修改按既有新版本/派生需求规则处理，不覆盖历史完成依据。

### 2.3 项目资产领域模型与沉淀规则

下表是待 G0 验证的最小领域契约。内容源文件、分类及来源证据留在 Git；必要分类控制元数据、内容确认状态、生产任务状态、复用资格与受理事件由协同后端持久化并关联固定内容版本。Host 校验同一快照在 Git 与后端引用中的一致性。本地执行现场另存，不复制到后端，不预防性建设通用资产数据库。

| 交接记录 | 固定需求/资产完成依据及业务目标、流程、规则、字段、异常、范围/验收条件、项目当前演示链接、限制/待澄清、来源/变更、接收/反馈 | Git 资料按既有权限读取且固定；当前演示不是历史快照，收悉不等于开发完成 |
| 复用记录 | 目标资产/任务、来源资产固定版本及确认依据、原型代码的来源完成基线、采用范围、幂等采用记录及后端受理依据、调整说明及检查结果、目标确认后的固定版本与确认依据 | 首期以完整场景包或需求包为复用单元；浏览或选中不算采用，后端接受采用记录也不等于复用成功。目标完成必要检查和确认并被后端接受后，绑定固定两端及目标确认依据才计为复用成功 |

清单提交引用已有资产源文件 SHA 与 MD 内容 hash，基线标记再指向该清单提交，避免清单填写包含自身的提交 SHA。源文件位置按 2.1.1 固定在 `场景/`、`需求/`、`原型代码/`，确认、基线与交接证据使用相关 MD 或根目录清单文件，不另设第四个业务目录；G0 验证清单字段与模板目录契约，不重新选择业务目录。
资产内容版本、内容确认状态、生产任务状态、复用资格、作者确认方式、项目基线和原型发布状态分开记录。场景/需求材料通过公共检查、推送 Git 并被后端接受确认后独立沉淀，后端在同一次受理内记录确认事实并自动授予该固定版本复用资格，无需等待原型生产完成。确认事实保留，后续复用资格可被显式停用或恢复；作为可采用来源时仍须核验后端当前有效资格，不能仅查询旧确认记录重新赋权。原型代码复用另以完成基线为依据。生产任务未完成不能被解释为材料未确认，材料已确认也不能被解释为原型已完成。成功发布或 AI 评审结论不能替代作者确认；直接确认与 AI 辅助评审后作者确认分别留证，不显示为他人审批通过，撤回演示链接不删除资产基线。
上游资产更新时，在当前工作版本/新候选清单中，对引用该上游旧版本的关系展示“待复核”及影响范围；作者可有依据地保留旧固定引用，或选择升级后重新检查并按所选提交路径确认，记录处置结果。待复核用于展示影响，不强制升级；复制后的来源溯源关系不作为必须升级的实时依赖，目标独立维护，已建立基线中的内容与关系保持不变。开始修改不撤销旧固定版本原有的有效复用资格，新草稿不可复用；显式停用经后端接受后阻止被选定固定来源尚未受理的采用，已受理采用按 2.3.3 保留来源继续，不删除历史正文，也不自动撤销已复制并独立维护目标的来源关系。场景联动修改按 2.7.5 处理：已完成需求保留旧场景依据及完成状态，不标记为必须重做，新范围另建需求；未开始需求同批次更新，不留下新场景与旧需求混用的候选关系。不得自动覆盖下游源文件或使旧基线指向新版本。本期用清单关系检查和展示实现，不自建推理或跨格式同步引擎。

#### 2.3.1 生产、校验、提交确认、基线、沉淀与复用

1. **生产**：场景/需求设计先领取实体占用；按 2.2.2 从场景 MD 确认驱动需求拆分，再由选中需求 MD 确认驱动编码。前置未完成不阻止需求设计；原型生产另按 2.7 原子校验所有前置完成及场景门禁，取得需求占用后，在独立 worktree 中基于认可集成状态生产本人当前成果。保留来源、差异和责任人，会话仅提供执行上下文。
2. **校验**：Host 公共检查核验 ID、路径、分类、版本引用、关系、必要记录及来源依据；作者基于真实业务依据确认本次材料范围内的核心业务规则和验收条件，字段存在或模型自报不能证明业务已明确。场景按本次场景确认范围具备核心规则与验收判据即可，不要求穷尽下游所有需求细节。缺少核心依据保持草稿，不接受确认、不自动授予复用资格。非阻断待澄清项须随固定材料明确展示限制及不适用范围，不能隐藏或冒充已解决。AI 只整理已有依据与提出问题，不能推断代填核心规则并冒充作者确认；作者按既有权限确认，不增加额外审批。原型模块另执行模板工程、Mock、浏览器及安全检查。失败或结果未知不进入基线。
3. **提交成果与确认**：作者在原型展示中明确当前需求，或选择一个需求点击“确认完成”，直接确认或主动选择 AI 辅助评审后自行确认。AI 基于固定候选、需求版本及输入依据提供结果；作者对完成条件、检查和来源作最终确认并记录必要处置依据，不设另一成员审批，AI 不自授确认。候选或输入改变后须重新检查、更新评审依据并重新确认，不能套用旧报告。Host 提交本需求相关代码与文档，基于已有认可成果形成完整项目快照；“整个代码和文档”不等于暂存所有 worktree 的未完成修改，也不把其他需求顺带标为完成。条件满足后自动执行 2.7 的提交受理、任务分支推送、精确集成候选检查及稳定分支条件更新；正常流程不增加人工合并按钮。冲突、检查或权限失败显示待处理，不能当作完成。
4. **确认版本（内部基线）**：单需求完成流程自动整理通过检查的集成成果及其固定清单、确认依据和不可移动基线标记；后端再次核验当前占用人/占用 ID、输入及前置条件，接受合并完成与基线引用后才结束任务和释放占用。作者无需再发起一次审批或手动合并；项目批次基线另只读聚合已完成固定版本。实际仓库/分支/标签权限在 G0 验证，拒绝时如实报告，不绕过。
5. **交接与沉淀**：来源明确、分类及状态已记录、已推送、公共检查通过且内容确认已被后端接受的场景/需求材料独立进入沉淀资产清单，不要求原型完成基线；作为可采用来源时另核验后端有效复用资格。原型代码及其完整成果交接另需自动合并成功、完成/基线引用被后端接受。后端接受原型基线后，Host 后台任务按该基线自动整理可交付清单，读取固定场景/需求 MD、代码引用、检查结果、已知限制及待澄清项；材料缺失需显式标出，不用 AI 推断冒充确认依据。清单按 baseline ID 幂等生成，待生成/失败/可查看与需求完成状态分开；失败只重试清单任务，不回滚完成或再次提交需求。清单正文经独立受控文档提交保存到 Git，引用已有基线，不改写该基线；后端仍只存引用与状态。用户可在交接清单页查看、修订和确认，按 1.3.1 读取固定资料，当前演示链接仅表示项目当前站点，研发接收不作为二次审批。直接路径同样可沉淀。会话全文、来源不明材料、未确认任务提交和临时构建产物不自动成为项目资产。
6. **复用**：在项目清单按场景、分类、类型、标题、关键词、内容确认状态、复用资格和固定版本检索，以完整场景包或需求包为首期复用单元。每次显式采用先核验固定来源、来源读取及目标编辑权限、后端有效复用资格，并由后端幂等接受采用记录后再引用或复制到目标任务；浏览选中、之前的检索结果或本地缓存均不能替代受理。采用与停用的竞争按 2.3.3 决定，已经接受的采用保留固定来源继续完成，仍须通过 Git 实际读取授权。包包含固定 MD、业务目标、已明确的核心业务规则与验收条件、分类、来源、关系及确认依据；可以附带非阻断待澄清项，但必须展示限制及不适用范围，目标采用前可读取这些内容。采用原型代码时另核验其完成基线。工具记录采用受理依据、来源与调整，目标重新校验并由作者直接确认或经 AI 辅助评审后自行确认，确认被后端接受后绑定目标固定版本及确认依据；采用受理不等于复用成功，不建立规则、字段或组件级独立复用资产。跨项目复制保留获授权的固定来源，目标按自身需求独立维护；当前不承诺跨项目自动同步或全企业资产库。

场景/需求材料及其来源、反馈、确认依据可独立沉淀；原型工程源文件及其需求/反馈/确认依据在完成基线后沉淀。官方会话、worktree、进程日志和任务记录是执行现场；演示链接、构建产物和发布记录是演示交付与验证记录。后两者可关联到资产版本，不能单独证明资产已沉淀或可复用。

#### 2.3.2 后续设计资产扩展契约与准入

未来概要设计、详细设计是 AI 辅助生产的过程材料，需研发确认技术约束与方案适用性，不承诺非研发人员独立产出可靠技术设计。研发具体开发、调试、测试、上线及生产代码仓库管理仍在工作台外。概要设计、详细设计未来均采用 project ID、asset ID/type、源文件、版本、输入关系、责任人、检查、提交确认、基线与复用这一最小契约；概要设计可依据需求/原型版本，详细设计可依据概要设计版本。每次引用固定版本，原型不能自动转换为已通过评审的设计文档。
新增类型先由负责人确认成熟工具与源格式、产出范围、业务作者与研发技术判断职责、提交确认规则、检查入口、展示和信息边界，再以最小样例证明 Git 差异评审、版本关系追溯、固定基线资料读取及复用可验证。无需执行的文档类型不要求 Node、Mock、静态构建或原型发布。
扩展按“范围确认 → 工具/源格式 POC → 单类型试点 → 独立准入”实施：至少完成需求/上游设计到产出、反馈修订、校验与提交确认、基线和复用闭环；两种提交路径按该类型单独确认规则，不默认强制交叉评审，并验证上游变化待复核、权限拒绝和敏感内容边界后才算支持。扩展 WBS、验收阈值与日期单独确定，不计入本期交付，也不提前实现设计工具或通用模块装载协议。

#### 2.3.3 分类、状态与复用资格的受理契约

**分类方向与维护权限。** 场景和需求按项目内统一业务领域分类，例如采购、库存、财务；这些是示例，不预设内置词表。新增场景或需求选择已有统一业务分类。所有具有项目编辑权限的成员均可维护该项目分类词表，不限制为负责人或维护者；后端按既有可信身份核验项目编辑授权，分类控制元数据和维护事件关联项目及对应固定材料证据。单个资产的停用/恢复权限不能推导整个项目的分类管理权限。业务分类不能与材料类型、确认状态、任务状态或复用资格混用；不设计层级分类或通用配置平台。

**已确认原则。** 新增场景或需求时显式记录业务分类、内容确认状态及生产任务状态；分类关联对应内容版本，不由标题、目录或会话推断。内容确认回答该固定材料是否已被作者确认并被后端接受；生产任务状态回答对应任务的生产进展；复用资格回答该固定材料当前能否作为新任务的采用来源，三者分别记录和展示。场景/需求材料通过检查、推送 Git 并被后端接受确认后独立沉淀，后端在同一次受理内记录内容确认与该固定版本自动取得复用资格，不依赖原型完成，不增加额外审批。内容确认事实与后续可变复用资格分别保留；已停用版本不能仅因读取或重放旧确认事件而重新获得资格。原型代码复用另须完成基线。

**确认内容门禁。** 本次材料确认范围内的核心业务规则和验收条件必须明确，并具有可核验的真实业务来源，才可按既定权限发起材料确认。本次可信用户确认动作提供作者确认依据，后端接受时生成对应固定版本的确认记录并自动授予复用资格，不要求首次确认前已有批准或确认记录。Host 核验结构、来源及固定版本一致性，业务是否明确由作者基于真实业务依据确认，不能仅凭字段存在、模型自报或 AI 生成的完整表述判断。场景只须明确其本次确认范围内的核心规则与验收判据，不要求首次场景确认就穷尽下游需求细节。缺核心依据或核心规则仍待澄清时保持草稿；AI 只整理依据与提出问题，不得通过推断或代填冒充明确依据。其他待澄清项不必全部清零，但须在固定材料及可阅读资产包中展示限制和不适用范围；非阻断项不能掩盖核心规则或验收条件缺失。作者确认沿用既有权限，不增加资产维护者或研发的额外审批。

**Git 与后端共同校验。** Git 保存固定正文、分类、来源及确认/复用证据；后端只保存与固定引用关联的必要分类控制元数据、内容确认/生产任务状态、复用资格及受理事件，不保存正文副本。Host 从同一份用户确认快照提取分类与来源，核对项目已有分类、MD、清单、固定 Git 引用及上报元数据；后端按可信身份、权限、revision、受理事件与固定引用接受状态及资格变化，确认受理与初次自动授予资格在同一事务内完成，幂等重试只返回原受理结果，不覆盖之后的停用结果。客户端操作可以影响复用资格，但必须走对应受控受理入口；客户端自填 `可复用=true` 或仅修改本地清单不能绕过后端受理，Git 中已有文件也不能单独证明具有复用资格。确认、采用、停用和恢复均须被后端接受才能展示受理成功；本地点击或后端拒绝不表示成功，响应未知显示待核验并查询原受理结果，不假设资格或采用已生效。

**已确认的修改与停用规则。** 新草稿不可复用；开始修改已有材料时，新草稿与旧固定版本分别记录，旧固定版本原有的有效复用资格继续保留，不因正在编辑而自动失效。取消草稿任务沿用既有任务取消规则，不改变旧固定来源的复用资格。显式停用针对操作者明确选定的固定来源，绑定资产身份与固定版本引用；后端接受停用后阻止该来源尚未受理的采用，不将整个资产历史或其他固定版本一并停用，不删除 Git 正文和历史。已经复制并独立维护的目标成果保留来源记录，不因来源停用自动撤销、删除或改写目标。

**停用与恢复权限。** 所有具有该资产编辑权限的成员均可对明确选定的固定版本发起停用或恢复，不限制为资产负责人或维护者。后端从既有可信身份校验该资产编辑权限，不把 Git 凭据、资产负责人身份或管理员占用释放权限替代实际编辑授权。受理记录固定来源、操作者、原因和服务端时间；停用/恢复不重做基线、不改写内容确认事实、不增加额外审批，恢复须经显式受理后才重新允许新采用。

**采用与停用的受理边界。** 浏览或选中来源不算采用；以后端是否已经接受该采用记录作为在途边界。后端对同一固定来源的采用与停用受理按同一竞争边界明确先后：采用受理校验固定来源版本、当前有效资格、来源读取与目标编辑权限，幂等保存目标任务、采用范围、固定来源及受理证据；停用先被接受则拒绝尚未接受的采用，采用先被接受则保留固定来源并允许该目标继续完成。继续完成仍须通过 Git 实际读取权限，采用受理不授予仓库访问能力。后端只记录必要控制元数据与受理事件，Git 保存来源及目标成果证据。采用受理不是复用成功；目标检查和确认被后端接受后再绑定目标固定版本与确认依据，原型代码目标遵守完成基线规则。

**长期保留与临时清理。** 已确认材料、固定版本及来源记录长期保留，停用只改变后续采用资格，不删除材料或证据。保留范围同时覆盖 Git 正文、清单、受管理的可达固定引用及其提交内容，以及后端对应元数据、确认/资格/采用受理事件和来源依据；不得通过常规分支、引用或元数据清理使正式资产、已受理采用来源或唯一确认依据变成不可读取。临时构建产物、缓存和任务现场按各自职责另行清理，不能当作正式资产保留的替代，也不能因停用而删除正式资产。清理前核对未提交/未推送修改、在途操作与任务现场及证据引用；尚有未保存成果、在途恢复依赖或唯一证据时阻断对应清理，保护现场并提示处理入口，不静默删除。实际存储、备份、固定引用可达性及清理实现由 G0 验证，不另建备份平台或预设实现周期。

**资产操作对照。** 下表是已确认的业务语义，不是新增 API 或状态枚举。

| 操作 | 受理与权限 | 对固定来源及目标的影响 |
| --- | --- | --- |
| 新增场景/需求 | 选择项目已有分类；按既有设计占用记录草稿与任务状态 | 新草稿不可复用，不影响已有固定来源 |

**G0 实施输入与实测边界。** 实际项目分类值、字段编码、分类与固定材料引用的校验方式及 Git 来源读取授权验证入口由 G0 样例固定；这些是实施输入，不再将已确认的词表维护权限、在途采用边界或取消草稿对旧资格的规则挂为待决策。上述语义已确认但尚未实测，不据此宣称权限、事务竞争或固定来源读取已经可用。

实际存储、备份、固定引用可达性和临时清理实现同属 G0 实施与实测；长期保留是设计约束，不代表现有 Git 与后端已验证能够持续保存和读取。验证应在常规清理后仍取得固定材料、来源及对应后端元数据/事件，不用“Git 曾经有提交”替代留存证据。

**必需验证。** G0 样例覆盖新增材料选择项目已有分类、所有项目编辑权限成员维护词表及无权限拒绝；场景/需求材料在原型未完成时通过检查、推送 Git 并由后端同一次受理接受确认和自动授予复用资格；新草稿不可复用、开始修改或取消草稿不改变旧固定版本原有有效资格；所有具有资产编辑权限的成员可停用/恢复、无编辑权限者被拒绝，资产编辑权限不能替代项目分类维护权限，不凭 Git 凭据或管理员释放权限放行；停用/恢复明确固定来源并记录操作者、原因和服务端时间，后端接受后才生效，不重做基线；旧确认查询或幂等重放不恢复已停用资格；浏览选中不算采用；采用与停用并发时仅按后端受理先后决定，停用先接受阻止尚未受理采用，采用先接受保留来源继续完成；重复采用只返回同一记录，Git 实际读取无权限仍拒绝；采用受理不计成功，目标确认后固定目标版本与确认依据；来源停用不删除 Git 历史、不撤销已复制并独立维护的目标及来源记录；原型代码没有完成基线时不得作为可复用代码；Git 与后端分类/固定引用不一致、后端拒绝、客户端伪造可复用标记均不得显示受理成功，响应未知显示待核验。以上是必需实测用例，不将本节文档约定当作已实测结果。

内容与留存必需用例：核心规则或验收缺失、只有字段占位或模型自称已明确时保持草稿且确认/自动授予被阻断；作者确认本次范围核心依据后，可以保留非阻断待澄清项，但资产包必须可读取限制及不适用范围；场景不因尚未拆出的下游细节被误阻断。停用及常规临时清理后，已确认固定正文、可达引用、来源记录、后端对应元数据/事件及采用依据仍完整可读；清理不能删除未提交/未推送成果、在途恢复现场或唯一证据。上述能力仍需真实 G0 样例验证。

### 2.4 原型工具链、安装与执行成果归属

G0 固定 DSH 发布版/源码提交、插件版本、指定模板目录的版本与校验值、模型标识、宿主工具链与 Git；模板运行时、包管理器和精确依赖组合直接读取模板，不重新选择。
指定模板及其 `AGENT.md` 是技术栈、运行时/包管理器、冻结依赖规则与锁文件、目录/路由/Mock 约定、预览启动与 ready 检查、工程检查、静态构建命令和产物目录的唯一来源；有类型系统的模板须包含类型检查。仅接入通过该契约验证的指定模板，不默认任何框架或目录都可直接运行。
官方 `load_workspace_dependencies` 可用于定位宿主已有 Node/pnpm 工具，核查目标发布版接口后直接使用；这不表示生成模板必须采用该工具链，模板所需运行时须另行核对版本和执行边界，不自造运行时分发器。

有依赖安装的模板按其规定的包管理器、锁文件或等价固定版本规则进行冻结安装；离线能力只有在对应缓存、证书和依赖全部实测满足后才能承诺。
没有依赖安装或类型系统的模板须在契约中定义对应的版本可复现与工程质量检查，不照搬命令，也不能省略原型行为、静态产物和安全边界的必需验收。

SSH Agent 或凭证引用只是取用方式，不自带调用方隔离；G0 必须验证普通 Agent、模板安装/构建脚本及其他执行入口无法越权取用发布凭证或调用敏感发布操作，限制在执行前生效。
专用服务器发布账号只获得规定部署目录与发布原语所需权限；连接前验证固定主机指纹，不在首次连接时通过现场 `ssh-keyscan` 自动建立信任。
敏感素材不得进入源码、Agent 会话、插件 client、命令参数显示、普通日志或静态产物；代码托管凭证与服务器发布凭证分别管理。
网络可达不等于授权访问；静态 Web 服务使用已有成熟方案（如 Nginx），站点协议与项目访问策略由服务器或项目已有访问入口落实，不假设统一企业身份。站点 URL 按项目实际情况使用 HTTP 或 HTTPS，不设独立协议配置层；选择 HTTPS 时校验证书链与主机名，校验失败阻断，不自动降级为 HTTP；选择 HTTP 时无需证书检查。G0 验证部署地址与访问方式符合项目设置；受限项目验证目标受众可访问、未授权访问被拒绝，显式公开项目验证无需身份认证的公开访问符合预期。无论访问方式如何，演示只包含原型与合成 Mock 数据，原始业务材料仍按仓库权限读取。

受限 webview 只约束页面获得的宿主能力，**不等于模板运行时、构建脚本、Agent shell 已被沙箱隔离**。
提示词不是强制控制；限制必须覆盖 DSH 所有文件写入和 shell 入口，以及包管理、安装脚本、构建脚本与生成代码的执行。
G0 必须尝试越界写入、修改模板受保护的依赖/锁文件与构建配置、调用任意命令和访问不允许的目标，验证拦截发生于执行前并留下明确结果。
Windows ACL 沙箱当前资料标记 partial：不限制读取、网络和进程可见性；workspace-write 也不能细粒度保护工作区内的模板规则与工程配置。
G0 必须实测受限子进程的 spawn/stdio pipe 与指定模板命令的兼容性，并确定规则和配置文件保护如何覆盖所有工具入口，不能直接把默认沙箱当作控制已成立。
如需 OS 级执行隔离，必须根据目标 OS 验证实际方案；未通过前不得称为“安全沙箱”或开放给无法承担本地执行风险的用户。
用户已确认真实场景、需求正文及附件可以按企业现有数据政策发送给 DeepSeek；沿用既有政策，不新增审批流程。模型输入会发往所配置供应方，完整 AI 对话、提示词、草稿和工具日志仍不上传协同后端。具体材料、截图及日志的发送范围、供应方保留规则和费用须与既有政策及实际模型配置一致；G0 技术用例优先采用合成样例，不能因使用内网 GitLab 就宣称数据全部留在内网。

### 2.6 原型模块 Mock 与静态演示

Mock 实现与初始化方式来自指定模板，在本地预览和发布后的纯静态页面中提供一致的合成数据与交互行为；不得依赖开发服务器的请求处理才能演示。
模板必须明确原型 Mock 启用、就绪检查与失败行为；模拟能力未就绪时阻断相关交互并显示诊断，未匹配的模拟请求失败，不向真实业务服务透传。
请求路径、请求客户端及允许调用方式由模板约定，生成业务组件须遵守；不能绕过约定直接请求真实业务目标。
静态资源请求与模拟 API 明确区分，页面、字体和脚本可正常加载；模板不配置真实业务 API 域名、Key 或用户数据。
模板的静态检查、执行约束与站点 CSP 共同限制请求、表单和资源来源；不得加载未经允许的外部脚本。分享使用与真实业务 API 分离的静态站点 origin，开发所需 loopback/热更新规则与分享规则分别验证。
G0 与 Host 发布前检查须覆盖 Mock 未就绪、未匹配请求、组件初始化副作用和绕过约定直接网络调用等负向场景；不能仅凭 Mock 配置或生成提示词宣称不会触达真实业务目标。
推荐固定合成 seed、内存 CRUD、成功/失败/空数据场景；刷新后重置，并提供显式“重置演示”按钮。
各浏览器会话独立，无跨用户共享业务状态；不得把浏览器内模拟保存描述为后端持久化。
G0 与 Host 发布验证均按已配置站点 URL 检查实际协议、部署 base path、刷新路由与资源路径；HTTPS 站点额外验证证书，HTTP 站点不执行证书检查。采用 MSW 浏览器模式的模板另行检查浏览器安全上下文（通常为 HTTPS，localhost 可例外）、Service Worker URL/scope、初始化等待与旧 Service Worker 更新，不将这些实现细节作为所有模板的要求。远程 HTTP 目标若无法满足所选模板的 Service Worker 条件，阻断发布；由维护者选择并验证可在 HTTP 静态站点运行的 Mock 模板方案，不绕过浏览器安全限制、不临时禁用 Mock 或增加 fallback。非研发用户只看到模拟交互无法在当前站点运行的原因与维护者处理入口，不需要选择或理解技术协议。
分享产物不包含绝对源码路径、原始需求附件、凭证或内部调试映射；生产式静态构建不公开含本地路径的 source map。

### 2.7 协同后端、持久化占用与自动完成

#### 2.7.1 数据与权威边界

后端提供独立 API 和具备事务唯一性、条件更新及持久化能力的存储。协同后端由企业集中部署为固定服务，客户端连接固定服务地址，不在用户侧部署。框架、数据库与协同会话/绑定成员授权按当前 ADR 及 G0 证据确定；不建设通用工作流引擎、远端 Agent 或完整会话同步。

#### 2.7.2 占用、前置条件与释放

占用键为带实体种类的 `(project ID, entity ID)`：需求、场景、批次交接及批次基线分别使用自身 ID。初次录入先幂等预留稳定 ID，再原子取得设计占用才能与 AI 开工；ID 预留不计完成进度。后端短事务校验身份、权限、expected revision、场景门禁及唯一当前占用，通过条件更新授予新的 occupation ID/代次，绑定 owner、task、client。长任务只保留持久化记录，不持数据库长事务；同一占用键最多一个当前占用，同作者双端也不重入，只有同一操作的幂等重试返回原结果。

占用没有 TTL、自动到期、续期或心跳超时释放。断网、关闭客户端或本地暂停不会释放占用。完成确认后正常释放；作者主动取消须校验可信身份与当前 owner、occupation ID/代次、task/client 和 revision，原子中止任务并释放。后端管理员可按明确权限手动释放，必须指定被释放的占用 ID/代次及 expected revision、记录操作者和原因，并在同一事务中标记原任务已中止/占用撤销、作废其未完成提交受理、解除该批次冻结。此后其他作者才可重新占用；即使同一作者再次占用，旧占用 ID 的提交、确认和释放也一律拒绝。管理员释放不是完成审批，也不能将未完成成果标为完成。

需求设计时登记同项目前置 requirement ID 及所需需求版本或范围；此时前置可以尚未完成，不要求已有完成提交。保存条件时检查存在性、自依赖及依赖环，不能以场景关联或软件包依赖代替前置条件。原型生产认领时，后端在授予占用的同一事务中核验本需求已有确认版本、所有关联场景未冻结、全部指定前置已自动合并并被后端接受完成；不满足时说明尚缺的前置，不授予原型生产占用。认领绑定每项前置的需求版本、完成事件和认可集成 SHA；无依赖需求可以并行，待同步或仅 Git 已合入的前置不得放行。

需求或前置条件变更需要有效设计占用或场景批次权限，并产生新 revision 和对应 MD 内容 hash；已有任务不得继续沿用旧条件。原型任务内若需反向完善需求，按 2.2.3 先保存本地现场，按条件结束本次生产占用并完成需求修订与用户确认，再重新核验并认领；不能在旧认领下悄悄替换需求或前置范围。旧版本完成历史保留，但不表示新增范围已完成。

读取固定资料不需要占用。单需求基线及交接材料修改使用该需求占用；多需求交接/项目批次基线仅聚合后端已接受的固定版本，使用独立清单 ID，不长期占用所有需求。清单占用不能被用于修改其引用的需求内容。

#### 2.7.3 本地工作与远端提交边界

每个需求使用独立 worktree/分支。本地开工基础取后端认可的已合并状态，并核验包含认领时绑定的前置完成依据；本人当前预览只展示这份基础加自己的改动，不自动跟随他人的合入或远程站点更新，不提供历史预览切换。

Host 在开始受管理任务和发起提交前查询当前占用及输入条件；发现占用撤销或变化时停止该旧任务的新受管理提交/合并/确认，保留现场并提示核对。断网时占用仍存在，本地草稿与执行现场保留，远端提交受理、合并及完成不能在未核对后端状态时继续。系统不承诺强制停止离线用户的本地编辑，也不将其草稿自动算作已完成成果；重新联网先查询当前占用、输入和幂等操作结果，再判断继续或处理冲突。

后端在提交受理和最终完成两个节点都必须验证可信操作者等于当前占用人，并且 occupation ID/代次、task/client、expected revision、输入和前置依据仍匹配。管理员释放后，旧作者不能提交完成；同人重新占用也必须使用新占用 ID，不盲目重放旧操作。

Git 不参与后端事务，不能凭占用记录撤销已在途的 Git 命令。任务分支、稳定分支条件更新/受保护入口及最小操作记录共同约束集成；直接越过受控入口的 Git 变更不自动成为认可成果。所有在途合并与管理员释放竞态都按 2.7.4 核对，不能只凭 Git 成功宣布完成。

#### 2.7.4 作者确认后自动合并与完成

作者直接确认，或主动选择 AI 辅助评审并查看结果后自行确认，普通无冲突流程均自动执行以下步骤；AI 结果不能代替可信作者确认、工程检查或后端门禁，不增加独立人类评审者、人工合并或管理员审批。

1. Host 固定原型菜单中被用户明确确认的 requirement ID，检查本需求成果及所选提交路径的确认依据，核验场景/需求 MD 与已接受 hash、代码输入绑定一致，向后端请求提交受理。后端短事务核验当前占用人和占用 ID/代次、需求/input revision/hash、前置完成依据与场景门禁，记录幂等 operation ID，未通过则不继续受控提交。
2. Host 固定并推送任务分支源 SHA，验证获授权读取端可读取；按操作记录核对占用仍有效，然后基于后端认可集成头构造集成候选，只合入本次受理的任务差异，不机械继承远端分支上尚未获认可的其他任务提交。
3. 在短暂集成窗口中，对精确候选执行必要工程、Mock、浏览器及关系检查，整理确认清单/基线，并以预期稳定分支旧 SHA 做条件更新。其他任务已正常完成使认可集成头变化时，重新基于新认可头形成候选并重检；冲突、检查失败或权限拒绝进入待处理，本需求仍由原作者占用，不假报完成，也不静默覆盖。作者无需在无冲突时再次点击合并。
4. Git 成功后，后端最终再次核验可信操作者等于当前占用人、同一占用 ID/代次、输入/前置及预期认可集成头、候选检查与可读取引用，单事务更新认可集成头、所选需求完成/基线/确认事件，结束任务并释放占用。至此形成可交付基线，触发 2.3.1 的后台清单任务；以本需求原型完成为前置的后继认领、原型代码沉淀、完整成果交接及分享依据均需等到此节点，独立场景/需求材料按阶段内容确认受理后沉淀。基线确认页展示该结果，不重复要求作者确认。

集成只短暂串行，其他需求本地生产继续；不持项目级长任务锁。最小元数据包括操作 ID、占用 ID、任务源 SHA、预期认可集成头、候选 SHA、检查结果及 Git/后端处理状态，不新建通用集成平台。

Git 与后端没有分布式事务。合并已推送但后端完成未接受时，显示“合并待核对/完成待同步”，不得作为后继输入、发布源或下一次集成起点。后续集成先核验实际稳定分支与认可集成头；存在未知或孤立合并时暂停集成受理，不继承其改动。重连先按幂等键查询：已接受则恢复结果；未接受且原占用和全部条件仍有效时续办同一操作；占用已撤销或被替换则拒绝旧完成，保留 Git 与操作证据。维护者按可追溯反向提交纠正未认可的合入，验证仅包含已认可成果后核对并记录可继续的集成头；不以强制覆盖隐藏差异。纠正前其他独立 worktree 可继续本地工作，但不能越过集成阻断。管理员释放与在途 Git、后端响应丢失、同人重新占用都必须验证该恢复过程。

场景、需求设计和清单确认不等同于原型完成：设计类校验前置定义和依赖图，不要求前置已完成；Host 按 2.2.3 固定材料、计算 MD SHA-256 并推送，再带文件 hash、固定 Git 引用、当前占用及 expected revision 幂等上报，后端接受确认状态并正常释放，然后驱动相应后续 Agent 任务。阶段文档提交只纳入本次确认的 MD 与必要关系/确认清单，不携带本地未确认代码和其他候选需求草稿。任何写入稳定分支的资产变更都使用同一受理、候选核验及条件更新入口，只有后端认可后才推进认可集成头，不能通过“仅文档提交”带入未认可代码。阶段确认可以推进认可集成头，但不形成原型完成基线；部署只取项目当前已确认基线的固定代码版本，不能将裸认可集成头直接当部署源。场景联动另遵守 2.7.5 的完整批次事务。单需求原型基线随自动完成流程形成，项目批次基线/交接只引用已接受的固定成果。

#### 2.7.5 场景与需求联动修改

**准入与冻结**：开始场景修改的短事务校验可信身份、场景及关联集合 revision、全部关联需求的 revision/业务状态/占用，以及共享需求是否已被其他批次冻结。任何关联需求有占用或业务任务未结束即整体拒绝；不暂停他人、不先冻结等待。需求认领和场景准入采用同一门禁和确定的加锁顺序，先成功的一方排除另一方；长时间只持久化冻结状态，不持数据库长锁。

场景批次期间全部关联需求禁止常规修改和原型认领；批次作者凭当前场景 occupation ID/代次联动修改，不为每条需求另申请占用。新需求 ID 绑定该批次。关联新增、移入、移出须原子校验源/目标场景、共享需求状态及 revision，不能移出再认领绕过冻结。共享需求被任一场景冻结时，涉及它的其他场景修改同样拒绝；联动清单仅更新本次场景上下文，不自动改写其他场景。无关联冲突的场景及需求继续运行。

**联动清单与状态**：本地 AI 产出“旧场景 → 新场景、保留已完成成果、差异派生新需求、更新未开始需求及前置条件”的清单，由作者确认，不增加评审。已完成指指定需求版本已合并并被后端接受完成；单独的 Git 提交、基线 tag 或本地确认不算。原版本已完成而新版本尚未生产的，以新版本状态判断，不能借历史完成跳过新范围。任务处理中、暂停、待同步/待核对时，必须由作者有效取消或后端管理员释放并中止原任务后才可重新安排，断网不改变其状态。

| 关联需求类别 | 本次场景修改的处理 |
| --- | --- |
| 已完成的需求版本 | 保留 ID、内容、基线、旧场景及交接依据；变化/新增范围另派生新 requirement ID 并登记来源及前置条件，不继承完成状态 |
| 当前版本尚未开始原型生产 | 保留 ID，同步修改内容及场景依据、验收和前置条件，产生新 revision；联动确认明确新的确认版本，保留旧确认历史 |
| 不再适用的未开始需求 | 明确取消/不适用及原因，保留历史；同时检查依赖它的需求，不静默将前置视为完成 |
| 有占用或业务任务未结束 | 拒绝场景修改态，不应用联动修改 |

**批次确认与恢复**：Host 固定完整联动清单及材料，按同一受控 Git 集成入口处理，再发幂等 batch key。后端同时校验当前场景 owner/occupation ID/代次/task/client、场景和各需求 expected revision、关联集合 revision、前置图及固定引用，单事务接受场景、需求、派生 ID、关系和确认事件，并结束批次解除冻结。任一校验失败则最后确认状态整体不变，不显示部分更新；Git 已推送但后端未接受仍为待核对，不推进认可集成头。

作者主动取消或后端管理员手动释放时，按当前占用 ID/代次及 revision 原子中止批次、作废待完成操作并解除该批次冻结。取消/释放与新认领使用同一门禁事务；旧作者或旧批次请求不能更新需求、释放新占用。断网和客户端关闭不自动解冻；草稿保留，重连查询当前占用及批次事件，不能盲目重放。

| 逻辑接口 | 最小行为 |

| 查询项目/实体/占用 | 可见项目目录；实体分类、内容确认状态、生产任务状态、固定版本当前复用资格及受理依据、revision、固定引用、前置状态、当前 occupation ID/owner/task/client 及场景冻结，不返回 AI 过程；读取旧确认事实不重新授予资格 |

| 原子领取 | 校验唯一占用、身份/revision 和场景门禁；原型生产额外校验全部指定前置完成并绑定其完成依据，授予新占用 ID/代次 |
| 确认设计/清单 | 当前占用人及占用 ID、expected revision、MD hash/算法、Git SHA/路径、分类/来源及前置图校验；Host 核验结构与来源，作者基于真实依据确认本次范围核心规则与验收，缺核心依据保持草稿，非阻断待澄清展示限制/不适用范围；后端按操作者 Git 授权临时读取固定 MD，独立核验实际哈希及元数据，业务 API 不接受正文且后端不保存正文；确认状态与正常释放原子完成，场景/需求材料通过检查及读取核验后，在同一次后端受理内接受本次可信用户确认动作、生成确认记录并自动授予该固定版本复用资格；返回确认事件 ID 供 Host 驱动后续任务，幂等重试不覆盖后续停用 |
| 停用/恢复固定来源复用资格 | 可信身份具备该资产编辑权限；明确固定来源，记录操作者、原因与服务端时间，由后端受理后生效；不重做基线、不增加审批，不删除 Git 历史或自动撤销独立目标；管理员释放权限不能替代编辑授权 |

接口路径、编码、框架和既有认证/读取验证入口由 G0 固定；上述占用、前置与完成行为是确定的产品约束。

必需用例：同需求双作者/双端认领仅一成功；需求设计不被未完成前置阻断；前置不存在/自依赖/成环拒绝；指定前置仅 Git 合并或待同步不放行、完成确认后才能认领；独立需求并行、每需求独立 worktree；断网/关闭客户端占用保留；后端管理员手动释放后他人可占用，旧作者提交拒绝，同人重占旧 ID 仍拒绝；作者取消不影响新占用；直接确认自动合并无需第二次点击或审批；精确候选冲突/检查失败不完成，集成头变化重建重检；管理员释放与在途合并/响应丢失竞态、孤立提交阻断后继/发布/下一集成并可核对纠正；真实双客户端、持久化事务及稳定分支条件更新验证，不以本地锁代替。

确认驱动必需用例：新建与 Git 地址打开均得到三业务目录；一场景一 MD；自然语言明确确认与按钮双击/重复提交只产生一个有效确认及后续任务；确认目标不明不代猜；Agent 自称已确认不触发上报；MD 保存字节、Git 固定文件与上报 SHA-256 一致；确认期间文件变化、固定引用不可读或后端拒绝不启动后续 Agent；场景确认仅生成一次候选标题，未选项不确认/不占用；需求确认后默认编码，前置未完保持已确认但等待；反向修订保留代码、确认新 MD 并重新认领，旧 hash 不允许完成；最终完整快照不混入其他任务草稿；基线完成后自动生成清单，失败仅重试清单；部署只用当前确认基线，阶段 MD 提交不被误当作部署版本。

场景联动必需用例：场景准入与需求认领竞争仅一成功；任何占用/未结束任务阻断准入，断网不解冻；共享需求和关系移入/移出不能绕过门禁，加锁顺序无死锁；完成留旧、变化派生、未开始同步及前置重新校验；批次任一失败不部分更新；取消/管理员释放与新认领原子竞争，旧占用不清除新冻结；Git 成功后上报失败/响应丢失按批次和集成操作恢复。

#### 2.7.7 项目目录、内容与状态分离及新成员认领走查

**正文推送 Git，协同后端接收哈希和控制元数据。** 按 2.7.1 权威边界，阶段确认就将场景/需求 MD 及分类、来源证据固定并推送 Git；后端接受内容确认后材料可独立沉淀，原型完成时再提交相关代码与文档形成完整项目基线。场景、需求、基线、交接的正文与证据全部保存在 Git 固定版本中；协同后端只保存实体身份、最小摘要、必要分类控制元数据、server revision、内容确认状态、生产任务状态、复用资格及受理事件、固定引用（Git 提交 SHA、文件路径、内容 SHA-256）、前置条件及完成依据、占用与场景冻结，不另存正文副本。占用键为带实体种类的 `(project ID, entity ID)`（2.7.2），锁定对象是实体身份加 revision，控制判断基于后端元数据。

文件 hash 只标识内容，不证明业务语义或自动验证依赖图。受控 Host 确认入口必须从同一份用户确认快照提取 MD 中的实体、分类、来源、场景和前置关系，核对根清单、上报字段及输入绑定；推送后按固定 Git 引用重读并计算文件 hash，检查证据绑定该引用。后端不以两个客户端自报 hash 或检查 ID 证明字段一致，而是按操作者有效 Git 读取授权，在内存中独立读取同一固定 MD、复算实际字节 hash 并解析、比较控制元数据；固定仓库、提交和相对路径须与受理范围匹配，客户端不能另填一套分类或关系。该解析与读取方式、正文不进数据库/日志/文件缓存/错误响应、权限不足及引用不可读的拒绝均须 G0 实测，不能使用通用服务凭证扩大读取或回退信任客户端声明。后端再核验可信身份、当前占用/revision、关系门禁及受理事件；结构化核验不能替代作者对业务依据的确认或证明真实用户确认动作，复用资格也不能直接接受客户端自报标记。新成员从 Git 固定引用取得 MD 并在本地复算 hash，不能凭后端 hash 还原正文。

**后端实体记录是最小目录卡。** 以需求为例，一条需求的后端记录（2.3 需求行、2.7.1）只含身份（project ID、requirement ID、名称摘要、server revision）、与固定版本关联的必要分类控制元数据、状态（生产任务状态、内容确认状态、对应固定版本的当前复用资格及依据、固定版本引用）、关系（关联场景集合及 revision、派生来源、前置需求 ID/所需版本及完成依据）、占用（当前 occupation ID/代次、owner/client/task）与受理事件（幂等键、类型、固定引用、操作者、服务端时间；停用/恢复另记原因）。材料确认受理同时记录该固定版本初次自动取得资格；后续停用/恢复事件明确被选定的固定来源，按事件结果维护当前资格，不用旧确认事实或当前生产任务状态覆盖资格。每个字段回答"锁定谁、能否认领、基于什么开工、哪个版本可复用"，正文一律按固定引用从 Git 读取。

采用记录另只保存幂等键、固定来源、目标实体/任务、采用范围及必要受理证据；与停用事件核验同一固定来源的受理先后。目标确认后补齐目标固定版本及确认依据，形成固定两端的复用关系；采用受理本身不计成功，正文和完整调整证据仍按固定引用从 Git 读取。项目分类控制元数据和维护事件以项目编辑授权受理，不与单资产资格操作授权混用。

**项目发现。** 协同后端同时是项目目录：按 2.3 项目行持久化稳定 project ID、名称、负责人、仓库关联与资产清单入口；成员经查询接口只见其既有可信身份拥有项目授权的项目，仓库读取授权由独立协同用户绑定的 GitLab 成员权限决定，不以管理 token 可见范围扩张目录，不增加 GitLab 开户、账号同步或独立项目门户。

**新成员从零到认领。** 工作台不设任务分配机制（2.7.1 不建设通用工作流引擎）：需求在需求协同阶段确认后即可被有权限成员认领，获取方式只有门禁加认领。

1. **进项目**：先登录协同后端，再从目录选择已登记项目；后端按协同用户绑定的 GitLab 有效成员权限过滤目录。本机已打开项目与后端可见项目分别显示，pending 项目仅恢复初始化，ready 后才可认领。
2. **拿内容**：Host 按 3.2 打开既有项目，以项目身份、仓库关联和资产清单识别，clone 到受管理工作空间并校验清单与模板标记；场景/需求材料、关系清单、确认/基线/交接证据全部随固定版本可读（1.3.1）。
3. **看进度**：按 2.7.6 查询接口读取各需求的最后确认状态、revision、固定引用、前置状态、当前占用及场景冻结。需求列表由两部分组成：已确认需求目录（正文从 Git 固定版本读取）与占用中的条目（仅显示"由谁处理中、当前不能认领"的必要占用状态，本地草稿与 AI 过程不可见，1.2）。
4. **认领开工**：可认领判定只取决于既有身份与项目权限、当前占用、场景冻结与前置条件（2.7.2），与加入先后无关；原子领取是条件更新短事务，不满足时明确说明尚缺的前置或冲突原因。开工基础不是最新代码，而是认领时绑定的前置完成依据与认可集成 SHA（2.7.3），worktree 由此建立。

**可见性边界。** 预留 ID、尚未确认设计的需求对其他成员只显示占用状态，不显示内容与清单；确认上报后其摘要、revision 与固定引用才进入后端（2.7.4 设计确认上报）。任何查询不返回完整 AI 对话、提示词、中间草稿或工具日志（2.7.1）。
