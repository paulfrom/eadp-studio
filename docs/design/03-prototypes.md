# 原型工作台交互设计

状态：2026-10-31 用户进一步明确按可点击设计稿实现，允许交互调整但保持风格；需求选择并入原生 AI 会话选择，选哪个需求就以哪个需求进入对应会话。工作台保持 AI＋成果两个主栏，删除独立需求大侧栏。产品、文字设计与[可点击设计稿](../dseign/原型交互工作台.html)同步维护，不能将设计稿降为历史参考来解释实现偏差。本次仅做静态验证；原生运行工具此前的独立本地验证见[记录](prototypes/verification-runtime-2026-10-31.md)，不代表本次桌面闭环通过。开发段占用、commit 与恢复仍按[本地开发协议](prototypes/local-development-protocol.md)执行。

## 1. 用户目标

用户围绕项目原型与 AI 持续协作，查看多个需求共同形成的页面、业务流程和工程文件，运行统一应用，核对跨需求交互，再确认当前原型成果。本地自动开发队列、开发占用与提交同步见[本地开发协议](prototypes/local-development-protocol.md)。

原型不是一条需求对应的独立工作台。对话本轮关注某个需求、页面或文件，不会把整个原型切换成单需求任务；需求集合是查看和定位入口，不是每轮开工前必须锁定的输入包。移除“当前需求＋固定版本”“实现依据”“绑定新需求版本”等交互和门禁。

需求材料仍按需求协同阶段独立整理和确认；原型的项目级呈现不改变这些材料自身的版本规则。正式基线固定的是被接受的成果版本，与给原型指定一条固定需求依据是不同概念。

示例项目是采购协同平台，原型同时包含采购订单、审批记录和供应商目录。三项需求组织成同一个可操作应用，不是三个互相隔离的预览。

## 2. 桌面端职责

### 2.1 工作台结构

| 区域 | 内容与交互 | 边界 |
| --- | --- | --- |
| 项目侧栏 | EADP 品牌、项目卡片、场景／需求／原型／基线／交接导航、底部用户。 | 与 AI 交互稿一致；不把工程文件树当成业务阶段导航。 |
| 顶部 | 项目名、原型名称、需求数量及当前运行状态。 | 没有固定单需求版本或“实现依据”入口。 |
| 原生会话选择 | AI 会话头部以需求编号、名称和开发状态选择会话；可在此继续、切换或进入尚无会话的需求。 | 不增加独立需求选择栏；材料状态与开发状态分别表达。“查看材料”是单独动作。 |
| AI 会话 | 复用宿主 `conversation.content`，保留原生流式消息、工具、附件、提问、停止和输入。 | 选择已有事项定位原会话；切页面、切文件不重建会话或改变项目原型范围。 |
| 右侧成果区 | “预览／代码”切换，运行预览、确认原型。 | 对同一个原型工程操作，不按点击的需求切换工作树或应用。 |
| 底部输出 | 可折叠的运行输出与问题。 | 只读诊断，不提供任意终端命令输入。 |
| 成果核对 | 在工作区内展开，与预览并列查看；固定所阅成果并发起受控接受。 | 不用模态抽屉遮住业务预览；逐需求完成与整体接受分别表达。 |
| 状态条与诊断 | 当前源码与运行状态；技术详情按需展开。 | 诊断保留按需抽屉；路径、提交、工程证据不常驻业务主界面。 |

AI 协作使用项目已有 `NativeConversation` 与宿主公开 Factory，不自行轮询消息正文或过滤工具消息后再拼一套聊天。原生体验属于产品成功标准：消息增量、工具过程、附件、交互问题、输入法、停止、切换与返回的连续性均须在真实桌面验证。设计稿仅表达视觉意图，不能替代宿主原生交互。

### 2.2 需求集合与 AI 协作

原生 AI 会话头部的需求菜单合并原需求集合与本地事项队列的选择入口，显示项目全部普通需求及真实开发状态。已有活动事项恢复原会话和现场；没有本地事项则通过统一 Host 入口为该需求准备开发会话，保留原始排队／创建操作身份。等待期间显示所选需求的准备状态，不能回退到其他事项，更不能把 `queued:` 身份作为文件工程。允许已有规则下的可读草稿探索，不额外增加需求必须再次确认的门禁。

“查看材料”只打开当前所选需求正文，并提供返回原型入口，不负责开始开发。进入原型的需求页按钮与会话菜单使用同一个 `enterPrototypeRequirement` 命令；失败时保留目标、现场和原操作键，下一次选择同需求核对原结果。选择需求明确本轮开发的业务上下文，项目原型仍是多需求共同形成的应用，不锁定材料版本，不因切文件或预览页面更换会话。

同一开发会话涉及多个需求时，所选需求作为本轮关注点保存在 Host，并通过官方动态系统上下文提供给原会话；不只改标题，也不扩大写入权限。后台自动推进其他开发项不抢走用户已选择的会话。切换期间不挂载旧会话输入，避免需求名称已经切换、实际消息仍发往旧会话。

主输入框始终属于当前原生会话；后续指令不调用新建事项。主界面不提供“新建补充事项”或事项类型表单。包括跨需求调整在内，用户直接在当前原生会话表达意图，由 Host 识别实际涉及需求并管理内部执行事项、分支与占用。范围不明确时在对话中提出具体问题；明确意图仍须经可信 Host 核实权限，不能靠模型文字扩大授权。会话可以跨多轮持续使用；开发段表示一次进入／恢复后持有许可的连续开发过程，许可释放后继续修改须重新进入下一开发段。材料阅读与只读基线查看不隐式取得开发权。

占用冲突反馈须说明当前事实与可执行下一步：属于本人当前设备的原事项应恢复原会话；其他账号或设备仍在开发时说明占用归属及处理方式，保留输入，不自动抢占或另建同需求可写事项。只在确需改变他人／其他设备许可时取得明确授权。状态保存、网络或会话恢复失败须分别解释，不能复用旧占用提示掩盖实际原因。完整技术细节留在诊断。

示例关联：采购订单定位订单列表与编辑页面，审批记录定位审批过程，供应商目录定位供应商页面。共享组件和跨需求流程可以服务多个需求，不强行建立需求与页面的一对一关系。

AI 以当前项目原型、工程和本轮对话为上下文，按当前任务读取相关需求和文件。实际读取范围应如实表达，未读内容不能声称已读取；这不形成常驻的固定依据面板或重新绑定流程。用户对一个需求的讨论可以产生跨页面调整，文件变更仍统一显示在当前工程中。

相关需求内容更新时，可提醒核对影响并提供查看入口；保留对话、代码和预览，不自动重置任务，不增加“重新绑定固定依据”门禁。材料自身修订仍通过需求阶段处理。

多人协作采用“不同需求并行，同一需求开发互斥”。首次业务代码写入前，Host 根据明确实现意图原子领取实际开发需求；内部执行事项可包含多个需求，确认需求的自动开发逐项排队、执行前领取。参考阅读不领取，不要求用户预先选定固定版本输入包。已被占用时保留输入并显示占用状态，不创建第二个同需求可写任务。独立分支负责现场隔离，不能代替后台开发占用，详见[协同契约](prototypes/collaboration-contract.md)。

“我的协作事项”提供本人桌面的开发队列：需求确认后自动入队，桌面自动串行开发，一项产生成果后进入待用户核对并继续下一项，不等待用户逐项批准。一个事项仍可包含多个需求，但各需求独立显示开发程度、成果、核对与纠偏进度，不能用事项级模型结束代替逐项认可。用户可暂停队列、针对某项需求纠偏并重新核对；这些本地阶段不写入协同远端，也不自动形成项目原型基线。

首次 AI 开发完成后，Host hook 自动提交并推送，后端核验 commitId 与指定远端引用一致后释放该需求占用。纠偏须先重新原子领取，AI 改完仍保留占用，直到用户最后确认、推送并经后端核验后解除；他人已占用时保留输入并等待。每次标记携带 commitId，但是否可开发以占用标识为准：未占用不要求远端 commit 一致即可原子领取，已占用返回正在开发中；管理员可主动修改标识，缓存不替代后端许可。释放不删除成果、对话或工作现场，也不代表项目整体已接受。关闭应用保留本地队列和现场；重开核对后端占用、远端提交及未知操作后自动继续，不盲目重发未知模型请求。具体授权、hook 与恢复见[本地开发协议](prototypes/local-development-protocol.md)。

### 2.3 预览与运行

| 操作 | 交互结果 | 失败与恢复 |
| --- | --- | --- |
| 运行预览 | 当前可写事项向当前原生 AI 会话发起运行任务，由 AI 调用受管预览工具。 | 失败诊断返回同一轮对话，AI 修复后重试；不要求用户手动执行 pnpm。 |
| 停止／重新运行 | 控制当前原型的受管进程，重建当前源码对应的预览。 | 不停止其他应用或任务；保留工程和对话，允许重试。 |
| 页面导航 | 从同一应用切换订单、审批、供应商等页面。 | 不改变需求集合，不重新创建会话；路由来自实际工程目录。 |
| 刷新预览 | 刷新当前应用。 | 合成数据按模板规则重置。 |
| 放大／外开 | 放大画布或打开同一受管本地预览。 | 不等于分享、远端部署或正式发布。 |
| 源码变化后查看 | 保留旧预览，明确提示待重新运行。 | 不把旧构建描述成当前源码的结果。 |

运行操作先保存原操作身份及目标，再沿用既有开发占用和串行队列派发。Host 管理进程、持久保存真实运行结果；只有工具验证成功才显示成功，普通对话轮次结束不等于预览成功，代码修改后须重新运行验证。只读已认可基线沿用独立受管运行，不隐式修改成果。开发完成 hook 的工程检查失败仍沿用自动修复流程；原生运行工具的真实桌面闭环尚未验收。

预览只有一个宽度：随画布自适应桌面。设计稿不再提供桌面、平板、手机等分开演示，也不在预览时提示“合成业务数据 · 仅用于需求核对”；底栏只说明当前为自适应桌面。是否满足移动端与多端适配由需求本身决定，不由预览宽度切换证明。

内嵌承载采用主进程持有的隔离 `WebContentsView`（`apps/desktop-distribution/build/studio-prototype-view.ts:82`），原型作为独立顶层文档加载，保留现有 CSP；不直接移植设计稿 iframe。画布布局、焦点、遮挡、停止及恢复方案与 PT05／PT07 的实现验证样本见[内嵌承载设计](prototypes/technology-and-browser-validation.md#11-r03内嵌承载候选与证据边界)。真实桌面 Electron／Chromium 版本与承载体验尚未完成闭环验收。切到代码或打开覆盖面板时隐藏原生画布，恢复前核对当前预览实例；失败保留工程并显示重试入口，不以旧构建或独立窗口冒充内嵌成功。

设计稿的预览用隔离 iframe 承载业务页面，隔离属性必须允许表单提交，否则订单新建与保存无法完成，页面流程会在保存这一步断掉。这条约束同样适用于产品的受管预览：承载层要放行预览页面自身的表单交互，不因此获得工作台命令权限。

应用内“保存订单”“查看审批”只影响业务原型，不能触发工作台确认。真实产品沿用受控 loopback 服务、Mock 与网络围栏，预览页面不能获得工作台命令权限。

本地业务验证由稳定 Playwright 驱动随包专属 Chromium（`host/prototype/browser-provider.ts`），按需求用例执行点击、填写、校验与结果断言，并返回截图、DOM、console 和 trace；现有 Electron 检查继续负责实际桌面预览的技术保护，两种结果分别表达。模板当前使用内存精确 Mock handler，不是 MSW；方案与新增分发成本见[技术选型与浏览器验证](prototypes/technology-and-browser-validation.md)。浏览器验证的真实业务用例尚未完成桌面闭环验收。

### 2.4 文件与代码

- 代码视图显示当前原型工程的文件树、文件标签、正文、行号、搜索和变更对比。对话变更卡、工程问题和搜索结果统一定位到代码视图。
- 原型文件按工程组织，包含不同需求的页面及共享组件，不只展示某一条需求的文件。没有为单需求固定正文设置的常驻文件入口。
- 默认只读查看，显式“编辑”后才进入编辑态。仅任务已授权区域允许保存；保护文件的规则不因展示设计改变，Host 仍核对真实权限、路径、当前内容和占用。
- 有未保存编辑时，切文件、关标签或离开提供保存／放弃／继续编辑选择，保留草稿；冲突不自动覆盖。
- 保存实际源码变化后，工程检查与预览证据过期；变更对比是文件改动查看，不宣称代码已被项目接受。
- 文件树隐藏凭证、`.git`、依赖和临时构建目录，以及其他成员私有现场。工作目录仅在诊断入口展示。

### 2.5 确认当前原型

“确认原型”在主工作区展开成果核对区，呈现当前原型包含的需求、当前工程与跨需求业务核对参考，保留可操作预览。确认对象是当前原型成果，不是列表选中的一条需求；不再显示单需求固定依据校验。只有技术诊断使用抽屉。

点击入口时由 Host 准备当前精确成果，不要求作者先点技术性的“固定当前成果”。审阅后只需一次“确认并提交原型”，界面顺序调用既有确认与受控提交命令；已确认或提交未知的操作保留原身份，显示继续提交／核对原提交，不重新准备替代候选或再次要求作者确认。

| 面板内容 | 用途 | 门禁边界 |
| --- | --- | --- |
| 原型包含的需求 | 理解当前成果涉及的业务范围。 | 供查看、定位，不新增强制选择或锁定集合的步骤。 |
| 当前源码与预览 | 显示当前源码修订与预览是否对应当前源码。 | 预览未运行或已过期只作提示，不阻断确认。 |
| 跨需求业务核对参考 | 核对订单、审批、供应商及它们之间的交互。 | 可记“符合／有问题／未核对”，不新增逐项勾选门禁。 |
| 问题与 AI 辅助评审 | 定位页面／文件，将问题或可选评审请求放入 AI 草稿。 | 不自动发送、修改或确认，不强制 AI 审核。 |
| 作者确认 | 作者认可当前原型并发起受控提交。 | AI 不能代替作者确认，不再叠加重复的确认弹窗。 |

工程检查不在工作台呈现，也不作为确认门禁：类型、规范、构建与浏览器验证属于实现内部事实，业务是否正确仍由用户实际操作判断。只有未保存的源码修改会阻止确认，避免把未保存内容当成当前原型成果。

完成受理与后续基线入口按原型成果表达；基线仍保留正式接受的代码版本。未知结果先查询原操作，不重复提交；已被后台接受的成果不因本机收整失败回退。设计稿中的接受与基线都是明确标记的模拟，不证明现有后台已经支持集合级受理。

### 2.6 关键状态

| 状态 | 交互要求 |
| --- | --- |
| 生成中／取消 | 展示原生会话实际状态；保留已产生代码与对话。 |
| 尚无可运行产物 | 显示空态与运行入口；可先查看工程，不强制选择一条需求。 |
| 预览失败 | 展示原因与重试，不清空代码。 |
| 源码已变化 | 标旧预览，不把需求内容更新等同于源码已经改变。 |
| 多需求之间切换查看 | 项目原型身份不变；选择已有事项定位其原会话与现场，切换前保存编辑缓冲和输入，不新建或覆盖会话。 |
| 提交未知／接受后收整失败 | 按原操作恢复，分别呈现接受事实与未完成收尾。 |

### 2.7 进入开发段与恢复

进入／恢复开发段时，Host 核对当前账号、事项、需求占用和真实 Git 提交。同一有效占用内，原生消息持续进入同一会话；消息身份、轮次与完成 hook 所需记录在桌面持久化，不逐条重新申请远端授权，也不每个工具操作重新请求远端许可。首次开发完成仍自动推送、同步并释放，后续修改重新领取；纠偏完成仍保留占用至用户最终确认。

commit 匹配时直接进入；不匹配时桌面同步该事项的受管成果分支，成功后更新协同服务占用记录中的 commitId。这里的远端更新指协同记录更新，不是为进入会话额外推送代码。未提交代码、编辑缓冲、分叉及冲突不能被拉取覆盖；同步失败保留原现场及操作阶段。远端保留原子占用、代次、幂等及成果接受事实，不接管本地会话、Git 合并或本地流程判断。

发送、Git 和后端调用都区分确定成功、确定未执行和结果未知。未知时沿用原 operationId／原生 requestId 查询并恢复，不重新建立会话或换键重发。重启恢复选中的事项、原会话和已落盘现场；模型线程不能从内存断点恢复。原生未发送附件目前只有内存草稿，跨崩溃恢复缺少公开接口，列入[上游缺口](../blocked-upstream.md)，不能宣称无损恢复。

## 3. 协同后台职责

协同后台管理项目、任务、稳定开发需求范围、逐需求占用代次、commitId 和受管远端引用，并提供原子领取、成果同步及管理员改标识接口。桌面负责本地队列、原生会话、工程检查、合并和成果核对；完整需求正文、模型会话、纠偏输入和工具日志不复制到协同后台。

整体原型接受仍明确固定当前成果及实际涉及需求，保留代码版本、确认人、权限和幂等事实。自动开发成果同步只更新逐需求占用，不改变项目认可头、不生成原型基线，也不表示各需求已获业务认可。接口与事务详见[协同契约](prototypes/collaboration-contract.md)，真实桌面闭环仍须独立验收。

## 5. 验收标准

### 5.1 设计审阅

1. 工作台的深色主题、248px 项目侧栏、顶栏、状态栏、面板、消息、输入框和按钮与现有 AI 交互稿一致。
2. 首屏保持设计稿的 AI＋成果双主栏；需求选择只在原生会话头部，菜单显示多个需求及开发状态，无第三个需求大侧栏或固定版本绑定入口。
3. 项目原型身份保持不变；选择已有需求事项定位原会话，页面和文件导航不新建会话；查看材料后可返回原型，且不要求锁定实现依据。
4. 文件树展示多需求工程；预览／代码、文件标签、搜索、变更对比、编辑保存和未保存保护均可操作。
5. 运行、停止、重启、失败恢复和源码变化导致预览过期可操作；工作台不出现工程检查入口与结果。
6. 预览只有一个自适应桌面宽度，底栏说明自适应桌面；预览时不出现“合成业务数据 · 仅用于需求核对”提示。
7. 业务样例的搜索筛选、必填／金额校验、保存失败与重试、只读订单、审批和供应商页面可操作；订单、审批与供应商三个页面之间能互相跳转并回到原页面。
8. AI 协作使用原生会话，流式输出、工具记录、交互问题、附件、停止、输入法和会话草稿保持宿主体验；不存在简化聊天轮询或每条消息新建事项。
9. 确认面板面向当前原型，跨需求核对与 AI 评审可选；问题仅入草稿；无固定需求绑定或预览必须运行的额外门禁。
10. 场景、需求、原型三份设计稿各自的流程都能走通：需求稿与场景稿从审阅写入到确认固定版本，需求稿的两项阻断可在对话中答复后解除。
11. 模拟接受结果明确标识为演示；不把一条内部需求完成显示成整个项目原型已经完成的实际事实。
12. 键盘、焦点、Escape、窄窗折叠和减少动态效果有相应处理；视觉、可读性及真实浏览器效果仍须独立核对。
13. 开发段进入时核对占用和 commit；匹配直接进入，不匹配由桌面同步受管分支并更新协同记录，失败保留代码与草稿。有效占用内连续原生消息不重复远端授权。
14. 分别在发送、工具写入、提交、推送、后端同步和最终确认处中断后恢复；不重复执行、不错误释放、不丢已落盘现场、不显示虚假完成。未发送附件的上游限制单独记录。
