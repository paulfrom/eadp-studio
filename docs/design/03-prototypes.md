# 原型工作台交互设计

状态：2026-10-26 交互设计草案。按用户本轮明确决定修正：视觉与现有 AI 交互原型一致；原型是多个需求的集合，没有固定的实现依据。配套[可点击设计稿](../dseign/原型交互工作台.html)。本轮仅修改设计和术语，未改产品源码，不构成真实桌面验收。

## 1. 用户目标

用户围绕项目原型与 AI 持续协作，查看多个需求共同形成的页面、业务流程和工程文件，运行统一应用，核对跨需求交互，再确认当前原型成果。

原型不是一条需求对应的独立工作台。对话本轮关注某个需求、页面或文件，不会把整个原型切换成单需求任务；需求集合是查看和定位入口，不是每轮开工前必须锁定的输入包。移除“当前需求＋固定版本”“实现依据”“绑定新需求版本”等交互和门禁。

需求材料仍按需求协同阶段独立整理和确认；原型的项目级呈现不改变这些材料自身的版本规则。正式基线固定的是被接受的成果版本，与给原型指定一条固定需求依据是不同概念。

示例项目是采购协同平台，原型同时包含采购订单、审批记录和供应商目录。三项需求组织成同一个可操作应用，不是三个互相隔离的预览。

## 2. 桌面端职责

### 2.1 工作台结构

| 区域 | 内容与交互 | 边界 |
| --- | --- | --- |
| 项目侧栏 | EADP 品牌、项目卡片、场景／需求／原型／基线／交接导航、底部用户。 | 与 AI 交互稿一致；不把工程文件树当成业务阶段导航。 |
| 顶部 | 项目名、原型名称、“需求集合”入口及当前运行状态。 | 没有固定单需求编号或版本，没有“实现依据”入口。 |
| 左侧 AI | 当前项目原型的持续对话、文件变更卡和输入框。 | 可跨需求讨论；切页面、切文件不重建会话或改变原型范围。 |
| 右侧成果区 | “预览／代码”切换，运行、检查、确认原型。 | 对同一个原型工程操作，不按点击的需求切换工作树或应用。 |
| 底部输出 | 可折叠的运行输出、工程检查和问题，支持定位文件。 | 只读诊断，不提供任意终端命令输入。 |
| 状态条与诊断 | 当前源码、运行与检查状态；技术详情按需展开。 | 路径、提交、工程证据不常驻业务主界面。 |

### 2.2 需求集合与 AI 协作

“需求集合”列出原型包含的多个需求，可查看需求摘要，并定位相应页面或代码。它不是固定实现依据，不要求用户先选定唯一需求、锁定版本或再次确认集合才能运行、对话或查看文件。

示例关联：采购订单定位订单列表与编辑页面，审批记录定位审批过程，供应商目录定位供应商页面。共享组件和跨需求流程可以服务多个需求，不强行建立需求与页面的一对一关系。

AI 以当前项目原型、工程和本轮对话为上下文，按当前任务读取相关需求和文件。实际读取范围应如实表达，未读内容不能声称已读取；这不形成常驻的固定依据面板或重新绑定流程。用户对一个需求的讨论可以产生跨页面调整，文件变更仍统一显示在当前工程中。

相关需求内容更新时，可提醒核对影响并提供查看入口；保留对话、代码和预览，不自动重置任务，不增加“重新绑定固定依据”门禁。材料自身修订仍通过需求阶段处理。

多人协作采用“不同需求并行，同一需求开发互斥”。首次业务代码写入前，Host 根据明确实现意图原子领取实际开发需求；可跨多个需求并动态扩领，参考阅读不领取，不要求用户预先选定固定版本输入包。已被占用时展示开发者与事项并保留输入，不创建第二个同需求可写任务。独立分支负责现场隔离，不能代替后台开发占用，详见[协同契约](prototypes/collaboration-contract.md)。

“我的协作事项”同时提供本人开发队列：一个事项可包含多项需求，默认串行，由用户手动继续或切换。显示待开始、正在执行、待用户核对、已暂停或待恢复等本地阶段；这些不是需求完成状态。关闭应用保留队列、已领取需求和原现场，重开核对有效任务后恢复原会话及界面，等待用户继续，不自动启动队首或重发模型指令。

### 2.3 预览与运行

| 操作 | 交互结果 | 失败与恢复 |
| --- | --- | --- |
| 运行预览 | 对当前工程串联必要的工程检查、静态构建、浏览器验证和本地预览；有效检查可以复用。 | 展示实际步骤与失败原因；不要求用户手动执行 pnpm。 |
| 停止／重新运行 | 控制当前原型的受管进程，重建当前源码对应的预览。 | 不停止其他应用或任务；保留工程和对话，允许重试。 |
| 页面导航 | 从同一应用切换订单、审批、供应商等页面。 | 不改变需求集合，不重新创建会话；路由来自实际工程目录。 |
| 刷新／设备切换 | 刷新当前应用、调整画布宽度。 | 合成数据按模板规则重置；设备尺寸不自动证明响应式通过。 |
| 放大／外开 | 放大画布或打开同一受管本地预览。 | 不等于分享、远端部署或正式发布。 |
| 源码变化后查看 | 保留旧预览，明确提示待重新运行。 | 不将旧构建或旧检查描述成当前源码的结果。 |

内嵌承载采用主进程持有的隔离 `WebContentsView`（`apps/desktop-distribution/build/studio-prototype-view.ts:82`），原型作为独立顶层文档加载，保留现有 CSP；不直接移植设计稿 iframe。画布布局、焦点、遮挡、停止及恢复方案与 PT05／PT07 的实现验证样本见[内嵌承载设计](prototypes/technology-and-browser-validation.md#11-r03内嵌承载候选与证据边界)。真实桌面 Electron／Chromium 版本与承载体验尚未完成闭环验收。切到代码或打开覆盖面板时隐藏原生画布，恢复前核对当前预览实例；失败保留工程并显示重试入口，不以旧构建或独立窗口冒充内嵌成功。

应用内“保存订单”“查看审批”只影响业务原型，不能触发工作台确认。真实产品沿用受控 loopback 服务、Mock 与网络围栏，预览页面不能获得工作台命令权限。

本地业务验证由稳定 Playwright 驱动随包专属 Chromium（`host/prototype/browser-provider.ts`），按需求用例执行点击、填写、校验与结果断言，并返回截图、DOM、console 和 trace；现有 Electron 检查继续负责实际桌面预览的技术保护，两种结果分别表达。模板当前使用内存精确 Mock handler，不是 MSW；方案与新增分发成本见[技术选型与浏览器验证](prototypes/technology-and-browser-validation.md)。浏览器验证的真实业务用例尚未完成桌面闭环验收。

### 2.4 文件与代码

- 代码视图显示当前原型工程的文件树、文件标签、正文、行号、搜索和变更对比。对话变更卡、工程问题和搜索结果统一定位到代码视图。
- 原型文件按工程组织，包含不同需求的页面及共享组件，不只展示某一条需求的文件。没有为单需求固定正文设置的常驻文件入口。
- 默认只读查看，显式“编辑”后才进入编辑态。仅任务已授权区域允许保存；保护文件的规则不因展示设计改变，Host 仍核对真实权限、路径、当前内容和占用。
- 有未保存编辑时，切文件、关标签或离开提供保存／放弃／继续编辑选择，保留草稿；冲突不自动覆盖。
- 保存实际源码变化后，工程检查与预览证据过期；变更对比是文件改动查看，不宣称代码已被项目接受。
- 文件树隐藏凭证、`.git`、依赖和临时构建目录，以及其他成员私有现场。工作目录仅在诊断入口展示。

### 2.5 确认当前原型

“确认原型”打开右侧核对面板，呈现当前原型包含的需求、当前工程、工程检查与跨需求业务核对参考。确认对象是当前原型成果，不是顶部选中的一条需求；不再显示单需求固定依据校验。

| 面板内容 | 用途 | 门禁边界 |
| --- | --- | --- |
| 原型包含的需求 | 理解当前成果涉及的业务范围。 | 供查看、定位，不新增强制选择或锁定集合的步骤。 |
| 当前源码与工程检查 | 展示 typecheck、lint、build、Mock 和浏览器检查。 | 当前代码变化使旧证据失效，正式接受仍须重新检查确切成果。 |
| 跨需求业务核对参考 | 核对订单、审批、供应商及它们之间的交互。 | 可记“符合／有问题／未核对”，不新增逐项勾选门禁。 |
| 问题与 AI 辅助评审 | 定位页面／文件，将问题或可选评审请求放入 AI 草稿。 | 不自动发送、修改或确认，不强制 AI 审核。 |
| 作者确认 | 作者认可当前原型并发起受控提交。 | AI 不能代替作者确认，不再叠加重复的确认弹窗。 |

工程检查不证明跨需求业务正确。用户需实际操作，并结合需求内容判断规则、异常与业务衔接是否合理；未核对不能显示成自动通过。停止预览不会额外阻断有效工程成果的确认。

完成受理与后续基线入口按原型成果表达；基线仍保留正式接受的代码版本。未知结果先查询原操作，不重复提交；已被后台接受的成果不因本机收整失败回退。设计稿中的接受与基线都是明确标记的模拟，不证明现有后台已经支持集合级受理。

### 2.6 关键状态

| 状态 | 交互要求 |
| --- | --- |
| 生成中／取消 | 展示原生会话实际状态；保留已产生代码与对话。 |
| 尚无可运行产物 | 显示空态与运行入口；可先查看工程，不强制选择一条需求。 |
| 工程检查失败 | 展示失败项和文件位置，可修复重试，不复用旧通过证据。 |
| 预览失败 | 展示原因与重试，不清空代码，不抹除独立工程检查事实。 |
| 源码已变化 | 标旧检查／旧预览，不把需求内容更新等同于源码已经改变。 |
| 多需求之间切换查看 | 保留同一原型、会话、工程和未保存编辑，不切换成单需求工作台。 |
| 提交未知／接受后收整失败 | 按原操作恢复，分别呈现接受事实与未完成收尾。 |

## 3. 协同后台职责

本文记录交互设计。根据设计稿开展的需求到原型技术设计、决策树和源码差距另见[原型技术设计](prototypes/technical-design.md)及[并行协作 ADR](../adr/0008-project-prototype-parallel-collaboration.md)。2026-10-26 两轮已明确：多人按协作事项独立分支并行集成，依赖仅提示，实现指令授权范围内代码写入，整体原型基线与需求状态分离；干净合并自动重检继续，冲突处理后用户重确认；允许草稿探索；需求确认后只提示进入原型，由用户发送实现指令。整份技术设计尚待整体确认；交互稿已补事项、队列与占用冲突的模拟，真实操作及后台并发仍未实现或验收。

当前尚未新增接口或表结构，未修改权限、Git 和基线实现。完整需求正文、源码、会话和工具日志不因集合展示而复制到协同后台。

当前产品原型任务及完成命令仍围绕单个需求实体组织；该实现粒度与本轮明确的项目原型视图存在差距。产品实施时应按多个需求共同构成原型的语义整合会话、工程、检查与成果受理，不能仅改按钮文案便声称后台已支持集合。现有单需求内部任务不能成为界面必须选择固定依据的理由，也不能把一个内部任务完成冒充整个原型已经完成。

正式受理应明确当前成果及其涉及的需求范围，保留代码版本与确认人、权限和幂等事实；这种成果追溯不等于开工前固定一条实现依据。具体协议和并发控制须随产品实施一起设计与验证，本稿不凭空假设已有集合接口。

## 4. 数据与文档格式

| 信息 | 来源与含义 |
| --- | --- |
| 需求集合 | 项目中与原型相关的多项需求，供查看和定位，不是锁定的单需求输入。 |
| 对话上下文 | 当前项目原型、实际读取的相关内容和用户本轮指令，可跨需求持续调整。 |
| 工程与文件 | 当前原型工程及其任务授权，包含多个需求的页面与共享内容。 |
| 页面目录 | 原型工程 `config/routes.json`。 |
| 检查／预览 | 当前源码、静态产物和受管进程的实际事实。 |
| 正式成果与基线 | 后台实际接受的成果及代码版本；界面不得推测接受结果。 |

工作区组织须服务同一项目原型的持续实现与预览；当前独立任务工作树是实现现状，不在本稿中冒称已经成为项目级共享工程。隔离、占用和受理的工程调整须保护各任务未提交成果，不引入兼容层或静默迁移。

交互稿文件：

- [原型交互工作台.html](../dseign/原型交互工作台.html)：深色 AI 工作台骨架和离线演示。
- [prototype-workbench.css](../dseign/prototype-workbench.css)：与 AI 交互稿一致的视觉与布局。

设计稿持续标识“交互设计稿／模拟数据”，不连接真实模型、Host、协同服务或 Git。代码是缩略展示样例，保存仅演示编辑、检查和预览状态，不执行源码编译；接受和基线也仅为本页模拟。

## 5. 验收标准

### 5.1 设计审阅

1. 工作台的深色主题、248px 项目侧栏、顶栏、状态栏、面板、消息、输入框和按钮与现有 AI 交互稿一致。
2. 首屏明确是项目原型，需求集合中可查看多项需求；不存在固定单需求标题、固定版本、实现依据或重新绑定入口。
3. 从不同需求定位订单、审批、供应商等页面，始终在同一原型与会话内，且不要求先选择或锁定实现依据。
4. 文件树展示多需求工程；预览／代码、文件标签、搜索、变更对比、编辑保存和未保存保护均可操作。
5. 运行、停止、重启、检查、失败恢复和源码变化导致旧证据失效可操作。
6. 业务样例的搜索筛选、必填／金额校验、保存失败与重试、只读订单、审批和供应商页面可操作。
7. 确认面板面向当前原型，跨需求核对与 AI 评审可选；问题仅入草稿；无固定需求绑定或预览必须运行的额外门禁。
8. 模拟接受结果明确标识为演示；不把一条内部需求完成显示成整个项目原型已经完成的实际事实。
9. 键盘、焦点、Escape、窄窗折叠和减少动态效果有相应处理；视觉、可读性及真实浏览器效果仍须独立核对。

### 5.2 产品验收边界

产品实现后须以当前版本完成真实桌面、多需求原生会话、工程文件、预览运行、作者核对、协同受理和基线结果的闭环，协同服务沿现有配置使用 `100.119.183.44`。覆盖跨需求操作、并发编辑、取消、检查与启动失败、未知提交及重启恢复。按[技术设计开发顺序](prototypes/technical-design.md#8-实施拆分与删除范围)推进，各工作包同时完成对应实现验证，不另设独立 POC 环节或开发前置条件；局部检查不代替最终真实桌面验收。
