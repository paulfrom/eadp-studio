# 阶段二：需求协同设计

依据：[领域语言](../../CONTEXT.md)、[阶段一场景设计](scenarios/01-scenarios.md)、[一致性对比 ADR](../adr/0003-user-directed-revision-consistency.md)、[通用场景 ADR](../adr/0004-builtin-general-scenario.md)。场景与需求统一采用「写入提议＋整篇写入」；AI 提问，用户明确回答后由 Host 校验执行。

## 1. 用户目标与业务规则

需求是**可独立描述、验证和交付的业务能力**，可以包含多页面、主流程和异常分支。需求从已确认普通场景细化，或由用户命名并选择普通场景／内置通用场景新建；所有需求沿用真实项目场景关系，自身独立整理、修订和确认。

成熟模式参考：[Azure Boards 关系类型](https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference)区分关联和前置依赖，[追溯链接](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/add-link)表达来源联系；[IBM 可疑追溯](https://www.ibm.com/docs/en/engineering-lifecycle-management-suite/test-management/7.1.0?topic=artifacts-suspect-traceability-in-engineering-test-management)将潜在影响交给用户判断。本设计采用关系追溯和独立对比快照模式；具体本地输入、非阻断及写入提议授权以用户决定为准。

| 业务范围 | 规则 |
| --- | --- |
| 需求边界 | 按独立业务能力拆分，不按页面、按钮或步骤机械拆分。 |
| 候选承接 | 带入标题、摘要、目标、范围、实际来源、相关规则与验收依据、待澄清项；不编造未读取依据。 |
| 来源追溯 | 普通来源保留固定确认版本及具体原文片段，可双向回看；不要求逐条手编场景规则编号。 |
| 场景与需求发生分歧 | 不规定场景或需求永久优先；AI 发现冲突，用户选择修改方向，不自动改关联文件。 |
| 修订与确认 | 各材料独立占用、修订和确认，取消整体冻结、强制同批及自动来源升版。 |
| 冲突及失败的作用 | 对比是独立非阻断能力，冲突、范围不足、失败、旧结果均不影响材料按自身条件确认或继续流程；不需要“带冲突确认”分支。 |
| 查找范围与触发 | 先查已有关系，再查项目本地潜在关联；手动发起，或场景／需求确认后自动发起一次。 |
| 对比输入与文件历史 | 同一当前 MD，历史由 Git 保存；自动和手动对比都只读本地实际文件，不读 Git 历史，不执行任何 Git 操作。 |
| 冲突留存与解决 | 每次对比只留当次结论和冲突摘要，后台不维护处理状态；解决在客户端完成，不改文件、不阻流程、不要求复比或文件确认。实际修改另走写入提议及独立修订。 |
| 模板与规则 | 需求模板独立项目共享，内置默认且支持上传；GWT 推荐，不是强制语法门禁。 |
| 身份与分类 | 后台分配稳定 REQ-0001，不手改、不回收；无需求分类、默认分类或分类兼容字段。 |
| 新建入口 | 手工先命名并选择场景，正文空白；AI 按模板提出写入提议，用户明确回答后才整篇写入。候选创建承接已选内容。 |
| 多轮与联合拆分 | 同一场景可多轮补拆，参考已有需求减少重复；可选多个已确认普通场景联合拆分，每候选仅绑定实际相关的所选子集，不覆盖、修改或自动合并旧需求。 |
| 内置通用场景 | 在既有项目场景中固定提供、默认可选，无须用户创建、编辑或确认；沿用真实场景身份和系统预置版本，不增加无场景类型，不把空来源解释成通用。 |

下述章节定义通用场景初始化、模板、冲突记录与命令契约。

## 2. 端到端用户路径

| 路径 | 固定输入 → Agent 输出 → 用户动作 → Host／后台事件 → 失败恢复 |
| --- | --- |
| 手工新建 | 用户命名并明确选择一个或多个有效场景；可直接选内置通用场景 → 无自动首稿 → 用户创建 → 后台幂等预留 UUID／REQ 编号、来源和设计占用，Host 创建空白正文 MD → 不明结果先查原操作，不重复领号；空来源明确拒绝。 |
| 普通场景拆分 | 一个或多个同项目已确认普通场景的固定版本、实际片段及已有关联需求 → 专属 Agent 提出候选和来源子集 → 用户逐条或多选采用 → Host 按候选逐个幂等创建需求并写入承接内容 → 未采用不创建；失败显示每条结果，原操作重试，不重建已成功项。 |
| 整理需求 | 当前 MD／hash、所选需求模板固定版本、实际已读资料 → 需求 Agent 提出结构化首稿或修改建议 → 用户以明确动作回答写入提议，或手工编辑 → Host 校验 expectedHash、模板绑定、依据、范围和身份后整篇写入当前草稿 → 正文 hash、模板固定引用、项目上下文或所选依据变化令写入提议作废，重读后重新提问；保存失败保留输入。 |
| 确认需求 | 当前材料、有效占用、阅读 hash、正式依据及固定场景来源 → 可选 AI 辅助评审 → 用户由可信 Host 确认 → 独立材料门禁、Git 固定候选及后台接受成功 → 显示固定版本；后台结果未知先核对原集成，不能显示已确认或重复创建。 |
| 独立修订 | 已确认材料及影响目录 → 可选修改建议 → 用户显式启动该材料修订并回答写入提议 → 只占用、整篇写入和确认该材料 → 关联材料仍可读取／独立操作，来源不自动升版。 |
| 一致性对比 | 关系目录与当前本机实际文件，同次读取字节和 hash → AI 输出当次结论、冲突摘要与潜在关联 → 用户查看 → Host 提交独立后台结果 → 失败、部分范围或提交失败如实显示，可独立重试，确认回执不等待。 |
| 冲突解决 | 查看当次冲突摘要 → 可选拟修改文件清单／建议 → 用户选择修改方向 → 实际修改须另获目标材料占用，回答写入提议后整篇写入并独立确认 → 下一轮对比重新检查是否一致，不继承上一轮冲突清单。 |

场景确认后先询问是否立即拆分，拒绝时仍保留稍后入口，不自动创建需求。补拆参考已有需求仅用于减少重复，不能将相似候选视为已覆盖或自动合并；不同场景中的真实冲突须保留为待澄清，不由模型裁决。通用说明只提供归属，不作为单场景或联合业务拆分输入，也不提供需求业务依据。

普通来源在采用时显示明确固定版本。候选记录每个来源的项目、场景 ID、版本、确认记录及文件 hash；采用前核对该批来源和模板上下文。只有用户改变所选来源集合／固定引用、候选实际输入不符或模板上下文变化时，才将该候选标为过期，重读并生成，不静默替换版本。另有场景新版本并不改变已选不可变旧版本；后台仍合法接受的历史固定来源可继续使用，不因新版本出现而自动过期或升版。已创建需求的旧来源引用保持不变；后续显式更换来源属于该需求修订。

## 3. 桌面工作台与自身确认

| 位置 | 设计与取数边界 |
| --- | --- |
| 需求目录 | 复用场景目录范式：稳定编号、标题、摘要、来源场景芯片、确认状态、创建人／编辑人及修订提示。提供标题／编号搜索、确认状态 Tab、来源场景筛选、排序和分页；移除分类侧栏与维护入口。 |
| 指标 | 规则条数和待澄清项从实际可读需求材料按统一解析口径统计，区分本地草稿与已确认版；无法可靠识别时显示“未统计”，不数 GWT 关键词或用模型置信度凑数。一致性冲突数量只取该材料最近一次对比结论，未读取／失败显示未知；历史对比次数不冒充独立业务问题数量，不宣称项目完全一致。 |
| 双栏工作区 | 左侧需求专属 Agent 会话，右侧同一当前 Markdown 的预览／源码编辑、导出、折叠与恢复；复用阶段一写入提议协议、hash 跟踪、资料读取状态及本地会话。新会话读取当前材料、当前绑定模板和所选资料，不整段继承旧聊天。 |
| 来源面板 | 普通场景展示固定确认版本及原文片段定位；通用场景展示“系统内置”和真实预置版本。可从场景查看关联需求，从需求回看正式来源；潜在关联另列，不能冒充正式关系。 |
| 冲突面板 | 在项目列表及涉及材料详情提供入口，显示最近一次对比的时间、范围完整性、冲突摘要及涉及材料；历史对比逐次留档，冲突没有处理状态，不出现“已处理”“已忽略”。面板不改称“材料已一致”。 |
| 确认状态条 | 分列业务内容、资料与引用、版本与占用、可选模板结构检查。对比结论／冲突独立展示，不进入确认门禁。原型仿真、原型验证、覆盖率属于后续阶段，不能展示虚构通过值。 |

普通 AI 始终 propose-only；写入提议与材料确认分别表达。AI 只提问是否把本轮结论写入目标文件，写入由 Host 校验 expectedHash、模板绑定与依据后整篇执行；AI 不自行判断已获授权，不写文件，不确认材料。自然语言确认与按钮确认都必须由可信 Host 绑定真实用户动作、最终阅读 hash 和占用令牌，不允许 Agent 自行确认。内容变化后旧检查与旧写入提议作废；外部修改和未保存输入冲突时保留双方供用户解决，不静默覆盖。

需求自身确认检查核心规则明确、验收可判断、正式业务依据真实、核心待澄清项已解决、来源有效且同项目、身份／路径／hash／占用／固定 Git 内容一致。非阻断问题保留限制。模板章节和 GWT 不是业务语义的替代品；默认关闭的本机结构检查沿用阶段一约定。独立一致性冲突不得自动写成 blocking 待澄清项。

前置需求与来源场景分别维护：前者表示生产顺序，后者表示业务来源。关系写入沿用 validatePrerequisites：同项目、另一有效需求、无重复、无自引用和环，绑定明确版本。前置需求尚未生产完成不阻止当前需求文档整理或确认；只在原型认领及完成校验时要求绑定版本已有后台接受的完成证据，相关证据变化使生产输入失效。

## 4. 文件、模板和后台数据职责

场景与需求各维护一个当前 MD，编辑及修订更新同一文件，历史由既有 Git 流程保存，不生成 v1／v2 业务副本。需求文件路径为 `需求/<名称>.md`，同项目重名依次追加 `-2`、`-3`；标题改写后文件随之改名，旧路径不再保留副本；唯一 `eadp-metadata` 块承载技术身份、来源和业务校验信息，不增加 frontmatter 或第二套身份格式。REQ 编号只作后台稳定展示标识，不作为文件名或版本号；分配按项目和资产类型原子递增，同一 operationId 重试复用 UUID／编号，失败可留空号，编号不回收。

需求模板独立于场景模板，沿用项目 `.template/`、Git 清单及受控配置发布模式。工程方案在 `project.assets.json` 分别维护场景／需求模板目录和默认项；需求模板使用独立 ID／路径，不覆盖场景默认模板。后台不保存模板正文、清单或默认项，只记录材料绑定的固定模板引用；项目写权限用户发布，读权限用户查看。默认更新只影响新材料，旧材料显式切换且不改正文，旧上下文写入提议过期作废。手工新建正文空白；模板引导 AI 建议，从候选新建承接已选内容。Host 初始化流程使用[默认需求模板](templates/default-requirement.md)，场景与需求使用独立模板 ID 和路径。

| 权威位置 | 保存内容 | 不承担的职责 |
| --- | --- | --- |
| Git 固定材料及依据文件 | 需求正文、质量项、待澄清项、正式依据及片段定位、来源版本、模板固定引用、关联文件及 hash；保留各自历史。 | 不保存冲突处理状态、会话或原始模型结果。 |
| 协同后台 | UUID／编号、标题摘要及必要目录投影、权限／占用／修订、正式关系和固定版本引用、接受事实、幂等操作；独立对比与冲突摘要事实。 | 不重复保存材料、完整 metadata、完整 diff、证据文件副本或完整业务片段。 |
| 本机过程数据 | 会话、写入提议、资料实际读取状态、当前草稿、必要重试操作；对比使用的内容只在本次内存中处理。 | 不表示跨机可见，不取代后台接受或 Git 历史。 |

普通来源保留实际固定版本及原文片段，片段由该固定文件与可核对的章节／范围定位，不能链接可变最新正文冒充历史。需求中的来源引用与后台正式关系须一致；场景新版本、打开材料、刷新状态或查看对比结论均不得自动升级来源。

通用场景按 [ADR-0004](../adr/0004-builtin-general-scenario.md)复用项目初始化：后台幂等预留真实身份；Host 用[固定只读说明](templates/general-scenario.md)及受控身份生成实际 MD，纳入初始化提交；后台核验真实固定文件后，以短事务接受系统预置版本和项目就绪事实。接受途径与普通用户确认互斥，不伪造阅读 hash、确认人、普通集成或业务依据；不是 Git／数据库跨系统原子事务。响应未知核对原初始化事实，后续认可头变化不重复预置。固定读取按后台持久接受途径选严格契约，不能在普通解析失败后 fallback。界面和 Host／后台均禁止普通修改；不获得普通业务场景复用资格。不新增旧项目懒补、migration 或兼容层。

## 5. 独立一致性对比的工程契约

### 5.1 输入、能力和触发

1. 手动入口接受当前项目和目标材料；确认后自动入口接受本次后台已接受的确认记录。可信 Host 在确认成功回执后独立调度，同一确认事件只启动一次；排队或运行失败不改变确认结果。用户主动重试是新的对比记录，不覆盖旧结果或继承旧冲突清单。
2. 查询专用关系目录，仅从后台关系表及必要协同控制字段取得正式场景来源、关联需求、前置关系与当前占用提示；先覆盖已有关系，再在当前项目 `场景/`、`需求/` 中受控查找潜在关联。不通过通用状态刷新、固定版本加载器或其他会间接读取 Git／排队同步的路径取上下文；后台目录查询也不加载固定材料正文。
3. 输入范围限本次选择的项目本地工作区。自身正在编辑时使用该任务当前文件，其他材料只读该工作区实际存在的文件；不遍历其他成员私有任务目录，不跨工作树搜索补齐，不读上游缓存或远程内容。关系目录不可用或候选材料缺失时标记范围不足，不能宣称完整检查。
4. 使用受控路径解析与普通文件校验，拒绝绝对路径、目录穿越和符号链接越界。缺失、不可读、编码／身份无效、超过读取边界分别处理，不生成文件、不复制材料、不自动补齐。模型上下文截断须标记范围不足，不静默截断后宣称全部检查。
5. 每个输入用同一次受控读取的字节计算 SHA-256，并由同一字节解码后交给模型；不 hash 后二次读模型输入。项目相对路径、材料 ID、hash、实际读取范围及本地内容状态由 Host 在本次任务内自证，不上传后台；不记录本机绝对路径。输入身份无效的文件不作为正式材料输入。
6. 根据已有本地任务状态及实际读取内容标注“本地草稿／本机当前文件／状态无法核对”，不调用 Git status 或固定版本读取判断草稿。后台无法判断其他电脑私有内容，也不能将本机 hash 视为全项目最新版本证明。
7. 对比会话只暴露项目范围受控本地读取和关系目录能力，不暴露终端、Git、文件写入、拉取／同步、材料确认或自动修复工具；不能仅以提示词限制权限。Host 与后台都不新增独立模型网关，模型能力仍由 DSH 提供，后台不新增 AI 端点。

比较使用“当前本机实际内容”，来源追溯使用“固定接受版本”，二者目的不同。对比不执行 fetch、pull、checkout、show、status、提交或任何其他 Git 操作，也不调用会间接执行这些操作的路径。材料初始化、模板发布和材料自身确认的 Git 流程不属于对比职责，不得借自动触发把它们并入对比任务。

### 5.2 后台记录与结论

| 记录 | 必要结构与约束 |
| --- | --- |
| 对比记录 | comparisonId、项目／发起人／时间、触发类型、目标材料、可选确认事件 ID、operationId；执行结果 completed／failed／cancelled，覆盖范围 complete／partial；有限失败码、摘要及冲突数量。运行中属于本机任务状态，提交成功前不能显示“已项目共享”。 |
| 冲突摘要 | conflictId、comparisonId、序号、有限冲突摘要、关系类型（正式／潜在）、涉及材料。随对比一次写入，之后不可变；没有处理状态、逐条提醒、修改方向或处理历史。 |
| 结论与提醒 | 不单独存表：通过＝completed 且 complete 且冲突为零；范围不足＝partial；失败／取消分别表达。提醒取目标材料最近一次对比的结论，只落在该材料，不改写材料或任务状态。 |

这些记录是客户端对本次本机结论的观察，后台只校验契约、权限、幂等和引用归属，不能凭记录验证本地文件、AI 结论或其他成员私有草稿的新旧。后台使用专用结构化白名单 Schema，禁止任意 JSON 和额外属性。协议上限沿用现有 `IdSchema` 的尺度：ID 与操作键最长 100 字符，冲突摘要、失败摘要各最长 500 字符；每次对比的冲突最多 100 条，每条冲突的涉及材料最多 100 个，序号为 1—100；SHA-256 为 64 位小写十六进制。越限拒绝，不悄悄截断；Host 读取或上下文边界导致未检查完时明确显示 partial，不能靠拆传多份结果宣称整项目已完整检查。仅接收当次结论、有限摘要与涉及材料，拒绝完整材料、完整 diff、原始模型响应、会话、提示词、工具日志、绝对路径及文件副本；不能依靠通用按字段名删减代替输入约束。原文业务片段仍在固定材料／本机查看，不以“冲突证据”名义上传整段正文。

completed 且 complete 且冲突为零，只能表达“本次已读范围未发现冲突”；partial 必须显示“范围不足”，failed／cancelled 不能显示一致。冲突摘要存在只表示本次发现分歧，不证明文件已改或业务已一致。每次对比保留独立记录；新对比不继承旧冲突清单，也不由新一轮零结果自动证明历史冲突已解决。

提醒沿用项目内界面：结论由最近一次对比派生，项目列表和涉及材料详情显示“最近一次检查不通过”或“范围不足”，用户不能手工清除标记；不新增外发消息、定时通知或强制弹窗。项目读权限可查询共享结果，项目写权限可提交结果；服务端核验实际权限，不以客户端声明的身份或模型输出决定。无权用户不得借对比接口读取项目目录。

### 5.3 命令、并发和失败恢复

以下职责按共享 contracts、Host 命令及专用后台路由实施，沿用现有项目权限、幂等机制与占用设计，不另建通用工作流框架。

| 命令／接口 | 输入与结果 | 并发及恢复边界 |
| --- | --- | --- |
| createMaterial／POST entities | 名称、普通／通用场景固定来源、所选需求模板、operationId；返回需求身份／编号。移除需求 categoryId。 | 后台核验同项目真实已接受来源及模板，重复原操作复用编号；Host 写失败恢复原材料，不新建替代资产。 |
| splitScenario／splitRequirements／selectCandidate | 多个普通场景固定输入；候选包含标题、摘要、目标范围、实际来源子集／片段、规则验收、待澄清及输入 hash；采用传候选 ID 与 expectedInputHash；候选 ID 同时作为稳定创建操作键。 | 不采用未选场景、未读取资料或所选固定输入或模板上下文已变化的旧批次；多个候选分别幂等创建，不改旧需求。 |
| 保存／整篇写入／模板绑定 | 当前材料 ID、有效占用、expectedHash、写入提议 ID 或模板固定引用。 | 原文不匹配、写入提议已作废、hash／模板／占用变化拒绝写入，重读后重新提问；同一提议重复回答只生效一次；仅操作该材料。 |
| PUT entities/:id/relations | 当前需求占用、expectedRevision、scenarioIds／固定来源及前置版本。 | 正式关系与固定来源原子更新，校验前置 DAG；源场景正在独立修订不构成整体冻结，仍可绑定明确已接受版本。 |
| confirmMaterial／integrations | 当前材料固定引用、阅读 hash、独立业务质量与占用依据。 | 各自固定候选和后台接受；删除 scenario-batch、冻结集合及关联自动升版。结果未知查询原集成，不重复确认；对比不进入事务。 |
| GET entities/:id/consistency-context | 项目内关系及必要目录投影，不含材料正文。 | 纯后台查询，不经 Git 内容加载、状态同步或文件补取。 |
| compareConsistency（Host） | 项目／目标、触发来源及当前本地工作区，返回本次实际范围和结构化结果。 | 独立只读任务；输入变化标为过期，不修改输入、不触发 Git、不重跑材料确认。 |
| POST consistency-comparisons | operationId 及上述有限结果，后台原子保存结论与冲突摘要。 | 响应未知先查原操作；未共享显示待同步，可重传同一结构化结果，不能因网络恢复再次执行模型或读取 Git。 |
| GET consistency-comparisons | 项目、材料、结果筛选及分页，附带该次冲突摘要。 | 独立查询；不读取文件或推断其他电脑内容。默认展示最新对比及历史入口，历史对比不得消失。 |

运行期间输入变更：结果仍准确指向本次实际读取字节，Host 根据已知文件变更标为“相对本机内容已过期”。再次查看可用受控本地读取核对 hash，无法读取则显示无法核对；不调用 Git，不把过期升级为确认门禁。用户仍可基于历史冲突决定是否修改，无须先复比；若选择实际修改，写入提议必须针对目标当前 hash 重新生成，用户明确回答后才整篇写入。

比较模型失败、用户取消、权限失效、读取失败或后端提交失败各自显示真实状态；保留可重试的有限操作，不留持久材料副本。重新执行模型生成新的 comparisonId；同一已生成结果的网络重传沿用原 operationId。结果未知先核对后台原操作，不以重跑替代核对。提交结果不要求当前材料有占用或已确认；修改文件则必须重新核验目标材料的权限、占用和版本。

## 6. 验收标准

以下用例分别验证契约、Host 执行和产品交互，保留与实际行为对应的自动检查或界面证据。

| ID | 操作与输入 | 必须观察到的结果 |
| --- | --- | --- |
| R01 | 手工命名并选普通场景新建需求。 | 后台分配稳定 UUID／REQ 编号，正文空白，真实固定来源有效，无分类输入；重试同操作不重建不重编号。 |
| R02 | 改名、修订、创建失败后再建。 | 原编号不变且不回收；允许空号，文件路径随名称变化，重名追加 `-2`、`-3`。 |
| R03 | 不新增场景，直接选通用场景新建。 | 默认可选且有真实预置文件／版本，显示系统内置；无需编辑或人工确认通用场景。 |
| R04 | 空来源、跨项目、无效版本；伪造系统预置标志或改通用正文。 | 各入口明确拒绝，不替换成通用，不降级普通解析；普通需求业务质量条件不放宽。 |
| R05 | 新项目初始化响应丢失后重试；随后认可头推进。 | 核对原操作及预置接受事实，不重复预置，不伪造用户阅读／确认凭据。 |
| R06 | 对多页面业务能力拆分，用户暂不采用。 | 按独立能力给候选，不按页面机械拆；未采用不创建需求，稍后仍能拆分。 |
| R07 | 同场景补拆及多场景联合拆分，采用部分候选。 | 参考已有需求，每候选只带实际读取的所选来源子集及片段，完整内容写入新草稿，旧需求不覆盖／合并。 |
| R08 | 候选生成后来源／模板上下文变化；重复采用请求。 | 过期候选不能静默换依据写入；重新生成后可采用；原成功操作不重复创建。 |
| R09 | AI 提出首稿／修改后用户未回答或回答否，或 hash 已变仍消费旧写入提议。 | 未回答或回答否不写文件；旧 hash 的写入提议作废并拒绝写入，重新提问后才整篇写入；同一提议重复回答只生效一次；纯手工编辑仍可确认。 |
| R10 | 需求模板上传／发布、改默认、显式切换。 | 独立项目共享，正文不自动改，旧绑定不自动切换；旧写入提议过期作废，场景模板不被覆盖。 |
| R11 | 同义标题或非 GWT 正文确认；核心规则／验收／业务依据缺失。 | 不按 GWT 语法拒绝；缺真实业务条件则拒绝确认，不能以通用说明冒充依据。 |
| R12 | 未完成前置需求下确认本文档，再认领原型；构造自引用、重复和环。 | 文档可独立确认；原型按固定前置版本完成证据阻断；非法关系在关系写入时拒绝。 |
| R13 | 场景修订与关联需求独立修订／确认。 | 只占用当前材料，无整体冻结或同批要求；打开／刷新不改关联文件，不自动升级来源。 |
| R14 | 材料确认成功，立即令模型失败／超时。 | 成功确认回执不等待比较；比较失败单列，可继续业务，无冲突门禁。 |
| R15 | 手动及自动对比装设 Git、终端、同步、写入和确认调用探针。 | 所有上述能力零调用；经通用 state／固定加载器间接 Git 或补取也判失败。 |
| R16 | 对比受控读取期间修改文件，核对模型实际输入与本机记录 hash。 | 同次读取字节一致，结果绑定实际输入；后续变化显示过期，不把 hash 当全项目最新证明。 |
| R17 | 本地缺失、不可读、非法身份、上下文超限或关系目录查询失败。 | 结论为范围不足或失败并说明原因，无自动补文件或远程读取，不显示完整一致，不阻确认。 |
| R18 | 路径穿越、绝对路径、符号链接越界，或其他成员私有草稿不在本工作区。 | 拒绝越界读取；只处理本机实际可见输入，跨机状态显示无法核对，不搜索私有任务补齐。 |
| R19 | 正式关系外发现潜在关联。 | 先展示正式关系，再展示潜在关系及依据；后台正式来源／前置关系不被自动修改。 |
| R20 | 对比完成、范围完整／部分、零冲突、失败、取消分别展示。 | 各状态不同，零冲突只限本次已读范围；失败或部分不伪装一致，不生成材料 blocking 问题。 |
| R21 | 尝试对冲突执行忽略、登记已处理、设置逐条提醒，或按 revision 更新冲突。 | 后台没有这些字段与接口，请求被拒绝；提醒只由最近一次对比结论派生，不显示业务已一致。 |
| R22 | 查看冲突摘要后选择“以需求修改场景”或反向修改。 | 先出文件清单与建议，用户回答写入提议后按目标当前 hash／独立占用整篇写入，各材料独立确认；选方向本身不修改／确认。 |
| R23 | 两人同时提交对比结果或重传同一 operationId，或由无写权限用户提交。 | 幂等键保证同一操作只生效一次，后提交者另建对比记录不覆盖前者；无权限拒绝，材料 revision／占用不参与对比并发。 |
| R24 | 提交完整材料、diff、原始模型／会话、绝对路径、任意字段、超限数组／摘要。 | 专用 Schema 拒绝，审计／幂等／错误日志不绕道保存这些载荷。 |
| R25 | 结果提交响应未知后重传；主动重比。 | 先查原操作，重传不重复结果或审计；重比建独立记录，不继承旧冲突清单、不自动证明旧冲突已解决。 |
| R26 | 查询需求目录／双方详情，正文不可读或对比结果未同步。 | 编号、来源、确认状态可核对；规则／待澄清／冲突各自取数，不可得显示未知，不用历史比较条数假装问题总数。 |
