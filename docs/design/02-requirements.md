# 阶段二：需求协同设计（访谈稿）

状态：阶段二部分决策已确认，包括需求拆分粒度、多轮及多场景联合拆分、候选承接、在现有项目场景中增加内置“通用场景”、普通场景来源的固定版本追溯、一致性对比的本地输入与非阻断边界、项目共享需求模板、稳定业务编号及取消分类。通用场景的正文和初始化／确认方式、模板用于新草稿的方式，以及差异权限、并发、提醒等细节仍待讨论。本文不表示完整设计已经批准，也不表示功能已经实现或验收。

依据：[工作里程碑](../milestones.md)、[领域语言](../../CONTEXT.md)、[阶段一场景设计](scenarios/01-scenarios.md)及[阶段一实施记录](scenarios/implementation.md)。本文只细化需求与场景的衔接及里程碑已有的阶段二范围。

## 用户目标

需求是可独立描述、验证和交付的业务单元，可以从已确认场景细化，也可以直接关联项目内置的“通用场景”新建，无须用户先新增场景。“通用场景”是在现有项目场景体系中增加的内置场景，不另建无场景来源类型；需求仍沿用场景关联。普通场景来源保留固定确认版本，通用场景的正文及初始化／确认方式尚待明确。需求自身须整理并确认，不等同于单条规则、页面或 AI 生成结果。

**已确认**

- 需求按可独立描述、验证和交付的业务能力拆分。一个需求可以覆盖多页面的主流程和异常，不按页面数量机械拆分。
- 从一个已确认场景发起拆分时，AI 先给出候选；同一场景可多轮补拆，每轮参考已有需求以避免重复。用户选择候选后才创建新需求草稿；不覆盖或修改已有需求。拒绝立即拆分时不自动创建需求，仍可稍后发起。候选和新建草稿都不代表需求已经确认。
- 在现有项目场景中增加内置“通用场景”，新建需求时可以直接关联它，无须用户自己新增场景；不新增独立的无场景来源类型。通用场景的正文、是否可编辑及初始化／确认方式仍待明确。
- 多个已确认场景可联合发起拆分；每个候选实际引用其中相关的场景子集，不强迫采用全部所选场景，也不自动合并已有需求。
- 采用候选时，需求草稿承接候选标题、摘要、目标、范围、实际来源、相关规则与验收依据、待澄清项。候选含具体场景来源时，保留其固定确认版本及相关原文片段。依据只带实际依据内容，不把 AI 推断当作依据。
- 需求不设分类；新建需求、采用候选、编辑、筛选、需求元数据及后台契约都不引入分类维度。
- 规则推荐用“前提条件、触发、预期结果”表达；确认依据是规则明确且验收结果可判断，不要求固定的 Given/When/Then 语法格式。
- 具体场景来源追溯到固定场景版本及具体原文片段。场景规则不要求用户逐条手工编号。
- 发起一致性对比时，先检查已有场景与需求关系，再搜索当前项目的本地业务材料以发现潜在关联；向用户展示可核对的依据，不自动修改正式关联。
- 场景与需求各自独立修订、独立确认，不因关联关系整体冻结，也不强制同批确认；修订只占用当前正在编辑的材料。修改场景或需求不会自动改写另一份关联材料。
- 场景或需求确认后自动发起一次一致性对比，用户也可手动发起。无论触发方式，对比只读取当前项目中实际存在的本地场景和需求文件当前内容，不读取 Git 确认版本或历史作为输入，不执行 Git 操作、不下载或切换 Git 历史、不提交文件。材料自身原有 Git 确认流程独立保留。
- 根据当前本地任务状态和实际文件内容识别尚未确认的编辑，并标明为本地草稿；不读取他人未共享的草稿。文件缺失或不可读时标记输入缺失或比较范围不足，不从 Git 自动补齐。对比失败须提示并允许重试；差异、缺失或失败均不阻止当前材料确认或后续流程。
- 对比结果及其处理状态独立于材料内容。用户可登记处理结果、忽略或提醒差异；这些动作只更新协同后台的差异记录，不要求重新对比或先确认文件。提醒会记录后台标记并在界面提示，具体交互待后续细化。用户选择修改相关材料时，进入 AI 提出修改建议、用户采纳、再修订材料的流程；修改后的材料各自独立确认。
- 比较失败不代表一致，也不形成材料待澄清项或确认门禁。比较结果是否完整，不改变当前材料及后续业务流程的可继续性。
- 需求选用普通场景来源时，绑定所选场景的固定确认版本；场景产生新版本不会自动迁移该需求的来源引用。内置通用场景也沿用场景关联，其初始内容及可用方式待明确，不伪造确认版本。

需求沿用现有项目场景关联；普通场景可绑定一个或多个同项目已确认版本，并保留固定版本追溯。内置通用场景使需求不必以用户先新增场景为前提，其正文及初始化／确认规则待明确；不把任意空来源或无效引用自动解释为通用。需求内容与自身确认版本保持独立。

## 桌面端职责

阶段二沿用阶段一的材料整理与 Agent 会话范式，并采用专属需求 Agent。具体交互仍待完整设计确认。

**已确认的交互结果**

- 现有项目场景中提供内置“通用场景”，新建需求可直接关联，无需用户自己新增场景。普通场景可发起多轮补拆，每轮参考已有需求避免重复，只有用户选择候选时才创建新需求，不覆盖或修改已有需求。
- 用户可选择多个已确认场景联合拆分。候选展示其实际依赖的场景子集，不要求包含全部所选场景，也不自动合并已有需求。创建需求草稿时，承接该候选的实际来源；具体场景来源保留其固定版本和原文片段。
- 需求拥有自己的 Markdown 工作区和确认过程。需求确认不会自动修改关联场景；场景确认也不会自动修改关联需求。界面使用后台分配的项目内业务编号，如 `REQ-0001`；改名或修订不改变编号，用户不能手动修改编号。
- 提供独立于场景模板的项目级共享需求 Markdown 模板管理，沿用场景模板管理方式，包含内置默认模板并支持上传模板。默认模板包含目标、范围、流程、字段、业务规则、异常、验收条件、来源和待澄清项。
- 需求新建、采用候选、编辑和筛选界面均不显示或使用需求分类。
- 场景或需求确认后自动发起一次一致性对比，并提供手动入口。比较只读取当前项目中实际存在的本地场景和需求文件当前内容；根据当前本地任务状态和实际文件内容识别尚未确认的编辑，并标明为本地草稿，不读取他人未共享的草稿。缺失或不可读文件标记为输入缺失或比较范围不足，不自动从 Git 补齐。
- 一致性对比不执行 Git 操作（包括 fetch、pull、checkout、show），不下载或切换 Git 历史，不提交文件，也不使用 Git 确认版本或历史作为比较输入。材料自身原有 Git 确认流程独立保留。记录每次比较实际输入文件的项目相对路径和内容 hash，以便说明比较依据；不记录本机绝对路径，不复制材料文件，也不把比较报告作为流程门禁。
- 展示差异及处理状态；待处理差异不得显示为已一致。比较失败须明确提示并提供重试；差异、输入缺失或比较失败均不阻止当前材料确认或其他流程，材料自身仍须满足其独立业务确认条件。
- “登记处理结果”只更新协同后台的差异记录；“忽略”和“提醒”也只操作该记录，不强制重新比较或确认文件后才登记处理。提醒记录后台标记并在界面提示，具体交互待后续细化。用户选择“修改相关材料”时，先由 AI 提出修改建议，再由用户采纳并进入材料修订；采纳前不写入，修改后的材料仍独立确认。

里程碑提出的需求列表、场景关联信息、指标与筛选项，以及需求文档面板和专属会话，作为阶段二设计范围待具体化；本文不预设界面布局或操作细节。

## 协同后台职责

阶段二须承接需求实体及其与项目场景的关系，并在现有项目场景体系内提供内置“通用场景”。普通场景来源固定到一个或多个本项目已确认版本，并可从需求侧及场景侧核对；需求确认时校验普通来源有效、同项目且版本固定。通用场景的正文、初始化及确认方式待明确，不新增无场景来源分支，也不伪造其确认版本。需求自身确认后形成自己的固定材料版本。后端按需求资产类型在项目内分配稳定业务编号，如 `REQ-0001`；改名或修订不改变编号，不允许手动修改或回收。UUID 继续作为资产技术身份。

需求模板独立于场景模板，供项目成员共享；模板管理沿用场景模板管理方式，项目内置默认模板并允许上传。需求相关的后台实体、创建及候选采用契约、编辑和筛选契约不包含分类字段或默认分类。

需求前置关系与环检测沿用里程碑中已有的 `validatePrerequisites` 约束方向，具体业务规则和接口细节待完整设计确认。一致性对比由桌面 Host 调用 DSH 模型能力完成，协同后台不新增 AI 端点。比较读取当前项目实际存在的本地场景和需求文件当前内容，不读取 Git 确认版本或历史，不执行 Git 操作、不下载或切换 Git 历史、不提交文件；材料自身原有 Git 确认流程不属于比较。根据当前本地任务状态和实际文件内容识别未确认编辑并标记为本地草稿，不读取他人未共享的草稿；文件缺失或不可读时记录输入缺失或比较范围不足，不自动从 Git 补齐。每次比较记录实际输入文件的项目相对路径和内容 hash，不记录本机绝对路径，不复制材料文件或设置报告门禁。差异或对比失败不构成确认或后续流程的门禁；修改相关材料须经 AI 提议和用户采纳后才进入修订。

场景与需求不实施整体关联冻结或强制同批确认。每项材料独立占用、修订和确认，当前占用只覆盖正在编辑的材料。差异不改变任一材料文件，可独立忽略、处理或提醒，不影响材料确认及后续流程；待处理差异持续作为独立状态呈现，不表示材料内容一致。材料确认只检查其自身业务条件，不依赖差异状态。差异列表及处理结果保存在协同后台，不写入材料 Markdown。

## 数据与文档格式

场景和需求各自维护一个当前 Markdown 文件；编辑更新同一文件，历史版本由 Git 保存，不为 v1、v2 等修订另建副本文件。材料自身的 Git 确认与版本历史按既有流程维护；一致性对比只读取本地文件当前内容，不把 Git 固定版本或历史作为输入，也不执行 Git 操作或提交文件。

需求模板为独立的项目级共享 Markdown 模板，管理方式沿用场景模板管理，提供内置默认模板并支持上传。默认模板包含目标、范围、流程、字段、业务规则、异常、验收条件、来源和待澄清项。[默认需求模板样稿](templates/default-requirement.md)是设计文档，尚未装入运行时；是否自动写入新建草稿及其具体应用时机尚未决定。

规则推荐以“前提条件、触发、预期结果”表达；不强制使用特定 GWT 语法。确认时检查业务规则是否明确、验收是否可由用户判断，不因格式不符而拒绝确认。需求不使用分类字段或分类筛选。

需求沿用唯一的 `eadp-metadata` 块表达 UUID 技术身份和来源；文件路径为 `需求/<资产ID>.md`，名称不决定路径。项目内业务编号由后台按需求资产类型稳定分配，如 `REQ-0001`；改名或修订不改变编号，编号不可手动修改或回收。材料不增加 YAML frontmatter 或第二套身份／来源格式。

每份需求材料及其来源关系需要表达以下已确认信息：

- 需求标题、摘要、目标和范围；
- 如有具体场景来源，记录一个或多个来源场景的固定版本；
- 如有具体场景来源，记录相关规则、验收依据及其固定版本内的具体原文片段；
- 当前待澄清项；
- 需求自身内容和确认版本。

从候选创建需求草稿时，承接候选中实际读取的依据内容及来源，不扩大为未读取资料或未确认场景；有具体场景来源时，绑定所选场景的固定确认引用，后续场景版本不会自动替换该来源。原文片段是追溯依据，不要求转成用户维护的规则编号。阶段一对“确认状态”“任务状态”“复用资格”的区分，以及材料固定版本与原文权威来源的规则继续适用。

一致性对比及修改建议由桌面 Host 调用 DSH 模型能力完成，协同后台不新增 AI 端点。原子修改范围限于当前材料，不将关联材料合并为一个写入或确认事务。协同后台保存差异列表及处理结果；差异记录与材料文件和 Git 历史分开。每次比较记录实际输入文件的项目相对路径和内容 hash，不记录本机绝对路径，不保存文件副本或要求比较报告才能继续流程。“登记处理结果”、忽略和提醒只更新后台差异记录；提醒另在界面提示，具体交互待后续细化；修改相关材料则进入 AI 提议、用户采纳及修订流程。

## 验收标准

### 已确认范围的验收判据

- 现有项目场景中包含内置“通用场景”，用户新建需求可直接关联它，无须自己新增场景；沿用场景关联，不另建无场景来源类型。其正文及初始可用规则随后续决策补齐，不凭空生成确认版本。
- 同一已确认场景可多轮补拆，每轮参考已有需求避免重复；多个已确认场景可联合拆分，每个候选只需引用实际相关的所选场景子集。只有用户选择候选时才创建新需求，不覆盖、修改或自动合并已有需求。
- 需求可以覆盖多页面主流程和异常；拆分边界按可独立描述、验证和交付的业务能力判断，而不是按页面数量判断。
- 普通场景作为需求来源时，记录同项目已确认场景的固定版本并可定位到原文片段；直接关联通用场景的需求仍使用项目场景关系，其初始内容及可用规则待明确。
- 需求草稿只承接实际读取且支持所采用候选的依据，不以未读取资料或 AI 推断补全。
- 需求规则推荐使用前提条件、触发和预期结果表达；不强制固定 GWT 语法，确认以规则明确且验收结果可判断为准。
- 项目有独立共享的需求 Markdown 模板管理，包含内置默认模板并支持上传；默认模板包括目标、范围、流程、字段、业务规则、异常、验收条件、来源和待澄清项。默认需求模板样稿尚未装入运行时。
- 需求新建、采用候选、编辑、筛选、元数据和后台契约均不包含分类维度，不设置默认分类或兼容字段。

- 默认需求模板和上传模板均按项目共享管理；默认内容包括目标、范围、流程、字段、业务规则、异常、验收条件、来源和待澄清项。参见[默认需求模板样稿](templates/default-requirement.md)，该样稿尚未装入运行时。新建草稿是否自动写入模板内容尚未确定。
- 场景或需求确认后自动发起一致性对比，并提供手动入口。对比只读取当前项目实际存在的本地场景和需求文件当前内容，不读取 Git 确认版本或历史，不执行 Git 操作、不下载或切换 Git 历史、不提交文件；材料自身原有 Git 确认流程独立保留。
- 根据当前本地任务状态和实际文件内容识别尚未确认的本地编辑并标记为草稿，不读取他人未共享的草稿；缺失或不可读的文件标记为输入缺失或比较范围不足，不从 Git 自动补齐。失败明确提示并可重试；差异、缺失或失败都不阻止材料确认或后续流程。
- 每次比较记录实际输入文件的项目相对路径和内容 hash，不记录本机绝对路径、不复制文件、不要求比较报告作为流程门禁。差异列表及处理结果保存在协同后台，与材料文件分开；登记处理结果和忽略只更新后台记录，提醒更新后台标记并在界面提示，不强制重比或确认文件。选择修改相关材料后，AI 先提出建议，用户采纳后再修订草稿，修改后的材料独立确认。
- 各材料独立占用、修订和确认；关联关系不触发整体冻结或强制同批确认。
