# 下一阶段目标提示词：无 embedding 查找与需求采用闭环

> 用法：把本文件全文交给下一阶段编码 Agent。本任务替代原 V0.3 的“阶段三：向量混合”，不是要求重做阶段一／二。方案依据为 README V0.4（2026-11-09）。

## 任务与完成目标

在当前工作区已有的本地知识能力上，完成“不同说法查找 → 自动带入真实参考 → 用户选择作为依据 → 需求提案审阅 → 保存 → 更新／删除资料后仍能回读”的真实桌面闭环。

正式不用 embedding。使用结构切片、中文词项／精确通道、有界查询扩展和候选融合；缺少 embedding 不是阻塞、异常或降级。不要继续 S4，也不要等待上游提供 embedding。

## 必须遵守的边界

- 主 Agent 负责拆分、关键判断、整合与验收；边界清晰的执行委派 subagent，明确文件所有权和共享工作区约束。
- 不新增产品后端、LightRAG 服务、Python 运行时、本地模型权重、向量库／表／扫描、全库生成问答、实体图、独立 reranker 或通用 RAG 配置层。
- 模型调用仅通过现有官方对话接口，沿用模型选择、凭据和授权；不自建供应商 HTTP 客户端，不读取或记录凭据。
- 不升级 DSH，不修改 `.local/upstream/`、`.local/build/` 冒充源码成果，不新增上游锚定编辑。公开接口不足时登记 blocked-upstream，只停止受阻路径，不自行 hack 或把自动参考改成仅手工搜索并声称目标完成。
- Client 不调用 Node、不访问本机文件、不读取官方会话内部状态。通过公开 service／Remote 取得所需数据；`cordis.patch.yml` 显式声明 service 和 slot。
- 不保留兼容层、migration、fallback 或并行旧实现。基础查询与扩展查询是同一编排中的独立通道，扩展失败保留基础结果须准确报告，不能冒充扩展成功。
- 不删除唯一草稿、资料、活动提案或项目快照；不因索引可重建而清空用户成果，不习惯性全量备份缓存。
- `defineTool` 必须有 output schema 与 render；必填用 `required: true`，对象声明 `additionalProperties`。
- 业务界面沿用“文档、查找、本次参考、需求依据、当时内容”，不暴露索引、向量、快照、evidenceId、hash、worker 等技术词。技术信息放诊断入口，不新增批准／校对门禁。
- 仓库不保留测试代码或测试执行命令；执行 `pnpm check` 与受影响构建。验收必须基于当前版本真实桌面及真实模型，不以静态检查代替。

## 工作一：补齐本次参考清单与采用入口

这是阶段二报告 §7.1-1 已后置的明确缺口，优先处理。

- 由知识 Host 提供公开只读 Remote，返回最近已完成轮次的实际注入参考，绑定项目、需求、会话和 turn；复用实际注入结果，不在 Client 重新搜索或解析会话事件。
- 显示实际片段、标题、出处和必要提示；切换项目／需求／会话时不串用候选，旧轮次结果不能冒充本轮结果。关闭、正在查找、未找到、未完成、已有参考分别准确显示。
- 在本次参考和资料页提供“作为需求依据”。资料页指定已保存版本和实际采用范围，不能默认关联整份资料；Host 实际重读并签发有效证据，失效后重新读取，不信任 Client 自报正文／版本／出处。
- 进入已有需求提案与审阅流程，只有应用提案才与正文同次保存；单纯浏览、选中或点击入口不直接写入已采用依据。无活动需求时说明需要先打开需求，不自动选错目标，不新增审批步骤。
- 复用现有证据登记、项目快照、固定后提案持久化及条件保存；先抽取多个入口共用逻辑，再复用，不写第二套引用链路。

可重点核对：`packages/eadp-contracts/src/knowledge.ts`、`requirements.ts`，`packages/eadp-knowledge/src/host/injection.ts`、`proposals.ts`、`index.ts` 及 Client，`packages/eadp-requirements/src/host/proposals.ts`、`files.ts` 及 Client。落点以当前代码为准，不预设必须新增哪些文件。

## 工作二：有界查询扩展与候选融合

- 保留原问题和当前需求／有界近期背景形成的上下文查询，原查询独立执行。继续使用现有结构切片、词项器、精确通道、SQLite worker 和代次发布。
- 通过现有官方对话模型生成替代表达和关键词；初始上限一次模型调用、三条去重扩展查询。校验输出结构、条数、长度和总字符数；不让模型输出可直接执行的 MATCH 语法、过滤器或业务结论。
- 编号、金额、日期和否定语义保留在原查询，用户硬范围作为独立过滤保留；不把示例金额／日期自动变为正文必须同值的新过滤；扩展只能增加候选，不能改写原问题或放宽过滤。模型只接收必要查询背景，不上传全库资料。
- 原问题与上下文查询先启动；模型等待不持有 SQLite 事务，扩展使用同一代次和准入规则。期间发生发布变化时按剩余预算统一重查，不拼接新旧代次；返回前继续核验最新 manifest、偏好和实际正文。
- 按 README §8.4：先融合每个查询内的词项／精确结果，再分别形成基础查询组与扩展查询组，最后按两组 RRF 融合；近义扩展不能多次投票压过原问题。保留基础候选名额、稳定排序、去重及所有命中原因，限制单资料占用。
- 搜索工具和自动注入复用查询编排。查询扩展调用底层官方对话接口，不开子 Agent 会话、不递归调用知识工具；同 turn 工具续步不重复自动扩展。
- 在现有总预算中设置扩展超时和候选上限，先核对已有常量与调用契约，记录实际选择及理由，不增加设置页面或多模式框架。

重点核对 `packages/eadp-knowledge/src/host/index/`、`injection.ts`、`proposals.ts` 与现有模型调用封装。不要为了扩展重写原索引系统。

## 工作三：失败、取消和诊断

- 扩展模型未配置、超时、格式非法或调用失败时，终止该步骤；已完成的词项／精确结果继续返回，明确说明“本轮未完成补充查找”。缺少 embedding 不产生任何未就绪提示。
- 区分“本轮未找到”“部分资料可能暂时找不到”“本轮未完成查找”和扩展步骤未完成。零命中不能被解释为知识库没有相关规则。
- 用户取消必须传播至模型与查询，迟到扩展结果不注入、不更新为新轮次；中断后的下一轮正常。主模型首次请求前只能注入本轮经原文核验的候选，同 turn 续步不重复。
- 诊断保留查询来源、基础与扩展组候选、命中原因、模型标识、调用次数、耗时、失败原因及版本，不记录凭据，不把生成线索作为证据。
- 清理产品代码／文案中旧 S4 或向量前置口径；历史报告保留并明确历史身份，不篡改过去的核查事实。

## 当前版本真实桌面验收

复用 Phase 2 的环境与真实资料，先核对实际启动配置、桌面构建、固定宿主提交和模型；不擅改真实用户配置。下一阶段使用独立证据目录 `.local/verification/knowledge-no-embedding/`，不要覆盖旧 Phase 3 的 S4 记录。

1. 不同说法实例：记录原问题、基础候选、扩展词及新增的具体有效原文；同时记录噪声。未找到有效改善实例就据实报告，不宣称扩展已改善查找。
2. 编号／范围实例：扩展没有丢失编号、否定或用户过滤，混淆资料不会被当成依据。
3. 失败／取消：真实模型调用失败或超时后基础结果可用且状态准确；运行中取消无迟到注入，下一轮恢复；关闭自动参考不调用扩展。
4. 每个新 user turn 首次主模型请求前收到实际片段，同 turn 续步不重复；日志可核实引用范围和 turn，不能仅凭模型回答推断已注入。
5. 参考清单和资料页两个入口分别完成：选择范围 → 实际读取 → 需求提案审阅 → 应用保存 → 更新资料 → 删除资料 → 重启后回读当时内容。切换项目／需求／会话不串用引用。
6. 复验受影响的保存冲突、迟到索引、扩展期间更新／删除／偏好变化、worker 中断恢复，输入和已保存成果不丢失。未执行项列为未验证。
7. 人工查看本次参考／采用入口的排版、空／错／加载状态和窄窗口；不沿用旧截图证明新版视觉通过。

不要求冻结样本或量化召回结论。记录实例中的实际等待、模型调用、有效原文及失败结果；这不代表全库效果、业务试用或生产就绪。若涉及协同后端，固定用 `100.119.183.44` 的既有配置；本地知识链路不为验收额外引入协同服务。
