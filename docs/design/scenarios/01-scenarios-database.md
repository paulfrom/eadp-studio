# 场景与需求协同后台数据库设计

本文与[场景设计](01-scenarios.md)、[需求设计](../02-requirements.md)、[建表 SQL](../../../apps/collaboration-api/db/schema.sql)及 [ER 图](../database/erd.md)共同描述目标数据库。SQL 按新库一次执行，不提供旧结构兼容层或迁移。数据库结构与约束定义不等于 Host、服务和桌面业务链路已接入；既有实现记录见[修正与验证记录](implementation.md)。字段中文名称及用途以 SQL 中的 COMMENT 为准。

目标结构取消整体关联冻结和强制同批确认，保留当前材料的占用及单资产接受事务。一致性对比独立且不阻断流程，手动或材料确认后自动发起，只读本地实际文件、不执行 Git 操作；每次对比的快照与冲突摘要存后台，不回写材料文件，也不参与材料确认事务。每个场景／需求维护同一文件，历史由原有 Git 流程保存，不作为对比输入。需求编号、独立模板、系统预置接受及独立对比的数据库结构由本 SQL 定义；运行时代码仍须分别接入这些规则。

## 数据权威与保存边界

| 内容 | 权威位置 | 后台职责 |
| --- | --- | --- |
| 场景／需求正文、质量项、待澄清项、限制说明 | 确认提交中的材料 Markdown | 校验固定内容，保存材料引用与确认事实，不保存整包 metadata |
| 正式依据文件及实际引用的抽取内容 | 同一确认提交树中的 `.eadp/evidence/` 文件 | 校验引用，不保存依据清单或全文 |
| 正式依据来源、路径、SHA-256、引用范围 | 材料 Markdown 的结构化元数据 | 通过材料固定引用定位，不建独立依据表 |
| 关联文件路径、SHA-256 及文件本体 | 材料 Markdown 中的文件清单及同一提交树中的文件 | 不建确认文件快照表；当前关联表仅供目录投影 |
| 标题、摘要、编号、人员、时间、占用、修订与确认状态 | 后台明确字段 | 目录投影与协同控制；确认标题和摘要随版本固定 |
| 需求来源、前置关系 | 后台关系表，绑定固定版本 | 同项目、来源已合法接受及前置条件校验；普通场景为用户确认，通用场景为系统预置，不混同接受途径 |
| 需求是否适用及不适用原因 | 固定材料中的业务声明，以及由它提取的确认版本字段 | applicability／applicability_reason 直接参与生产门禁，不藏在 JSON 快照中 |
| AI 对话、提示词、工具日志、未消费的写入提议、资料读取过程 | 桌面本地 | 不接收、不保存 |
| 一致性对比记录与冲突摘要 | 协同后台独立记录 | 保存本次对比结论、覆盖范围、失败码及冲突摘要与涉及材料，与材料内容、确认及任务状态分开；不保存处理状态和文件 hash，不借记录保存完整材料或 AI 过程，不取 Git 历史作为对比输入、不回写材料 metadata、不作为流程门禁 |

后台 JSON 字段必须有具体的控制协议用途；删除通用业务快照不等于禁止模板固定引用、幂等结果或修复事件等必要结构。集成请求、操作结果和审计明细只保存恢复与核对所需控制字段，不能重新塞入整包材料、依据或文件清单。

同项目归属采用复合外键，同事务分步写入后的完整性采用延迟约束触发器，不使用跨表 CHECK 或数据库事务 ID 作为历史封存依据；参见 PostgreSQL 的[关系约束](https://www.postgresql.org/docs/15/ddl-constraints.html)和[约束触发器](https://www.postgresql.org/docs/15/sql-createtrigger.html)。

## 项目创建与就绪统一建模

只保留 `studio_projects`，项目从首次预留即取得稳定 ID，后续阶段更新同一行，不再复制创建结果到另一张项目表。

| 状态 | 已确定事实 | 下一步与失败核对 |
| --- | --- | --- |
| reserved | 创建意图、幂等键、请求指纹、命名空间、仓库路径及工程标记已持久化 | 领取创建步骤；同一键不同请求拒绝 |
| creating | 远端建仓请求可能已发出 | 超时先用路径和工程标记核实远端，不盲目重建或接管同名仓库 |
| created | 远端仓库身份与地址已核实 | 分配成员；失败后从本阶段继续 |
| assigned | 成员分配完成 | 初始化目录、默认模板及项目清单，推送并完成后台接受 |
| ready | 初始化版本已被项目接受，认可头已记录 | 允许材料、占用、集成等业务操作 |

保留创建人＋幂等键、命名空间＋路径、工程标记、GitLab 项目 ID 的唯一约束；创建请求指纹不可变，不随项目改名重算。早期远端字段可空，created 及之后必须有完整远端绑定；ready 必须有认可头。失败保留最后已确定阶段，结果未知先核对。状态推进和重试采用条件更新及既有幂等机制，不能仅凭前端状态放行，也不能从 ready 回退后重新建仓。

## 确认版本与文件引用

`studio_confirmations` 保存实体、版本、修订、标题、摘要、commit_sha、path、sha256、接受途径和必要适用性字段。用户确认还须具有阅读 hash、确认方式、确认人和普通集成身份，授权修复另关联修复任务；系统预置只关联初始化接受事实，不伪造这些用户确认字段。删除通用 `metadata`，不建立 `studio_confirmation_evidence`、`studio_confirmation_files`。

普通场景和需求实体的 `template_id`／`template_ref` 保存当前绑定模板身份及固定引用，供整理与结构检查使用；同一绑定也记入材料身份元数据，历史确认版本从固定材料读取当时模板引用，不使用实体后来切换的绑定重解释旧材料。无需在确认表再次保存模板或模板清单。固定引用仅允许 commitSha、path、sha256；系统通用场景使用受控固定说明，不绑定可切换模板。

需求使用独立的项目级需求模板，复用上述模板管理及版本绑定边界，不重复在后台保存模板内容。需求采用项目内稳定的 `REQ-0001` 编号，文件路径按名称生成；删除需求分类字段及分类词表，不保留默认分类或兼容字段。

在现有项目场景体系内固定内置“通用场景”，默认可选，无须用户先创建、编辑或确认；沿用场景关联，不新增无场景来源类型。其真实初始引用由项目初始化接受，设计依据见[ADR-0004](../../adr/0004-builtin-general-scenario.md)。SQL 定义存储与约束，实际文件生成、固定内容核验和业务入口权限仍由 Host／后台实施。

**通用场景初始化与接受途径**

- 每项目预留一个正常场景实体，增加稳定的 `builtin_key = general` 标识，并约束同项目内置键唯一；保留真实 UUID、SC 编号及按名称生成的 `场景/<名称>.md` 路径，内置身份由 `builtin_key` 识别，不依赖可修改的名称。
- 后台在现有项目创建／初始化准备中幂等预留身份。Host 用[固定通用说明](../templates/general-scenario.md)正文及预留身份组装受控 `eadp-metadata`，连同默认场景／需求模板及项目清单写入同一真实初始化提交；复用初始化端点提交真实固定引用。说明样稿是正文规范，实际文件含项目专属身份，校验正文及元数据后计算实际文件 hash，不要求各项目完整文件具有相同静态 hash。
- 后台核对预留身份、固定说明内容、路径、hash 与初始化提交；在现有初始化接受事务内写入通用场景版本，并完成项目认可头和 ready。缺失、不同内容、伪造引用或冲突时不宣称项目已就绪；重复同一初始化返回原身份与版本。
- 固定 Git 内容的网络核验在数据库事务外完成；最终短事务重新校验项目状态、预留身份与原操作，再原子写入预置版本、认可头、ready 和幂等结果。Git 与数据库不构成跨系统原子事务。同操作异内容拒绝，并发初始化只能接受一份；结果未知按原操作查询。项目后续推进认可头后仍可查询原初始化接受事实，不将历史接受误判为需要重新执行，也不回退 ready 或生成第二个通用场景。
- 接受记录明确区分 `acceptance_kind = user-confirmed | system-provisioned`。`studio_project_initializations` 保存初始化操作身份、请求指纹、原初始化固定提交及发起人快照；每项目只能接受一次，后续认可头变化不改变原事实。系统预置分支必须关联此记录和真实固定引用，不填造用户阅读 hash 或手工确认动作；普通确认分支继续要求真实用户授权、阅读及质量检查，不能凭请求中的系统标志进入预置分支。两种途径使用互斥完整性约束，不能把普通确认字段整体改成可缺省。初始化事实、通用场景接受版本及项目 ready 由延迟约束在提交时统一检查。
- 当前业务确认 Schema 要求正式依据及规则／验收声明，不能伪造业务证据或将质量项设为 true 来容纳固定通用说明。为合法系统预置定义严格的身份与固定说明校验入口；读取已接受版本时按接受途径选择校验契约，沿用同一实体／版本模型，不以解析失败后 fallback 到另一契约。
- 通用场景不可被普通编辑、修订、改名或删除接口改变；界面展示“系统内置”。需求引用其真实场景版本，仍须满足需求自身的依据、规则、验收和确认条件。新建需求空选择仍非法，不自动替换成通用。
- 版本投影区分系统接受时间与用户业务确认时间，不能把初始化发起人记为业务确认人。通用说明不参与单场景／多场景业务拆分或普通场景复用资格流程，仅提供场景归属；相关约束同时覆盖 Host 和后台，不能只隐藏界面按钮。
- 不在打开既有项目时临时创建通用场景或虚拟引用。本模型用于新库部署，不增加旧结构兼容、懒补齐或迁移路径。

接入入口为[项目初始化接受](../../../apps/collaboration-api/src/projects.ts)、[初始化固定提交校验](../../../apps/collaboration-api/src/project-initialization.ts)及 [Host 初始化文件](../../../packages/studio-plugin/src/host/application/projects.ts)。本次数据库修改不包含这些业务路径，既有验证结果不能代替新方案验收。

正式依据与关联文件都由材料 Markdown 中的结构化清单描述。确认引用 `{commitSha,path,sha256}` 同时固定正文和其中的清单，无须后台再复制一份清单。清单 hash 指向关联文件字节，不把材料自身的 hash 写入自身，避免自引用。

确认前，可信 Host 和后台固定内容校验使用同一候选提交，验证材料 hash、文件相对路径、文件存在性及文件 hash，确认引用范围属于所归档资料。文件可以已存在于提交树而不在本次 diff 中；外部链接只作来源说明，不能替代要长期保存的文件。工作区文件、可变链接或仅上传未提交的附件均不能充当固定文件。完整 diff 仅限当前材料及其明确关联文件，不夹带其他材料草稿或资料，不因修订一份材料而自动修改或提升其他材料的来源版本。

历史读取始终通过确认 commit_sha 读取材料与文件，不能使用当前工作区同名文件，也不能从 `studio_entity_files` 的当前路径集合重建历史清单。当前关联表是可变目录投影，不参与历史确认判定，不得携带未确认正文或临时资料。后台已接受的提交及其引用文件须保持可达，不能清理成只有 hash 而无内容的记录。

普通材料的业务质量项与待澄清项在确认时从固定材料校验；核心规则、验收条件、真实依据缺失或存在 blocking 问题仍须阻断。系统通用说明通过上述严格初始化接受途径进入，不能据此放宽普通场景或需求的业务确认门禁。场景 applicability 必须为 applicable；需求 not-applicable 必须说明原因，后端根据该确认版本阻断后续生产，重新适用须形成新确认版本。

## 固定版本接受事务

固定内容、引用与权限先校验；最终接受时重新校验项目修订、当前材料有效占用、预期认可头及来源版本，在单资产事务中处理以下步骤。一致性检查结果与冲突均不参与该事务，不以检查未完成、失败、结果对应旧内容或存在冲突阻止接受，也不要求先解决冲突：

1. 条件更新项目认可头。
2. 写入不可变确认记录及必要适用性字段。
3. 对需求写入至少一个同项目、已经合法接受的场景固定来源；普通场景是用户确认版本，内置通用场景是系统初始化接受版本，两者均须具有真实固定引用。
4. 更新当前实体的确认、材料版本、确认状态及目录投影，结束当前材料占用；不冻结、更新或确认其他关联材料。
5. 将集成标记为 accepted；任一失败整体回滚。

Git 更新与数据库提交不是跨系统原子事务。结果未知按原操作与集成身份核对；Git 成功但后台尚未接受时仍为待核对，不显示已确认，也不重新生成候选或重复确认。确认与来源记录不可变，材料或文件变化须形成新版本。

需求材料确认记录保存不可变的 `source_count`，与同事务写入的来源条数严格相等；来源以确认版本及场景身份唯一，绑定同项目真实场景固定版本。延迟约束同时检查父确认与来源写入，允许同事务分步保存，但提交后不允许追加、修改或删除来源。更换来源只能产生新的需求确认版本，不能给历史确认增加关系。当前草稿来源仍可在独立修订中原子调整，不自动升级到场景新版本。

前置关系绑定同项目真实需求材料确认版本；生产占用输入绑定该需求真实原型完成版本及集成提交，避免需求 ID、版本、确认记录各自合法但互不对应。关系 DAG、权限、当前占用和原型完成证据的业务校验仍在服务事务中进行，前置需求未完成不阻止当前需求文档确认。

## 独立一致性记录

一次对比用三张独立关系表：对比结论、冲突摘要及其涉及材料。对比记录固定目标材料、触发途径、可选确认事件、操作键、执行结果、覆盖范围、有限失败摘要与冲突数量。确认后自动触发按确认事件唯一，主动重比创建新记录；网络重传复用原操作。

冲突只保存有限摘要、正式／潜在关系及涉及的其他材料，随对比一次写入。数据库不保存待处理／已处理／已忽略状态，不保存逐条提醒、修改方向或处理历史；冲突的实际解决在用户客户端完成，下一轮对比生成自己的冲突清单，不继承上一轮结论。

结论由记录自身派生：completed 且 complete 且冲突数量为零才算通过；partial 表达范围不足；failed 或 cancelled 不得显示一致。数据库不保存逐次读取的文件路径、SHA-256 与行范围，本次读了什么由客户端在任务内自证；缺少这些证据时，范围不足只能以 coverage 表达。

对比记录、冲突及涉及材料全部不可变，更新与删除一律拒绝；冲突数量与每条冲突的涉及材料数量在写入时封存，提交时由约束触发器核对，接受后不能再补。数据库限制同项目归属、枚举、定位及字段长度和集合上限；共享契约仍须拒绝额外字段、完整材料、完整 diff 和原始模型载荷。

数据库只保存客户端对本次本机结论的观察事实，不证明文件真实、新旧或模型结论正确；权限、用户身份和限界输入须由服务核验。对比数据不关联材料确认门禁，不触发 Git 或文件写入。

## 编号与审计

按项目及资产类型分别通过计数器行锁原子分配序号，场景为 `SC-0001`、需求为 `REQ-0001`，同项目各自从 1 开始。编号预留记录资产类型、UUID、编号、原操作键和请求指纹；新建操作键复用原分配结果，失败允许空号，不回收序号。实体身份、类型、编号保持不可变。

可变业务实体保留 creator／last_editor 八字段，独立不可变事实保留创建四字段。账号和姓名是历史展示快照，不随用户改名重写。来源明细沿用所属接受记录的审计身份，冲突及涉及材料随对比接受、审计继承父对比；状态使用 PostgreSQL 枚举。系统预置版本不填写用户业务确认人，发起人及接受时间由初始化事实追溯。取消为旧批次维护的场景关联修订号，需求关系更新使用该需求自身的 revision。

## 静态核对与实施边界
