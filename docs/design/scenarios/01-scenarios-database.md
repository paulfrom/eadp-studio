# 阶段一协同后台数据库设计

状态：2026-10-20 按本轮用户确认的存储边界修订。本文与[场景设计](01-scenarios.md)、[建表 SQL](schema.sql)共同描述目标设计；目标关系模型已接入运行时代码并使用隔离数据库验证，尚未替换现有运行库或完成产品验收；实施状态见[修正与验证记录](implementation.md)。按新库部署，不提供旧结构兼容层或迁移。

## 数据权威与保存边界

| 内容 | 权威位置 | 后台职责 |
| --- | --- | --- |
| 场景／需求正文、质量项、待澄清项、限制说明 | 确认提交中的材料 Markdown | 校验固定内容，保存材料引用与确认事实，不保存整包 metadata |
| 正式依据文件及实际引用的抽取内容 | 同一确认提交树中的 `.eadp/evidence/` 文件 | 校验引用，不保存依据清单或全文 |
| 正式依据来源、路径、SHA-256、引用范围 | 材料 Markdown 的结构化元数据 | 通过材料固定引用定位，不建独立依据表 |
| 关联文件路径、SHA-256 及文件本体 | 材料 Markdown 中的文件清单及同一提交树中的文件 | 不建确认文件快照表；当前关联表仅供目录投影 |
| 标题、摘要、编号、人员、时间、占用、修订与确认状态 | 后台明确字段 | 目录投影与协同控制；确认标题和摘要随版本固定 |
| 需求来源、前置关系 | 后台关系表，绑定固定版本 | 同项目、来源已确认及前置条件校验 |
| 需求是否适用及不适用原因 | 固定材料中的业务声明，以及由它提取的确认版本字段 | applicability／applicability_reason 直接参与生产门禁，不藏在 JSON 快照中 |
| AI 对话、提示词、工具日志、未采纳建议、资料读取过程 | 桌面本地 | 不接收、不保存 |

后台 JSON 字段必须有具体的控制协议用途；删除通用业务快照不等于禁止模板固定引用、幂等结果或修复事件等必要结构。集成请求、操作结果和审计明细只保存恢复与核对所需控制字段，不能重新塞入整包材料、依据或文件清单。

## 项目创建与就绪统一建模

只保留 `studio_projects`，项目从首次预留即取得稳定 ID，后续阶段更新同一行，不再复制创建结果到另一张项目表。

| 状态 | 已确定事实 | 下一步与失败核对 |
| --- | --- | --- |
| reserved | 创建意图、幂等键、请求指纹、命名空间、仓库路径及工程标记已持久化 | 领取创建步骤；同一键不同请求拒绝 |
| creating | 远端建仓请求可能已发出 | 超时先用路径和工程标记核实远端，不盲目重建或接管同名仓库 |
| created | 远端仓库身份与地址已核实 | 分配成员；失败后从本阶段继续 |
| assigned | 成员分配完成 | 初始化目录、默认模板及项目清单，推送并完成后台接受 |
| ready | 初始化版本已被项目接受，认可头已记录 | 允许材料、占用、集成等业务操作 |

保留创建人＋幂等键、命名空间＋路径、工程标记、GitLab 项目 ID 的唯一约束；创建请求指纹不可变，不随项目改名重算。早期远端字段可空，created 及之后必须有完整远端绑定；ready 必须有认可头。失败保留最后已确定阶段，结果未知先核对。状态推进和重试采用条件更新及既有幂等机制，不能仅凭前端状态放行，也不能从 ready 回退后重新建仓。

## 确认版本与文件引用

`studio_confirmations` 保存实体、版本、修订、标题、摘要、commit_sha、path、sha256、阅读 hash、确认方式、确认人、时间、集成身份及必要适用性字段；授权修复另关联修复任务。删除通用 `metadata`，不建立 `studio_confirmation_evidence`、`studio_confirmation_files`。

场景实体的 `template_ref` 保存当前绑定模板的固定引用，供整理与结构检查使用；同一绑定也记入材料身份元数据，历史确认版本从固定材料读取当时模板引用，不使用实体后来切换的绑定重解释旧材料。无需在确认表再次保存模板或模板清单。

正式依据与关联文件都由材料 Markdown 中的结构化清单描述。确认引用 `{commitSha,path,sha256}` 同时固定正文和其中的清单，无须后台再复制一份清单。清单 hash 指向关联文件字节，不把材料自身的 hash 写入自身，避免自引用。

确认前，可信 Host 和后台固定内容校验使用同一候选提交，验证材料 hash、文件相对路径、文件存在性及文件 hash，确认引用范围属于所归档资料。文件可以已存在于提交树而不在本次 diff 中；外部链接只作来源说明，不能替代要长期保存的文件。工作区文件、可变链接或仅上传未提交的附件均不能充当固定文件。完整 diff 仍按材料／批次范围限制，不夹带其他草稿和资料。

历史读取始终通过确认 commit_sha 读取材料与文件，不能使用当前工作区同名文件，也不能从 `studio_entity_files` 的当前路径集合重建历史清单。当前关联表是可变目录投影，不参与历史确认判定，不得携带未确认正文或临时资料。后台已接受的提交及其引用文件须保持可达，不能清理成只有 hash 而无内容的记录。

业务质量项与待澄清项在确认时从固定材料校验；核心规则、验收条件、真实依据缺失或存在 blocking 问题仍须阻断。删除存储表不删除确认门禁。场景 applicability 必须为 applicable；需求 not-applicable 必须说明原因，后端根据该确认版本阻断后续生产，重新适用须形成新确认版本。

## 固定版本接受事务

固定内容、引用与权限先校验；最终接受时重新校验项目修订、有效占用、预期认可头及来源版本，在单事务中：

1. 条件更新项目认可头。
2. 写入不可变确认记录及必要适用性字段。
3. 对需求写入至少一个同项目已确认场景固定版本来源。
4. 更新实体当前确认、材料版本、确认状态及目录投影，结束本次占用与批次冻结。
5. 将集成标记为 accepted；任一失败整体回滚。

Git 更新与数据库提交不是跨系统原子事务。结果未知按原操作与集成身份核对；Git 成功但后台尚未接受时仍为待核对，不显示已确认，也不重新生成候选或重复确认。确认与来源记录不可变，材料或文件变化须形成新版本。

## 编号与审计

项目内通过计数器行锁原子分配序号，编号与实体身份保持独立。新建操作键复用原分配结果，失败允许空号，不回收序号。具体格式和约束以 SQL 与场景设计为准。

可变业务实体保留 creator／last_editor 八字段；不可变记录保留创建四字段。账号和姓名是历史展示快照，不随用户改名重写。版本来源明细沿用所属确认的审计身份；状态使用 PostgreSQL 枚举。
