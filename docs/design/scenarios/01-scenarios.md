## 用户目标

**已定**

场景定义多个细化需求的共同业务范围。用户命名场景后创建空白正文的 Markdown，通过 AI 对话、资料和手工编辑完善材料；用户采纳后才将普通 AI 建议写入草稿，最终确认形成被项目接受的固定场景版本。空白指正文，不要求文件零字节。

完整路径为：**命名新建 → 提供资料并对话整理 → 采纳或手工编辑 → 门禁检查 → 用户确认／授权 AI 修复并确认 → 后台接受固定版本 → 询问是否拆分需求**。选择立即拆分时先展示候选，用户选择后才创建需求草稿；选择否时不自动拆分，已确认场景保留稍后拆分入口。同一场景可多轮补拆，也可选择多个已确认场景联合拆分，候选只引用实际相关来源，不覆盖或合并已有需求。现有项目场景中另固定内置“通用场景”，默认可选，不要求用户先创建、编辑或确认；不是独立的无场景来源类型。普通场景来源仍绑定各确认版本，通用场景引用项目初始化接受的真实系统预置版本；拆分不自动确认需求。

场景内容以业务目标、范围、角色、流程、规则、异常及验收条件为主。用户明确给出的技术约束可以保留，AI 推导的实现先作为建议。业务流程允许退回、重试和循环，不套用需求前置依赖的 DAG 限制。

最小业务确认仍要求真实业务依据、核心业务规则、可判断的验收条件及无未解决核心待澄清项；这些语义不依赖固定模板标题。核心问题未解决时保持草稿，非阻断问题明确保留限制及不适用范围。AI 辅助评审可选，有权限且持有当前有效设计占用的用户可以直接确认，纯手工 Markdown 也能走直接确认路径。一致性对比与这些材料自身条件分开，差异、检查失败或旧结果均不阻止确认，也不自动变成材料中的 blocking 问题。AI 不能自行批准材料。已有依据可确定的问题可在用户授权修复任务中修正，缺少业务答案仍须用户补答，不额外要求所有修复再次人工逐项采纳，也不自动修改其他关联材料。业务完整性的具体表达见第四节设计约定。

场景不使用分类，使用后台按项目原子递增分配的业务编号，例如 SC-0001。编号项目内唯一，不可手改、重排或回收，改名与修订保持不变；UUID 仅作隐藏技术实体身份，界面主要展示一个业务编号。确认状态、任务状态和复用资格分别表达；本地保存、采纳、正式确认是不同结果。材料固定版本不能称为后续原型阶段的基线。

**范围边界**

本期为阶段一项目场景。需求覆盖率属于阶段四；契约一致性等跨阶段指标另行决策，不用 HTML 示例指标暗示能力已经存在。

## 桌面端职责

**已定：工作区与材料编辑**

| 环节 | 交互与结果 |
| --- | --- |
| 新建 | 仅输入场景名称，后台自动分配编号并进入空白正文 Markdown，沿用设计占用流程；不出现分类输入，不自动预填模板八章。编号可查看但不可手工编辑。 |
| 对话与采纳 | 左侧场景 AI 对话，右侧当前 Markdown 预览／可编辑源码；提供导出、折叠及恢复。AI 按选定模板组织候选，普通首稿和修改均须采纳后写入。 |
| 三级采纳 | 先选择单条、整块或全部建议，再一次写回并更新 hash。其余旧 hash 建议保留历史但过期，基于新 Markdown 重读、重新生成后才能再采纳，不静默更换版本依据。 |
| 手工编辑与保存 | 停止输入后自动保存本地 Markdown，采纳也保存；切换／退出前确保保存完成。保存失败保留输入并提示，界面表达“本地草稿已保存”，不暗示正式确认或远端同步。 |
| 外部修改冲突 | 文件外部变化与未保存输入并存时保留两份、展示差异，用户选择或合并后保存；冲突未解决前暂停确认。若并发编辑发生在已授权修复任务中，则终止该任务，不在解决冲突后自动恢复授权。 |
| 会话 | 每个场景独立保有会话历史。新会话继承当前 Markdown、所选模板固定版本和当前选定资料，不自动继承完整旧聊天；旧会话保留并可恢复。 |
| 资料 | 支持文本／Markdown、PDF、Word、Excel、PPT 和图片，每份明确显示已读取、部分读取或失败；AI 只引用实际读取内容，上传或预览成功不代表已读。 |

模型接入由 DSH 宿主统一配置，不另建模型接入层。对话、提示词、建议草稿、工具过程和临时资料留在本地；用户选定的正式依据按“数据与文档格式”随确认版归档。

**已定：模板与本地结构检查**

场景模板设置复用 DSH 原生设置壳。用户可上传 Markdown 模板及手工切换。模板文件保存在项目 `.template/` 文件夹，由桌面客户端负责写入与替换，随 Git 提交到远程在项目内共享；后台不保存模板内容、清单与默认项，只记录场景绑定的模板固定引用。模板绑定与更新规则见第四节。

“模板结构检查”开关默认关闭，仅影响本机偏好，不同步成项目强制规则、不影响其他成员。关闭时执行独立统一确认门禁；开启时额外检查所选模板二级章节齐全，允许重排和新增章节、不要求正文照抄、不从模板文字生成业务门禁。缺章可进入 AI 修复。开关不能关闭版本、权限、核心待澄清项或后台接受等固定条件。

**已定：确认与修复**

普通确认由可信 Host 对应用户阅读的版本执行。门禁通过时，有权限且持有当前有效设计占用的用户可以直接确认，无须先做 AI 辅助评审。展示检查、Working Tree 和后台接受状态；后台未接受不能显示已确认，结果未知先查询状态并显示待核对，不盲目判失败或重复创建。

确认遇阻断时提供明确动作“AI 修复并确认”。用户点击一次授权本次修复任务直接写入、重算 hash、重跑完整门禁，并由可信 Host 自动提交确认，无须再次采纳。范围限于结构、引用错误及已有依据可确定的内容，不能编造业务答案。

| 修复任务状态 | 已定处理 |
| --- | --- |
| 缺少可补充的业务答案 | 暂停任务并询问用户，不继续写入或提交。用户通过“补充并继续修复确认”显式续接同一任务；普通聊天回复不自动恢复。 |
| 显式补充并继续 | 纳入用户补充，重读当前 Markdown，重新核验用户权限、有效占用及输入版本，再在同一任务内继续，无须逐条采纳。已执行轮数累计保留，暂停／补答不重置最多 3 轮总额度。 |
| 终止 | 缺少可读取的来源、相同阻断无改善、发生并发编辑、3 轮额度耗尽、用户取消或任务完成时终止；保留现场及原因。终止任务不能通过普通补答或聊天自动恢复。 |

最终确认仍以修复后的内容、hash、完整门禁及后台接受结果为准；接受结果未知时先核对，不以再次修复或重复提交代替查询。

**已定：列表、可见性与显式修订**

- 卡片显示创建人，另显当前编辑人／占用及修订状态；确认详情显示确认人和时间。本阶段不新增业务负责人指派或转交。
- 其他成员可以看到草稿名称和占用状态，草稿正文、会话及未选为正式依据的资料仍留在作者本地。
- 已确认场景默认只读打开，不因查看领取设计占用。存在修订时，其他成员仍读取旧确认版及修订／占用状态，看不到新草稿正文。
- 用户点击“开始修订”先看影响清单，再显式启动当前场景修订，仅占用当前编辑材料。关联需求不自动冻结、改写或升版，不要求与场景同批确认；独立一致性对比只提供差异和处理能力，不改变材料确认条件或阻止流程。
- 阶段一列表沿用已纳入 HEAD 的 MaterialCatalog，补齐设计稿要求的信息、筛选、统计及分页形态。

## 协同后台职责

**已定**

| 领域职责 | 后台边界 |
| --- | --- |
| 新建与目录投影 | 沿用场景实体、UUID 技术身份及设计占用，移除场景分类约束；按项目原子分配 sequence 与业务编号 code，向其他成员投影草稿名称、编号、占用和修订状态，不上传或泄露本地草稿正文与 AI 过程。 |
| 查看与修订 | 读取已确认版不领取占用；显式开始修订先明确影响，仅占用当前材料。取消整体关联冻结与强制同批确认；一致性对比及差异处理与修订／确认分开。 |
| 固定版本确认 | 接受可信 Host 提交的固定版本及确认依据；普通路径对应用户阅读版本，授权修复路径对应用户动作、起始版本、修复记录及最终版本。完整门禁和后台接受结果均针对最终版本。 |
| 结果未知 | 先核对既有请求／资产状态；未明确接受时不显示已确认，也不盲目重复创建。 |
| 需求来源与拆分 | 沿用项目场景关联，固定内置“通用场景”默认可选，无须用户先创建、编辑或确认，初始引用须有真实系统预置接受记录。普通场景来源保留固定确认版本；同场景可多轮补拆，多场景可联合拆分，每候选仅引用实际相关子集，选取才创建草稿，不覆盖或合并已有需求。 |
| 模板与正式依据 | 保存场景绑定的模板固定引用及材料确认的固定引用；正式依据的来源、路径、hash 和引用范围随材料存入 Git，由确认提交定位，不建后台依据索引。本地结构检查偏好不成为项目强制规则。 |

collaboration-api 不新增 AI 端点。会话编排、资料受控读取、结构化建议解析、采纳和修复由桌面 Host 执行；本地保存或 AI 声称完成不改变后台确认状态。

**已确认的接口调整与待实现差距**

下表依据已核对的现有链路列出已确认的必要调整，均为待实现差距，不表示新增接口已经存在；请求 Schema、审计字段及失败恢复按本文设计约定实现。

| 环节 | 现有链路 | 必要调整 |
| --- | --- | --- |
| 新建草稿 | createMaterial → POST entities → claim | 仅名称即可创建场景，由后台保留 UUID 技术身份并原子分配项目内唯一 sequence／code；同一新建 operationId 重试返回同一编号。删除场景分类约束；阶段二也已决定取消需求分类，不增默认分类或兼容层。只读打开已确认版不得复用新建／claim 行为。 |
| 保存及采纳 | 现有材料读取／保存与文件 SHA-256 | 保存补 expectedHash，Host 写入前比较实际 hash；采纳使用同一受控写入能力，一批建议一次保存。检测到外部变化与未保存输入冲突时保留两份，暂停确认并禁止启动自动修复；若已处于授权修复任务中则终止任务，解决冲突后不自动恢复。 |
| 普通 AI 整理 | 现有材料 Agent 会话、任务提示与工具通道 | 改为 propose-only：普通会话只产出结构化候选，不直接写场景文件；由用户采纳后经 Host 校验预期 hash 并写入。授权修复采用独立受控执行路径，不能让普通对话继承其写入授权。 |
| 场景会话 | 现有 start／restore | 按场景绑定并恢复历史，补新会话动作及其最小继承上下文；保留旧会话，不自动复制完整旧聊天。模型仍由 DSH 配置。 |
| 普通确认 | confirmMaterial → POST integrations → complete | 复用固定 Git 版本与后台接受链路，确认用户阅读 hash、业务质量项、权限和占用；移除绑定固定标题／8 字符的推断。结果未知先查询核对，不重复创建。 |
| 授权修复确认 | 复用 confirmMaterial → POST integrations → complete | 关联本次用户动作、任务身份、起始／最终 hash、累计轮数及暂停／续接记录；Host 限定写入范围并重跑完整门禁。同一任务补答续接不重置 3 轮额度，终止后不自动恢复，不新增 AI 后台端点。 |
| 需求拆分 | 现有 split／selectCandidate，当前确认后自动拆分 | 去除自动触发，改为确认后明确选择或稍后入口；split 只产候选，selectCandidate 才创建需求草稿，补已确认场景固定版本来源约束，不自动确认需求。 |
| 查看及修订 | GET versions 与现有占用／确认入口 | GET versions 支持只读同一文件的 Git 历史确认内容；先展示影响清单，再显式领取当前材料修订占用。删除整体关联冻结、强制同批确认和自动关联来源升版；各材料独立确认，不等待一致性差异处理。 |
| 一致性对比 | 待新增的独立对比与差异管理能力 | Host 复用 DSH 模型只读当前项目本地场景和需求文件，不执行 Git 命令；手动及确认后自动发起，文件缺失记录范围不足，不自动拉取补齐。后台保存对比记录、差异列表及处理结果，不反写材料 metadata、不取得关联材料编辑占用，不参与材料确认事务。 |
| 共享目录信息 | 现有 EntityView 及占用／固定版本投影 | 补创建人、编辑人、确认人／时间和修订状态；共享草稿名称与占用元数据，但不共享草稿正文、会话和临时资料。 |
| 项目模板 | 当前无模板管理端点；材料操作有既有路径白名单 | 按第四节约定扩展项目级受控配置变更，复用固定候选、条件更新、接受及核对机制；模板使用独立的路径与变更范围校验，不伪装成场景材料；本地结构检查偏好不进入项目强制规则。 |
| 正式依据与关联文件 | 现有材料确认与固定来源记录 | 正式依据和关联文件清单写入材料 Markdown 的结构化元数据，关联文件本体须可从本次固定提交读取；Host 与后台固定内容校验对照同一候选提交验证路径、hash 及引用范围。完整 diff 只允许当前材料及显式相关文件，不自动夹带其他材料的草稿或资料。后台不保存依据或确认文件清单，模板发布不能借此确认材料。 |

**已定契约**

| 对象 | 载体与规则 |
| --- | --- |

| 场景材料 | Markdown，命名后正文为空；普通首稿采纳后才写入按模板组织的内容。不建立 YAML 目标或双格式兼容层，需求 Markdown 保持阶段二边界。 |
| 场景模板 | 默认包含目标与范围、角色、流程、业务规则、异常、验收条件、依据、待澄清项八个二级业务章节；可上传和显式切换。模板随项目版本保存，每个场景绑定所选模板固定版本；更新默认只影响新场景，旧场景不自动切换或改写 Markdown。 |
| 模板与工程契约 | 场景 Markdown 模板是业务文档模板，不能替代原型工程 AGENT.md。模板文本也不能直接充当业务确认规则。 |
| hash 与建议 | 文件 hash 改变后重读 Markdown；旧 hash 建议过期，保留历史，重新生成后才可采纳。选定的一批建议一次写回，避免每条写入使同批剩余建议中途失效。 |
| 保存与冲突 | 草稿保存在本地；冲突时保留外部文件和未保存输入两份及差异，解决前暂停确认；授权修复中发生并发编辑则终止该任务，不能在合并后自动恢复。 |
| 会话与资料 | 场景独立本地会话；资料读取结果区分已读取、部分读取、失败，引用仅覆盖实际读取内容。 |
| 正式依据 | 仅用户选定的正式依据随确认场景归档，保留来源和 hash；未选定资料及 AI 会话／工具过程不随确认归档。 |

| 修复任务 | 可补业务答案时暂停，只有“补充并继续修复确认”续接同一任务；继续前重读并校验权限、占用、输入版本。累计最多 3 轮不重置；缺可读来源、无改善、并发编辑、额度耗尽、取消或完成终止。 |
| 需求来源 | 需求关联项目场景，包含固定内置通用场景；普通场景来源保留固定确认版本，通用场景使用系统预置的真实身份和固定引用，不冒充用户确认。所有来源仍须同项目且有效，空选择不自动替换为通用；详见阶段二设计。 |

**已核对的当前实现与差距**

- MaterialCatalog 已纳入 HEAD；当前材料采用 Markdown + eadp-metadata。读取已计算 SHA-256，普通确认前已比较用户阅读的 hash；普通保存尚缺预期 hash 比较，建议写回尚无专用协议。结构化建议沿用 eadp-candidates／eadp-review 文本协议模式，具体 Schema 按下文约定补齐实现。
- 当前 checkMaterial 除材料内显式 eadp-metadata 质量项、业务依据和无 blocking 问题外，还硬编码“核心业务规则”“验收条件”两章各至少 8 字符且非占位。这种固定标题／字数推断与自定义模板及关闭结构检查的方向冲突，须移除；业务规则和可判断验收条件本身仍必需。
- 历史实现的 categoryId 在 ReserveEntity、Host 和后台新建约束中必填，列表默认选首分类。场景与阶段二需求均已决定取消分类，须删除相关契约、表单、筛选、词表管理和元数据约束，不加默认分类或兼容层；当前需求实现仍待按阶段二设计修改。
- 当前后台 entity.id 使用 randomUUID()，列表直接显示完整 UUID，文件为 `场景/<id>.md`，数据库只保证 `(project_id,id)` 唯一。依据：[实体创建](../../../apps/collaboration-api/src/service.ts)、[ID 生成](../../../apps/collaboration-api/src/persistence/repository.ts)、[数据库约束](../../../apps/collaboration-api/db/schema.sql)、[目录卡片](../../../packages/studio-plugin/src/client/components/MaterialCatalog.tsx)。须补项目内原子递增的 sequence／code 及唯一约束，主要界面改显业务编号；保留 UUID 技术身份及其文件路径，不以旧 UUID 展示替代新编号。
- 当前需求新建契约、Host 和后台已要求至少一个同项目已接受场景固定来源；场景确认接受后仅提供拆分入口，用户选择后才发起拆分。现有拆分仍限单场景单确认版本，候选采用仅传标题创建需求，摘要及更细业务内容尚未承接；阶段二须补齐联合拆分、候选内容承接及系统预置通用来源。

**已确认的文件与本地协议**

| 记录 | 最小内容及约束 |
| --- | --- |
| 场景身份与绑定 | eadp-metadata 沿用 UUID entityId 身份、质量项、来源；业务编号取自后台不可变的 sequence／code 映射，不允许 Agent 或手工改编号。新增模板 ID 与 `FixedReference {commitSha,path,sha256}`，绑定变更由 Host 管理。 |
| 文件观察与保存 | Host 本地记录上次读取的整文件 SHA-256；保存输入包含实体／任务身份、`expectedHash`、新正文和操作 ID。写前重读并比较，成功返回新 hash；失败不丢输入。hash 不写入被它自身计算的同一文件字段，避免自引用。 |
| 结构化候选 | 沿用现有文本块协议模式，新增 `eadp-suggestions` JSON 块：批次 ID、实体 ID、`baseHash`、模板固定引用、分组、条目 ID、正文替换范围／原文／新文及已读依据引用。Host 验证范围、原文匹配及所选条目不重叠；非法候选显示错误，不能直接落盘。 |
| 一次采纳 | 传批次 ID、选中条目 ID、`expectedHash` 和操作 ID。只对同一版本、同一模板上下文的有效批次生成一次合并写入；重叠或已过期建议要求重选／重生成。首次成稿也是正文替换，不预填到正式草稿。 |
| 资料读取记录 | 本地记录资料 ID、名称、格式、原文件 hash、读取状态、已读页码／工作表／单元格／幻灯片或图像范围、失败原因；重试及模型上下文均依该记录，不能引用未读范围。上传或导出不自动选为正式依据。 |
| 正式依据归档 | 用户选定资料按内容 hash 保存到用户工程的 `.eadp/evidence/`，原始文件及实际引用的抽取内容随场景固定提交归档；来源、各文件 hash、引用范围和路径记入同一提交的材料 Markdown。后台仅保留材料固定引用和必要控制字段，不保存独立依据清单。来源内容变化须重新读取、重新选择版本，不能用链接指向可变内容冒充快照。 |
| 关联文件 | 材料 Markdown 中记录用户工程相对路径和各文件 SHA-256；文件本体必须存在于材料确认的同一 Git 提交树，可沿用该树中未发生变更的文件。拒绝越界路径、未提交文件、缺失文件或 hash 不符。历史读取以确认 commitSha 定位，不读取当前工作区同名文件。后台当前关联表仅作目录投影，不是历史版本权威，不建立确认文件快照表。 |
| 业务内容与控制字段 | 质量项、待澄清项、限制、正式依据引用元数据及关联文件清单保存在固定 Markdown 中，文件本体随同一提交保存；确认时从该固定内容校验，不另存后台业务快照。来源与前置关系进入明确关系表；会阻止需求生产的不适用状态和原因作为确认版本的 applicability／applicability_reason 字段，场景必须为 applicable。不通过集成请求、幂等结果或审计明细变相存入完整材料 metadata 或资料清单。 |
| 确认记录 | 检查结果在 Host 本地按最终文件 hash 记录；正式确认请求关联用户动作、固定 Git 引用、最终 hash、确认方式与来源。授权修复另含任务身份、起始 hash、累计轮次、暂停／显式续接及变更摘要；同任务补答不清零轮数，不上传完整会话、提示词或工具日志。 |

**已确认的项目模板发布方案**

模板放在用户业务工程 `.template/<模板ID>.md`，由桌面客户端负责写入和替换；`project.assets.json` 中的模板清单及默认模板 ID 只随 Git 保存，清单列出名称和相对路径。接受版本通过项目认可 Git 头定位，避免把包含自身的提交 hash 写进清单；后台不保存模板内容、清单与默认项，每个场景另绑定所选固定模板版本。已接受项目读取时清单可以没有模板目录（旧契约项目）：此时项目处于"尚未发布场景模板"状态，发布模板即以正常模板集成补齐清单与 `.template/`；新初始化仍必须声明模板目录，见 [ADR-0006](../../adr/0006-legacy-project-readonly-compatibility.md)。

模板发布作为明确的“项目受控配置版本变更”扩展现有集成协议。Host 从后台认可头构造仅包含模板及清单变更的候选，保留用户其他未确认工作；后台按现有项目写权限、预期项目修订及操作 ID 校验，只允许该类变更的路径和完整 diff。复用准备候选 → 条件更新远端头 → 完成接受的链路，客户端从已接受 Git 版本读取默认项及可用模板；不领取场景设计占用、不确认任何业务场景，也不产生原型基线。原有材料集成继续执行各自严格白名单，共用基础机制而不混合业务校验。

远端头或项目修订冲突时停止，刷新后重新预览再发布；结果未知时先查原操作及集成状态，不能重复新建。后台接受前新版本不成为共享默认；已有场景绑定的历史模板保留可读。本阶段提供新增、更新、默认选择和场景切换，不新增模板历史删除功能。模板发布已由 [Host 模板服务](../../../packages/studio-plugin/src/host/application/scenario-templates.ts) 组合[清单／固定内容读取](../../../packages/studio-plugin/src/host/application/projects.ts)、[候选提交／条件更新](../../../packages/studio-plugin/src/host/adapters/workspace/git.ts)及后台模板集成协议实现；只读目录通过后台模板端点按认可 Git 头投影。
