# 场景与需求材料独立沉淀，复用资格由后端与 Git 协同记录

2026-10-14 评审确认：场景和需求材料可以独立沉淀，首期以完整场景或需求包为复用单元，不把原型完成设为所有资产沉淀的前提。原型代码的采用仍以有效完成基线为依据。这样可以在尚未生产原型时保留并采用已确认的业务成果。

新增场景和需求必须显式记录分类及状态；客户端操作影响需求能否复用。Git 保存固定内容、分类及来源证据，协同后端记录必要分类元数据、状态、复用资格及操作受理依据；Host 核对同一固定版本，客户端不能自行宣称具备复用资格。材料确认、生产任务状态与复用资格分别表达，避免一个“已完成”同时承担三种含义。

分类方向已确认按业务领域，例如采购、库存、财务；这些是说明示例，不是内置分类词表。

编辑已确认材料时，新草稿不可复用，旧固定版本继续保持原有资格。显式停用被后端接受后，才阻止针对该固定来源的新的采用；停用不删除 Git 内容与历史，也不撤销已经复制并独立维护的目标成果及其来源记录。这使材料持续修订与已有资产的稳定采用互不混淆。

场景或需求材料通过检查、固定内容推送 Git 并被后端接受确认时，自动取得复用资格；无需作者再单独标记允许复用。确认事实与当前资格仍分别记录，后续停用不抹掉确认事实，重复确认事件不能恢复已停用资格。原型代码仍须完成基线。

所有具有该资产编辑权限的成员都可以停用或恢复固定版本的资格，沿用既有可信身份及资产编辑授权，由后端接受操作并记录操作者、原因和时间；不限制为资产负责人或维护者，不新增审批。Git 凭据和管理员释放占用的权限不能代替资产编辑授权。

来源停用与在途采用以后端接受采用记录为界：浏览或选中不算采用；未受理的采用被停用阻止，已受理的任务保留原固定来源继续完成。采用受理与停用必须明确并发先后，已有采用依据不绕过 Git 实际读取授权。采用受理不等于复用成功，目标确认被接受后记录最终固定版本及来源，失败和取消不计复用成功。

项目分类词表由所有具有项目编辑权限的成员维护，新增场景和需求时选择已有业务分类；该权限与具体资产的编辑权限分别校验。实际分类值、字段编码与操作一致性由 G0 样例验证，不增加层级分类或通用配置平台。

正式确认材料、固定版本及来源记录长期保留，覆盖 Git 可达的固定引用和对应后端确认、资格、采用及来源依据；停用不删除正式资产。临时构建、缓存及任务现场按各自规则清理，清理前保护未提交、未推送及在途唯一现场，不因清理临时内容切断正式资产的版本和来源证据。

核心业务规则与验收条件必须明确，缺少核心依据时材料继续保持草稿，不接受确认或自动授予复用资格。其他待澄清项可以随确认材料保留，但必须明确展示限制及不适用范围；作者确认实际业务依据，AI 不得编造规则或把未解决问题写成已确认事实。这是既有确认检查的内容标准，不增加二次审批。

本轮项目资产沉淀与复用决策已收敛；实际权限、固定引用可读、事务竞争和保留清理能力仍须 G0 实测，本决策不代表运行验证完成。
