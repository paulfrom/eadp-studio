# 工作台投影由一个所有者持有，读取与本地写入分车道且都有截止时间

状态：已确认（2026-10-20）。适用于 `packages/studio-plugin` 的 Host 与 Client 两半。

一次设置区块"停在登录表单"的故障暴露了三个相互独立的问题，它们的共同效果是**未决与未登录在界面上同形**：区块内部各持一份投影、`state` 排在本地写队列之后、命令没有截止时间。任何一环卡住，用户看到的都是"未登录"，而不是"无法确认"。因此固定的契约如下。

**投影只有一个所有者。** 工作台主面板（`main` 槽）与设置各节（协同账号/场景模板/外观/协同连接/关于，`settings.section` 槽）是同一个界面的多次注册，共用一份 `store`（`client/store.ts`），由 `client/session.ts` 统一读写（读取、登录/登出，以及工作台与场景模板发布这类返回新投影的命令都经它落盘）。两处注册声明同一个固定实例，任何一侧登录或登出都直接改这一份投影，因此不再需要跨界面事件通知。首次答复前渲染加载态（未决与未登录不同形），失败保留上一份投影并给出重试。`StudioState` 的空投影只有 `client/state.ts` 一处定义。

**读取不排进写入队列。** `StudioApplication.command` 把 `state` 交给独立车道（并发调用合并为一次读取），其余动作继续走单写者队列。理由：写操作可合法地运行数分钟（取工作树、装依赖、跑检查、恢复 Agent 会话），而工作台轮询与设置区块渲染的是同一份投影；让它们排在写操作之后，界面就会长期停在旧投影。投影在写入过程中读取本地状态是允许的——存储层以原子替换落盘，读到的只会是完整的新旧版本之一。投影本身也不再同步 Git：固定材料只读本地已有的对象，缺失的镜像与提交交给后台车道（见 ADR-0005），因此一次读取不会被远端拖住，也不会因材料未到而整体失败。

**每条命令都有截止时间。** 客户端 `studioCall` 为每次往返设 180s 上限（`shared/deadline.ts`），超时返回可重试的失败；`StudioService.command` 对一次性的组装等待设 60s 上限并复用其结算结果。上限取自实测与既有约定：桌面端实测冷启动后首次 `state` 需要 52s（本机、协同后端可达，含会话恢复与项目打开），插件自身的协同调用默认 60s、命名空间目录 180s，因此 180s 是该插件已容忍的最长合法路径，更短的限时会把健康冷启动误报为故障。截止只影响调用方看到的答复，不会取消已经展开的工作：跨进程与跨线的取消没有可靠语义，谎称已取消比明确失败更糟。重新同步会重新读取（若 Host 侧读取仍在进行则并入同一次读取）；迟到的答复按"最新写入优先"丢弃。

被放弃的替代方案：在区块内加超时而不改投影归属（四份状态仍会互相矛盾）；给串行队列加截止并让队列继续前进（无法取消的写操作会与新命令并发执行，本地写入的串行保证随之失效）；把 `state` 判断为只读而直接与写入并发（`state` 在修复冻结批次时确实会认领占用，因此只能是"合并读取"而不是"去串行化"）。

验证：`tests/windows-desktop/projection-lane.test.ts` 断言卡住的写操作不阻塞投影、并发读取只触发一次 Host 读取、投影失败以带 code 的答复返回、读取结算后下一次刷新重新观察 Host。桌面端实测（dev 装配 + CDP 驱动）：设置区块先显示"正在读取登录状态"，随后渲染出已登录账号卡片；冷启动首次读取 52s、第二次读取即时返回，证明共享投影与加载态在真实装配中生效。工作台与设置共用同一份投影后，登录/登出的一致性由 `tests/scripts/studio-task-purpose.test.mjs`、`tests/scripts/studio-settings-sections.test.mjs` 读取源码验证：两侧都声明同一个 `store`，面板不再自持投影，也不再有 `eadp:studio-state-changed` 通知。
