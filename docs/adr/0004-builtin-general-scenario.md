# 通用场景沿用真实场景身份，由项目初始化提供

用户要求在现有项目场景中固定内置“通用场景”，仅供新增需求时选择，不在场景目录显示，不开放正文查看、编辑或确认入口；需求仍关联场景。该决定保留现有场景与需求关系，不另建无场景来源类型，不把空来源自动解释为通用。

工程方案复用项目初始化：后台幂等预留真实场景身份，Host 用固定只读说明正文及预留身份组装受控 `eadp-metadata`，写入实际初始化提交。后台核验说明正文、身份与实际文件的固定引用后记录系统预置接受事实，并与项目就绪在同一事务中完成。各项目身份不同，不要求完整文件具有相同静态 hash；固定引用始终对应实际文件。场景版本继续使用现有身份、版本与固定引用；接受途径明确区分系统预置和用户确认，系统预置不生成虚假的用户阅读记录、业务依据或手工确认凭据。

通用说明只提供需求归属，不提供具体业务规则，不代替需求自身确认。它的系统校验只用于合法初始化中的预留资产，普通材料确认仍执行自身业务条件；不能接受客户端自填的系统标志绕过检查。固定版本读取也须根据后台持久接受途径选择严格校验契约，不在普通解析失败后转入预置分支。系统记录关联真实初始化操作，用户确认记录仍关联普通集成及阅读凭据；两种途径保持各自必需字段和互斥约束，不伪造普通集成或阅读 hash 填满旧字段。新增需求的来源选择显示“通用场景 · 系统内置”，已关联需求仅保留静态来源标识；Host 和后台禁止按普通场景修改它。

工程边界还包括：通用说明不作为单场景或多场景业务拆分输入，也不因系统预置而取得普通业务场景的复用资格；需求自身仍可借助 AI 整理真实业务内容。场景目录、统计、搜索和分页均排除内置通用场景，新增需求时的来源选择使用“系统内置”语义，初始化发起人不是该场景的业务确认人。

初始化先核验真实固定 Git 内容，再以短数据库事务接受预置版本和项目就绪事实，不声称 Git 与数据库跨系统原子。响应丢失时按原操作核对；项目后续推进认可头不改变原初始化已经被接受的事实，不因此重新预置场景。远端分支随后变化沿用项目认可头冲突处理。

该方案避免虚拟来源绕过原有引用规则，也避免用户为了新增需求先补做场景。项目初始化与材料版本管理使用原有 Git 流程；独立一致性对比仍只读本地文件，绝不因此拉取或读取 Git 历史。2026-10-26 用户明确收敛展示边界：内置通用场景不显示、不编辑，只在新增需求时可选。相关实现已按场景设计落地代码，真实桌面闭环仍须单独验收；不提供旧项目懒补齐或兼容层。
