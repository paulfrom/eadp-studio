# 一致性对比与场景、需求文件及业务流程分离

场景和需求表达不同粒度的业务内容，需求细化也可能发现需要反向修订场景的事实。用户明确要求项目提供独立的一致性对比能力：AI 查找关联文件并比较场景与需求的业务一致性，每次给出当前是否一致的结论和冲突摘要；冲突的实际解决由用户在客户端完成。

每个场景或需求维护同一个文件，历史由 Git 保存，不为各历史版本建立平行的业务文件。每次对比的结论、覆盖范围与冲突摘要存协同后台，与文件本身及材料、任务的业务状态分开；冲突不写回材料文件，不单独维护处理状态，也不作为材料确认或其他流程的门禁。对比失败应如实表达，不能伪装成没有冲突，也不能阻止流程继续。

一致性对比只读取本地实际文件，不执行 Git 命令，不读取 Git 历史作为对比输入，也不自动拉取、切换或提交材料。手动入口与场景／需求确认后自动发起的非阻断对比都遵守该边界；存在尚未确认的编辑时按已有本地任务状态标为草稿，不调用 Git 判断内容状态，也不把本地内容描述成已确认 Git 内容。本地关联文件缺失时如实表达范围不足，不用 Git 补齐。材料原有确认流程及其 Git 历史管理保持独立职责。

工程方案中，交给模型的内容与计算 hash 的字节来自同一次本地读取；不生成持久文件副本。关系查询仅使用后台已有协同控制字段，不调用会触发 Git 读取或后台同步的固定版本加载路径。确认回执不等待自动对比完成，缺失输入也不得排队补取。结果过期只描述其与本机可见内容的关系，后台不能据此判断其他成员私有草稿。每次对比保留独立记录，不覆盖旧结果，也不继承旧冲突清单。

对比任务只开放受控本地读取和关系目录能力，不开放终端、Git、文件写入、同步或材料确认工具，不能只依赖提示词限制行为。路径须校验实际解析位置仍在当前项目允许的业务材料范围内，拒绝目录穿越或符号链接越界；越界、缺失或不可读均如实归入范围不足，不扩大读取范围补齐输入。

查找从已有场景／需求关系出发，再在当前项目本地业务材料中发现潜在关联，展示依据，不自动改变正式关系。冲突只作为本次对比的摘要留存，数据库与接口都没有“待处理／已处理／已忽略”；“修改相关材料”另行进入写入提议及修订流程。

取消整体关联冻结和强制同批确认，各材料独立占用、修订及确认。用户选择修改方向后，先生成拟修改文件清单和写入提议，用户明确回答后才整篇写入对应草稿，修改后的材料仍须独立确认。冲突是否仍然存在，由下一次对比重新检查，不由上一轮结论或用户的操作声明推定。

该边界允许用户在存在冲突、检查失败或范围不足时继续业务工作，同时通过后端独立记录追踪每次对比的结论。以一致性检查阻断确认、要求先解决冲突才能确认，或将冲突与材料确认捆绑为一个事务，均不符合本决议；旧批次和自动关联来源升版实现也须按新设计删除或改写，不保留兼容层。一致性对比已实现：后台记录与冲突表见 `db/schema.sql:984-1055`，路由见 `apps/collaboration-api/src/routes.ts:84-101`，Host 侧本地对比与关系目录在 `host/application/consistency-comparisons.ts`，并有集成与单元测试覆盖。工程方案沿用项目读写权限与项目内界面提醒；不新增外发消息或定时通知通道。具体契约见[需求协同设计](../design/02-requirements.md)。

对比记录与每条冲突都是不可变快照，没有处理状态、修订号或处理历史；后台只接收有限摘要、关系类型与涉及材料，不接收完整材料、完整 diff、原始模型响应或会话。提醒取目标材料最近一次对比的结论，只表达“最近一次检查不通过”或“范围不足”，不表示冲突已解决，也不表示材料内容已经一致。
