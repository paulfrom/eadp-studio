# 项目原型采用并行任务与整体成果确认

2026-10-26 用户在技术设计首轮明确：多人各自分支并行修改，集成到同一项目原型；需求依赖保留为提示，取消原型认领和确认时的前置完成门禁。原型确认形成整体成果基线，各需求状态独立保留，不批量标记原型完成。该决定取代单需求原型生产完成模型在原型阶段的适用性；场景与需求材料的独立确认及固定历史保持原有含义。

项目独占编辑容易实现，但无法支持用户选择的并行协作。采用独立工作现场与受控集成，接受共享代码冲突和候选重新检查的成本；后端不能继续用某一需求的占用和 materialVersion 充当整体原型身份，也不能将内部任务完成显示成整个原型完成。

需求确认后桌面自动安排开发，或用户发送明确实现／修改指令后，原型 AI 可以在可信 Host 授权的代码范围内直接写入，用户查看实际变更和预览。修改需求 Markdown 仍回到需求阶段审阅写入；代码写入权限不包含成果确认、集成或发布授权。

第二轮进一步明确：按协作事项建立任务，一个事项可跨多个需求，多轮对话沿用其分支和会话，接受集成后结束该事项。干净合并最新认可成果后自动重检并继续原确认；有冲突时允许 AI 在原授权范围内修正，修正后的新成果由用户重新确认，失败保留现场。允许本人可读需求草稿用于原型探索，需求更新仅提醒影响，不强制重新绑定。需求确认后的开发衔接按下述 2026-10-29 决定执行。

本 ADR 记录两轮已确认的业务与架构边界，未代表整份技术设计已确认。详细协议、工程职责、失败恢复和验收用例见[技术设计](../design/prototypes/technical-design.md)。原型任务、开发占用与队列随后已实现（`db/schema.sql:1501`、`packages/contracts/src/index.ts:87-89`、`apps/collaboration-api/src/routes.ts:34-54`）。

用户随后追问“如何保证同一个需求不被两个人同时开发”，暴露了原方案只做分支隔离和关联追溯的不足。采用独立需求开发占用：同项目同需求按身份互斥，与材料版本和材料设计占用分离；任务可原子领取多个需求，阅读参考不领取。首次业务代码写入前由 Host 取得实际开发需求的占用，不增加先锁定固定需求输入包的界面流程。该机制已在后端契约、数据表与路由中实现；现代码仍按整个任务结束统一释放，尚不支持下述新决定要求的逐需求释放与重领，不应表述为新方案已实现。

2026-10-29 用户明确替换 2026-10-27 的“默认串行，手动继续或切换”策略：需求确认后自动形成本地开发队列，桌面串行实施，某项生成成果转入待用户核对后自动继续下一项。用户逐需求查看开发程度、纠偏并重新核对；本地核对不自动构成项目接受或基线。一个协作事项仍可包含多个需求，不能将事项级结束视作每需求已认可。

用户进一步明确每次开发前由后端原子“检查空闲并领取”，是否可开发以当前标识为准：已占用则返回已在开发中；未占用则原子置为占用，不要求 commitId 与远端一致。每次标记仍携带 commitId 作记录；已有占用的成果同步与正常完成解除仍核验指定远端引用。本地缓存只辅助恢复。管理员可主动修改标识，不以 Git 核验为前置；管理操作须审计并失效旧代次，避免旧客户端覆盖新占用。

首次 AI 开发完成经可信 Host 完成 hook 自动提交、推送及后端 commit 核验后释放，不等待用户核对。纠偏前重新原子取得占用；用户已明确纠偏占用保持至最后确认完成，期间 AI 改完可自动推送并同步 commit，但不释放。用户最终确认后推送并核验最新 commit 才解除。被他人占用时保留输入并等待，不借旧现场绕过互斥。释放不等于项目接受；需防止旧代次写入及过期成果覆盖他人修改，详见[本地开发协议](../design/prototypes/local-development-protocol.md)。

队列、开发程度、纠偏和逐项核对只在桌面保存，远端控制需求排他开发占用及提交一致性，不承担本地调度；项目权限、Git 集成及基线职责不因本地核对而改变。队列复用本地账号隔离持久状态，不另建分布式调度系统。用户已明确中断重开后自动继续：先核对后台占用、远端提交与未知操作，再继续已授权的剩余步骤，不盲目重发未知模型请求，不因 hook 重复事件重复提交或推进队列。其他机器没有本地未提交现场时不得声称无缝恢复。具体工程协议见[本地开发协议](../design/prototypes/local-development-protocol.md)。本次仅同步业务决定，产品实现与真实桌面验收尚未完成。

2026-10-29 用户进一步明确原型合并职责：为避免多项目并行时协同后端产生不可控的等待与资源成本，source/candidate 构造、三方合并、冲突处理和合并结果验证全部由桌面 Host 负责。协同后端只管理项目、任务、开发占用、并发代次、候选引用与 SHA、稳定分支状态和接受记录，不再运行 Git、读取代码树或重新计算合并。该决定取代此前“后台独立验证原型合并树”的工程方案，不保留兼容路径。
