# 项目原型采用并行任务与整体成果确认

2026-10-26 用户在技术设计首轮明确：多人各自分支并行修改，集成到同一项目原型；需求依赖保留为提示，取消原型认领和确认时的前置完成门禁。原型确认形成整体成果基线，各需求状态独立保留，不批量标记原型完成。该决定取代单需求原型生产完成模型在原型阶段的适用性；场景与需求材料的独立确认及固定历史保持原有含义。

项目独占编辑容易实现，但无法支持用户选择的并行协作。采用独立工作现场与受控集成，接受共享代码冲突和候选重新检查的成本；后端不能继续用某一需求的占用和 materialVersion 充当整体原型身份，也不能将内部任务完成显示成整个原型完成。

用户发送明确实现或修改指令后，原型 AI 可以在可信 Host 授权的代码范围内直接写入，用户查看实际变更和预览。修改需求 Markdown 仍回到需求阶段审阅写入；代码写入权限不包含确认、集成或发布授权。

第二轮进一步明确：按协作事项建立任务，一个事项可跨多个需求，多轮对话沿用其分支和会话，接受集成后结束该事项。干净合并最新认可成果后自动重检并继续原确认；有冲突时允许 AI 在原授权范围内修正，修正后的新成果由用户重新确认，失败保留现场。允许本人可读需求草稿用于原型探索，需求更新仅提醒影响，不强制重新绑定。需求确认后提供进入原型及准备指令的入口，用户发送后才开始实现，取消每条需求接受后自动发送实现指令的旧行为。

本 ADR 记录两轮已确认的业务与架构边界，未代表整份技术设计已确认。详细协议、工程职责、失败恢复和验收用例见[技术设计](../design/prototypes/technical-design.md)。原型任务、开发占用与队列随后已实现（`db/schema.sql:1501`、`packages/contracts/src/index.ts:87-89`、`apps/collaboration-api/src/routes.ts:34-54`）。

用户随后追问“如何保证同一个需求不被两个人同时开发”，暴露了原方案只做分支隔离和关联追溯的不足。补充的技术方案采用独立需求开发占用：同项目同需求按身份互斥，与材料版本和材料设计占用分离；任务可原子领取多个需求，阅读参考不领取。首次业务代码写入前由 Host 根据明确实现意图领取，不增加先锁定固定需求输入包的界面流程。开发占用在活动任务期间只增不减，随整个任务接受、取消或释放而结束，防止释放单项后旧稿再次夹带提交。该补充也已在后端契约、数据表与路由中实现（`db/schema.sql:1501`、`packages/contracts/src/index.ts:87-89`、`apps/collaboration-api/src/routes.ts:34-54`）。

2026-10-27 用户明确队列策略为“默认串行，手动继续或切换”：一个队列项对应一个协作事项，多需求可同项开发；本人当前客户端一次执行一个事项的 AI 实现，其余事项与开发占用保留。关闭应用不取消事项，不释放需求；重启先核对后台事实并恢复原工作树、会话和输入，再等待用户继续，不自动重发模型请求。队列复用本地账号隔离的持久状态，不为同机重开另建分布式调度系统；其他机器没有本地未提交现场时不得声称无缝恢复。具体工程协议见[桌面运行时](../design/prototypes/desktop-runtime.md)。
