# 本地恢复记录按版本重建，Git 同步一律走后台车道

状态：已确认（2026-10-21）。适用于 `packages/studio-plugin` 的 Host 半边。

启动时 `本地恢复记录格式无效，请保留现场后重新建立当前版本的本地状态` 与"所有 Git 同步都不许阻塞渲染和接口请求"是同一类问题的两面：本机状态与远端 Git 都是工作台的外部依赖，但它们不该决定界面能不能起来、读取能不能返回。因此固定三条契约。

**记录无效即重建，不迁移、不回填。** `StudioStore.read` 先按当前版本解析 `studio-state.json`（`clientId`、`scenarioStructureCheck` 与 11 个集合齐全才算当前版本）；解析失败或字段缺失时，把原文件改名为 `studio-state.json.invalid-<时间戳>` 保留现场，写入一份当前版本的空记录，并通过 `StudioState.recovery` 把保留路径报给界面。旧记录仍能读出的 `clientId` 会被沿用：后台占用绑定该身份，若随重建换掉，本人此前的占用既无法取消也无法认领，只能等管理员处理；本地工作记录是丢失的，设备身份不是。重建后的本地项目凭目录旁的归属标记重新认领：标记记录的是项目身份，打开已初始化项目时按标记认领、核对仓库地址与项目清单后直接绑定，不重新初始化也不重新克隆；无标记的目录仍然拒绝认领并保留现场。理由：本地记录只是可归因工作的现场，项目、任务、占用与基线的权威都在协同后端和 Git；为旧字段写迁移层会让"旧版本记录"永久留在代码里（规则 0），而用户失去的只是本机的任务登记，重新打开项目即可再生。被放弃的替代方案：字段级 backfill（要为每个历史版本维护一份迁移）、启动失败提示用户手工删文件（用户无法判断该删哪一个，实际就是原来的故障）、把归属标记操作 id 提高为唯一认领依据（记录重建后 id 不存在，目录会变成无法复用也无法清理的死角）、把设备身份存进独立文件（多一个所有者，且同样需要处理它的损坏）、重建后分配新身份（本人既有占用变成只有管理员能解除的死锁）。

**Git 同步只在后台车道执行。** `BackgroundLane` 是一条串行车道，与单写者队列并列：投影读取、命令答复都不等它。克隆裸镜像、取单个提交、推送候选、条件推进分支、恢复被中断的集成、模板发布的工作树与提交，全部排进这条车道；同一目标按键去重（`mirror:<project>`、`commit:<dir>:<sha>`、`operation:<id>`、`templates:<id>`、`project-init:<id>`），失败不记住键以便重试。理由：一次 `git fetch`/`git push` 在网络差时可长达一分钟，而它排队时挡住的是整个界面的渲染与所有接口请求。

**同步缺失表现为可重试的待办，而不是错误弹窗。** 读取固定材料只读本地已有的对象（`ProjectWorkspaces.localFixed`）：未命中就返回空、把取回排进车道，投影少一项而不是整体失败；需要基线提交才能建工作树的动作（取任务、模板发布）先核对本地是否有该提交，缺了就排队并在命令答复里说明"项目仓库正在后台同步，请稍后重试当前操作"；集成本身先落 `PendingOperation` 再排队，界面按既有 `pending` 记录展示，`retryOperation`/`retryProjectInitialization` 重新排队同一条工作。这条规则复用已有的待办模型，不新增界面概念。既有的 `publish`/`revokePublication`（远端部署）仍是一次显式长动作：它由用户点击触发、界面本就等待，其中没有对 Git 分支的同步写入。

被放弃的替代方案：在命令里给 Git 调用加超时（超时不会取消已展开的进程，只是把阻塞换成误导性的失败）；让投影自己发起 `git fetch` 并在失败时降级（渲染路径仍被网络拖住）；用新的"同步中"界面状态表示（已有 `pending` 与 `projectInitializations` 承载同一语义）。

验证：`tests/windows-desktop/state-recovery.test.ts` 断言当前版本记录原样读取、旧版本与损坏记录被改名保留且重建后可再次启动、另一用户不继承上一位的保留提示；`tests/windows-desktop/background-lane.test.ts` 断言同键只跑一次、失败键可重试、投影读取在缺镜像/缺提交时立即返回空缺并在车道结算后给出材料、镜像目录随工作区释放；`tests/windows-desktop/projection-lane.test.ts` 断言投影不被卡住的写阻塞；`tests/gitlab-auth-host/projects.test.ts` 断言创建/恢复只排队、重建记录后凭归属标记认领既有目录且不重新初始化、失败落在 `projectInitializations` 的 `unknown` 记录里并可重试；`tests/windows-desktop/{scenario-orchestration,task-recovery,asset-workflow}.test.ts` 断言模板发布、集成与恢复的 Git 工作结算后才可见，且答复先返回。
