# 工作里程碑

依据：`docs/dseign/` 四份设计稿与当前实现（截至 2026-10-19，MaterialCatalog 已纳入 HEAD）。整体进度按资产生命周期推进：**项目场景 → 需求协同 → 原型 → 基线 → 交接清单**，严格串行；每个阶段开工前必须先有明确的设计文档，无文档不允许开工写代码。

## 开工门禁：设计文档先行

- 每阶段第一步是产出设计文档 `docs/design/NN-<阶段名>.md`，经确认后才允许写代码；实现偏离设计时先回写文档再改码。
- 设计文档必含五节：**用户目标**（本阶段结束时用户能做成什么）、**桌面端职责**（做什么界面与交互）、**协同后台职责**（哪些端点/存储/投影变化）、**数据与文档格式**（载体、字段、协议）、**验收标准**（可验证的完成判据）。
- 阶段完成的唯一判据是该阶段验收标准逐条通过，不以「代码写完」为准。

## 设计稿用语与领域语言映射

按 `CONTEXT.md` 执行，不引入平行词汇：

- 设计稿「草稿编辑中 / DRAFT_IN_PROGRESS」→ 确认状态为草稿，任务状态为处理中。
- 设计稿「已固化基线 🔒」→ 确认状态为已确认（固定版本）。
- 设计稿「规则分歧 / 待补全项」→ 核心待澄清项未解决；含核心待澄清项的材料保持草稿、固化被阻断。
- 设计稿「置信度」→ AI 辅助评审产物，仅作用于可选评审过程，不构成确认。
- 设计稿「采纳」→ 作者将 AI 建议写入材料并由作者确认，属 AI 辅助整理，不是他人审批。

## 隐形需求与实现边界

**AI 能力边界**：模型接入由 DSH 宿主统一配置（StudioSettings models 节已明示「工作台不另建模型接入层」），`collaboration-api` 不新增 AI 端点。「后台 AI 开发」指 host 侧的会话编排、结构化协议解析与采纳写回。结构化输出已有两个已验证先例可沿用：`eadp-candidates`（场景拆分候选）与 `eadp-review`（评审意见）文本协议。

**原型指标语义**：设计稿卡片指标对应关系——「BDD 契约 N 项」= 需求文档规则条数（阶段二推导）；「仿真（已模拟/联调中）」= 模板 mock 围栏检查结果（模板是自研 `requestMock` 运行时而非 MSW，沿用现状、卡片文案表「仿真」语义，不引入 MSW 依赖）；「原型验证（验收完）」= 原型确认状态（阶段三回流）。需求规则 ↔ 原型页面/mock 的一致性自动检查涉及契约-路由映射设计，不绑定阶段，列为后续决策点。

**场景设计决议（2026-10-20，用户已整体确认）**：

- 项目场景承载一组细化需求的共同业务范围。所有需求必须来源于至少一个已确认场景，允许多个来源，并绑定各来源的确认版本。
- 用户先命名场景，创建空白 Markdown 文档；左侧与 AI 协同，右侧预览并允许手工编辑当前 MD。场景使用 Markdown，HTML 中的 YAML 文件示例不再作为载体约束；业务流程允许分支、退回及重试，不强制无环。
- 场景不使用分类，新建与确认均不要求分类，也不提供场景分类筛选；由后台按项目递增分配稳定业务编号，如 `SC-0001`。编号项目内唯一、不可手工修改、不回收，改名和修订不变；UUID 继续作为内部技术身份，界面主要显示业务编号。后端已分配稳定业务编号，桌面已消费该编号；材料路径继续使用 UUID。该决策不扩大到阶段二需求分类。
- 新增项目共用的场景模板设置，模板随项目版本保存：内置默认 MD 模板，包含目标与范围、角色、流程、业务规则、异常、验收条件、依据及待澄清项；支持用户上传 MD 模板。新建场景保持空白正文，AI 按模板组织候选，用户采纳后才写入。
- 每个场景绑定所选模板固定版本；更新设置只影响新场景，已有场景由用户显式切换，不能自动改写 MD。新增仅影响本地、可手动切换的“模板结构检查”开关，默认关闭，不同步为项目强制规则；开启时检查所选模板二级章节齐全，允许重排和新增，不从模板文字推导业务门禁。业务内容、版本、权限及后台接受等固定条件始终执行。
- 手工编辑停止输入后自动保存本地 MD，采纳建议时也保存；切换场景或退出前确保保存完成，失败时保留输入并提示。保存草稿不构成场景确认或正式远端同步。
- 每个场景保留独立会话历史；新会话继承当前 MD、所选模板版本及当前选定资料，不自动带入完整旧聊天；旧会话保留并可恢复。
- 自动保存遇到外部文件变更且页面有未保存输入时，保留两份并展示差异，用户选择或合并后再保存；冲突未解决时暂停确认并禁止启动自动修复。若已处于授权修复任务中则终止任务，解决冲突后不自动恢复。
- 同轮建议先选择单条、整块或全部，再一次采纳写回并更新 hash；剩余旧建议保留历史但过期，基于新 MD 重新生成后才能再采纳。
- 资料范围包括文本／Markdown、PDF、Word、Excel、PowerPoint 和图片；每份资料区分已读取、部分读取和失败，AI 只能引用实际读取的内容，上传成功不等于已读取。当前 Agent 资料读取链路仍须实现与样本验收。
- 普通对话整理中，AI 首稿及修改均须用户采纳后写入草稿。记录文件 hash，内容变化时重新读取；基于旧 hash 的 AI 建议过期，须读取最新 MD 后重新生成，禁止直接覆盖。
- 仅用户选定的正式依据随确认场景归档，保留来源与 hash；会话和临时资料留在本地。
- 用户最终确认场景并由协同后台接受后，选择立即或稍后拆分。立即拆分先生成候选，用户选择后才创建需求草稿，需求须独立完善与确认；稍后拆分保留已确认场景上的入口。
- 场景确认遇到阻断时，用户可点击一次“AI 修复并确认”，授权本轮基于已有依据修正结构、引用及内容，直接写入后重算 hash、执行完整门禁并由可信 Host 自动再次提交确认，无须再逐次采纳。缺失业务答案时暂停询问用户。
- 自动修复最多 3 轮；相同阻断无改善、缺少可读取依据或发生并发编辑时提前停止，保留现场并说明原因。仅后台已接受才显示已确认；接受结果未知时先核对状态，不盲目重复确认。
- 缺少业务答案时暂停；用户提交“补充并继续修复确认”后续接同一任务，累计最多 3 轮，重读并重检版本、权限及占用。普通聊天回复不自动恢复；暂停期间若文件被修改，终止旧授权并保留现场。
- 草稿名称和占用状态对其他项目成员可见；草稿正文和会话留在本地。修订期间其他成员继续读取旧确认版及修订／占用状态。
- 已确认场景先只读打开；用户点击“开始修订”，查看影响清单后显式启动修订和关联需求冻结，沿用已有批次确认规则。
- 卡片分别展示创建人、当前编辑人及修订状态，确认详情展示确认人和时间；本阶段不新增业务负责人指派或转交。
- 用户已于 2026-10-20 整体确认阶段一设计（含工程方案），作为实施依据；设计开工条件已满足，后端修正已落地并开展隔离验证，桌面与 Host 代码改造已完成；本轮仅做代码校验，38 条完整产品验收未执行。

## 阶段一 项目场景（形态奠基）

**当前执行顺序**：先完成协同后端修正，再开始桌面端修正。后端关系存储、编号幂等、固定 Git 校验、需求来源、修订批次、模板独立发布及修复授权控制已落地；桌面与 Host 已完成契约、编辑、会话、资料、模板及修复确认代码改造；按用户要求仅做代码校验，阶段一完整产品验收未执行。分类清单、接口边界及验证记录见[阶段一修正与验证记录](design/scenarios/implementation.md)。

设计文档：[项目场景设计](design/scenarios/01-scenarios.md)。**设计已于 2026-10-20 由用户整体确认，按协同后端、桌面端两类串行修正。** MaterialCatalog 已纳入 HEAD，作为现状参考。

**用户目标**：用户先为业务场景命名，生成空白 Markdown 文档，通过左侧 AI 对话结合所提供资料推理和设计，采纳产出或手工编辑右侧 MD；门禁通过后确认场景，由协同后台记录已接受的固定版本，再选择是否立即拆分更细节的需求。

**设计文档必须覆盖**：

- 桌面端：场景列表（卡片信息结构：确认状态徽章、创建人、当前编辑人、修订状态、资产编号；筛选 Tab；统计汇总条；分页）；命名后创建空白 MD；场景模板设置（内置默认、上传 MD）；双栏工作区（左对话 + 右 Markdown 文档、预览/源码编辑、导出、折叠为全屏对话）；资料输入与正式依据选择；门禁状态条与 Working Tree 展示；场景智能体交互（结构化建议卡、单条/整块/一键全部采纳、新会话、快捷引导指令、模型标识）；场景确认按钮及确认后的拆分需求选择；确认版只读查看及影响确认后的显式修订。
- 协同后台：场景实体、编号、占用、确认、固定版本既有链路的差距核对（`EntityView` 展示字段扩展、确认状态投影）；取消场景的分类字段及必填校验，不以默认分类保留旧约束。
- 数据与格式：场景 Markdown 载体及内置／上传模板（路径、元信息及模板应用规则按已确认设计执行）；文件 hash 记录、变化后重读及旧建议失效约定；结构化建议协议 schema（沿用 `eadp-candidates`/`eadp-review` 文本协议模式）；正式依据来源与 hash；需求至少一个固定场景来源的约束。

**代码实现范围**：沿用现有 MaterialCatalog 及 Markdown 材料链路补齐差距，按已确认设计取消场景分类、增加项目内业务编号并调整解析与校验；双栏工作区重构；场景智能体专属 preset 与采纳写回命令（含 `newSession`）；文件 hash 跟踪与重读；门禁聚合、授权修复续接及场景确认串联 Git 固定版本和后台接受；确认后由用户选择是否发起需求拆分。

**验收**：命名场景 → 创建空白 MD → 提供资料并对话整理 → 建议卡采纳／手工编辑 → hash 变化后重读 → 门禁通过 → 用户确认 → 后台接受 → 选择立即拆分或稍后处理，全程可用；核心待澄清项存在时确认被阻断；场景 Markdown 解析校验与需求阶段既有行为通过相应验证。

本阶段同时是形态奠基：列表范式、双栏工作区、门禁状态条、固化动作、建议协议均在此阶段落地，后续阶段复用同范式做增量。

## 阶段二 需求协同

设计文档：`docs/design/02-requirements.md`。

**用户目标**：从已确认场景拆分形成需求，所有需求均有场景来源；与「需求设计智能体」对话整理需求 Markdown（业务背景、时序、GWT 规则），规则关联场景内容，确认固化；需求列表呈现 BDD 契约数、待补全项、规则分歧与已固化基线筛选。

**设计文档必须覆盖**：

- 桌面端：需求列表（场景关联芯片、指标徽章、筛选 Tab）；需求 Markdown 载体的文档面板；需求智能体会话（复用阶段一协议与双栏骨架，换专属 preset）；固化按钮与门禁（无悬空场景引用）。
- 协同后台：需求实体、前置需求校验与环检测（`validatePrerequisites`）、scenarioIds 双向关联校验、场景确认冻结关联需求（frozenBy）联动差距核对。
- 数据与格式：`docs/requirements/REQ-YYYYMM-NN.md` frontmatter 与规则章节；指标推导口径（契约数=规则条数、待补全=核心待澄清项计数、分歧=冲突标记）。

**验收**：需求↔场景双向关联校验生效；场景确认后关联需求冻结；需求固化后列表状态、筛选 Tab 与指标徽章正确。

## 阶段三 原型

设计文档：`docs/design/03-prototypes.md`。

**用户目标**：从已确认需求认领原型，AI 按 AGENT.md 边界生成页面与 mock，工程检查与仿真围栏通过后在工作台内嵌预览并验收，确认原型完成；需求卡片随之呈现仿真、原型验证、BDD 契约数指标。

**设计文档必须覆盖**：

- 桌面端：原型阶段目录（按关联需求聚合，页面/路由清单取自模板 `routes.json`，替代现在复用需求目录的呈现）；内嵌预览面板（loopback 地址，保留外开入口）；检查/预览/确认操作条；需求卡片指标消费。
- 协同后台：claim/integrations 既有链路差距核对；`CheckEvidence`（工程/mock/browser）与原型确认状态写入 `EntityView` 投影的接口约定。
- 数据与格式：检查证据投影字段；指标取数口径（仿真=mock 围栏检查结果、原型验证=原型确认状态、契约数=阶段二规则计数）。

**验收**：需求卡片三项指标可取数且随检查、确认动作更新；预览内嵌可用；认领 → 生成 → 检查 → 确认 → 集成既有链路回归通过。

## 阶段四 基线

设计文档：`docs/design/04-baselines.md`。

**用户目标**：原型确认后自动形成固定基线；用户在「基线确认」阶段查看基线、执行复用停用与恢复，列表头部看到需求覆盖率，标题栏呈现仓库同步状态。

**设计文档必须覆盖**：

- 桌面端：基线列表增强；复用资格（VersionPanel）走查补齐；需求覆盖率统计展示；标题栏仓库/分支同步状态指示（对应设计稿「main (已同步)」）。
- 协同后台：baselines、eligibility、adoptions 既有链路差距核对（资格变更投影到列表）。
- 数据与格式：需求覆盖率口径（关联已固化需求的场景占比）。

**验收**：原型确认 → 基线生成 → 基线列表可见；复用停用/恢复生效且保留原内容与历史；覆盖统计与仓库状态展示正确。

## 阶段五 交接清单

**用户目标**：从基线一键生成交接清单材料，AI 会话完善交接内容，研发侧收悉回执，交接状态全程可追溯。

## 依赖与顺序

严格按资产生命周期串行：阶段一 → 二 → 三 → 四 → 五 → 六，不并行开阶段。阶段一是形态奠基（列表、双栏、门禁、固化、建议协议），后续阶段复用范式只做增量，这也是串行能成立的前提。每阶段以设计文档确认为开工条件，以验收标准逐条通过为完成条件。跨阶段通用决策点（需求规则与原型 mock/页面一致性自动检查、契约一致性统计指标）不绑定阶段，另行立项。
