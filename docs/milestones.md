# 工作里程碑

依据：`docs/dseign/` 四份设计稿与当前实现（截至 2026-10-19，含工作区未提交的 MaterialCatalog 工作）。整体进度按资产生命周期推进：**项目场景 → 需求协同 → 原型 → 基线 → 交接清单**，严格串行；每个阶段开工前必须先有明确的设计文档，无文档不允许开工写代码。

## 开工门禁：设计文档先行

- 每阶段第一步是产出设计文档 `docs/design/NN-<阶段名>.md`，经确认后才允许写代码；实现偏离设计时先回写文档再改码。
- 设计文档必含五节：**用户目标**（本阶段结束时用户能做成什么）、**桌面端职责**（做什么界面与交互）、**协同后台职责**（哪些端点/存储/投影变化）、**数据与文档格式**（载体、字段、协议）、**验收标准**（可验证的完成判据）。
- 阶段完成的唯一判据是该阶段验收标准逐条通过，不以「代码写完」为准。

## 设计稿用语与领域语言映射

按 `CONTEXT.md` 执行，不引入平行词汇：

- 设计稿「草稿编辑中 / DRAFT_IN_PROGRESS」→ 确认状态为草稿，任务状态为处理中。
- 设计稿「已固化基线 🔒」→ 确认状态为已确认（固定版本）。
- 设计稿「规则分歧 / 待补全项」→ 核心待澄清项未解决；含核心待澄清项的材料保持草稿、固化被阻断。
- 设计稿「置信度」→ AI 辅助评审产物，仅作用于可选评审过程，不构成确认。
- 设计稿「采纳」→ 作者将 AI 建议写入材料并由作者确认，属 AI 辅助整理，不是他人审批。

## 隐形需求与实现边界

**AI 能力边界**：模型接入由 DSH 宿主统一配置（StudioSettings models 节已明示「工作台不另建模型接入层」），`collaboration-api` 不新增 AI 端点。「后台 AI 开发」指 host 侧的会话编排、结构化协议解析与采纳写回。结构化输出已有两个已验证先例可沿用：`eadp-candidates`（场景拆分候选）与 `eadp-review`（评审意见）文本协议。

**原型指标语义**：设计稿卡片指标对应关系——「BDD 契约 N 项」= 需求文档规则条数（阶段二推导）；「仿真（已模拟/联调中）」= 模板 mock 围栏检查结果（模板是自研 `requestMock` 运行时而非 MSW，沿用现状、卡片文案表「仿真」语义，不引入 MSW 依赖）；「原型验证（验收完）」= 原型确认状态（阶段三回流）。需求规则 ↔ 原型页面/mock 的一致性自动检查涉及契约-路由映射设计，不绑定阶段，列为后续决策点。

## 阶段一 项目场景（形态奠基）

设计文档：`docs/design/01-scenarios.md`（工作区已有的 MaterialCatalog 未提交实现作为现状基线纳入文档裁决，文档确认前不继续扩散新代码）。

**用户目标**：用户新建业务场景，与「场景拓扑智能体」对话把业务口述整理为场景 YAML 规约（角色职责、时序步骤、GIVEN/WHEN/THEN 验收规则），门禁通过后一键固化，得到第一批已确认场景资产。

**设计文档必须覆盖**：

- 桌面端：场景列表（卡片信息结构：确认状态徽章、负责人、资产编号；筛选 Tab；统计汇总条；分页）；双栏工作区（左对话 + 右 YAML 文档、预览/源码切换、导出、折叠为全屏对话）；门禁状态条与 Working Tree 展示；场景智能体交互（结构化建议卡、单条/整块/一键全部采纳、新会话、快捷引导指令、模型标识）；一键固化按钮。
- 协同后台：场景实体、分类、占用、确认、固定版本既有链路的差距核对（`EntityView` 展示字段扩展、确认状态投影）。
- 数据与格式：场景 YAML 规约载体（`contracts/scenarios/SC-NN_spec.yaml`，frontmatter + 角色 + 时序 + RULE_NN GWT）；结构化建议协议 schema（沿用 `eadp-candidates`/`eadp-review` 文本协议模式）。

**实现要点（文档确认后）**：收尾提交现有 MaterialCatalog；按 YAML 载体重写 `parseMaterial` 与 `MaterialMetadataSchema`，直接替换旧格式不做兼容；双栏工作区重构；场景智能体专属 preset 与采纳写回命令（含 `newSession`）；门禁聚合与一键固化串联 Git commit + `confirmMaterial`。

**验收**：新建场景 → 对话整理 → 建议卡采纳 → 门禁通过 → 一键固化 → 列表状态联动全程可用；规则分歧未决（核心待澄清项存在）时固化被阻断；两种解析校验单测通过。

本阶段同时是形态奠基：列表范式、双栏工作区、门禁状态条、固化动作、建议协议均在此阶段落地，后续阶段复用同范式做增量。

## 阶段二 需求协同

设计文档：`docs/design/02-requirements.md`。

**用户目标**：在已确认场景下新建需求，与「需求设计智能体」对话整理需求 Markdown（业务背景、时序、GWT 规则），规则关联场景规约，确认固化；需求列表呈现 BDD 契约数、待补全项、规则分歧与已固化基线筛选。

**设计文档必须覆盖**：

- 桌面端：需求列表（场景关联芯片、指标徽章、筛选 Tab）；需求 Markdown 载体的文档面板；需求智能体会话（复用阶段一协议与双栏骨架，换专属 preset）；固化按钮与门禁（无悬空场景引用）。
- 协同后台：需求实体、前置需求校验与环检测（`validatePrerequisites`）、scenarioIds 双向关联校验、场景确认冻结关联需求（frozenBy）联动差距核对。
- 数据与格式：`docs/requirements/REQ-YYYYMM-NN.md` frontmatter 与规则章节；指标推导口径（契约数=规则条数、待补全=核心待澄清项计数、分歧=冲突标记）。

**验收**：需求↔场景双向关联校验生效；场景确认后关联需求冻结；需求固化后列表状态、筛选 Tab 与指标徽章正确。

## 阶段三 原型

设计文档：`docs/design/03-prototypes.md`。

**用户目标**：从已确认需求认领原型，AI 按 AGENT.md 边界生成页面与 mock，工程检查与仿真围栏通过后在工作台内嵌预览并验收，确认原型完成；需求卡片随之呈现仿真、原型验证、BDD 契约数指标。

**设计文档必须覆盖**：

- 桌面端：原型阶段目录（按关联需求聚合，页面/路由清单取自模板 `routes.json`，替代现在复用需求目录的呈现）；内嵌预览面板（loopback 地址，保留外开入口）；检查/预览/确认操作条；需求卡片指标消费。
- 协同后台：claim/integrations 既有链路差距核对；`CheckEvidence`（工程/mock/browser）与原型确认状态写入 `EntityView` 投影的接口约定。
- 数据与格式：检查证据投影字段；指标取数口径（仿真=mock 围栏检查结果、原型验证=原型确认状态、契约数=阶段二规则计数）。

**验收**：需求卡片三项指标可取数且随检查、确认动作更新；预览内嵌可用；认领 → 生成 → 检查 → 确认 → 集成既有链路回归通过。

## 依赖与顺序

严格按资产生命周期串行：阶段一 → 二 → 三 → 四 → 五 → 六，不并行开阶段。阶段一是形态奠基（列表、双栏、门禁、固化、建议协议），后续阶段复用范式只做增量，这也是串行能成立的前提。每阶段以设计文档确认为开工条件，以验收标准逐条通过为完成条件。跨阶段通用决策点（需求规则与原型 mock/页面一致性自动检查、契约一致性统计指标）不绑定阶段，另行立项。
