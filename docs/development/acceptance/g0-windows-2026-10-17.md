## 阻断缺陷：P1 建仓前用户状态被缓存放行

位置：[gitlab.ts:174](../../../apps/collaboration-api/src/auth/gitlab.ts#L174)。`namespace()` 使用缓存 `user()`（[第 80 行](../../../apps/collaboration-api/src/auth/gitlab.ts#L80)，TTL 60 秒），没有实时读取用户有效性。
调用方在 [projects.ts:64](../../../apps/collaboration-api/src/projects.ts#L64) 检查后，于 [第 67 行](../../../apps/collaboration-api/src/projects.ts#L67) 用管理令牌创建远端仓库。
直到 [projects.ts:91](../../../apps/collaboration-api/src/projects.ts#L91) 的 `grantCreator()` 调用 [gitlab.ts:182](../../../apps/collaboration-api/src/auth/gitlab.ts#L182) 实时检查，才会拒绝已封禁用户。
这违反当前 [新建项目交接:32](../handoffs/studio-project-creation-timeout.md#L32) 的建仓前实时用户检查约定。

复现使用真实产品 `GitLab` / `ReadThrough` 类、合成 fetch 上游和内存缓存：

1. 令 `/users/42` 返回 active，调用 `gitlab.user(42)` 暖缓存。
2. 将合成 `/users/42` 改为 blocked，组成员 API 保持 active/Maintainer。
3. 调用 `namespace(actor, 1)`：错误接受，调用序列只有组成员与群组详情，没有 `/users/42`。
4. 调用 `grantCreator()`：实时用户检查拒绝 `GITLAB_USER_INACTIVE`。
5. 清空缓存后调用 `namespace()`：同样拒绝 `GITLAB_USER_INACTIVE`，构成负向对照。

```powershell
node --import ./apps/collaboration-api/node_modules/tsx/dist/loader.mjs .local/acceptance/g0-windows-20261017/review/namespace-cached-user-probe.mjs
```

退出码 `0`，`status=reproduced`；脚本、调用序列与脱敏结果在 `review/namespace-cached-user-probe.mjs`、`review/namespace-cached-user-probe-result.json`。
`actualGitLabBlockingVerified=false`、`externalWrites=false`：没有封禁真实 GitLab 用户，也没有在该实验中实际建仓。
副作用结论来自上述真实代码调用顺序：暖缓存放行后会先发建仓请求，再被后续实时用户检查拒绝。
现有 [gitlab.test.ts:305](../../../apps/collaboration-api/src/auth/gitlab.test.ts#L305) 只断言群组成员实时读取，没有暖缓存后用户封禁负向，不能证明这条授权路径成立。
